## 3. 服务启停操作

### 3.1 K8s 环境（生产/ Staging）

#### 3.1.1 启动全部服务

```bash
# 1. 确认集群与命名空间
kubectl config current-context          # 应为 prod-context
kubectl get ns ia-prod

# 2. 按顺序启动（依赖优先）
kubectl scale deploy/keycloak -n ia-prod --replicas=2
kubectl rollout status deploy/keycloak -n ia-prod --timeout=300s   # 等待就绪

kubectl scale deploy/postgresql timescaledb neo4j minio kafka -n ia-prod --replicas=1
kubectl rollout status deploy/neo4j -n ia-prod --timeout=300s

kubectl scale deploy/server agent -n ia-prod --replicas=2
kubectl rollout status deploy/server -n ia-prod --timeout=300s

kubectl scale deploy/web -n ia-prod --replicas=2
kubectl rollout status deploy/web -n ia-prod --timeout=180s
```

#### 3.1.2 逐组件启停

| 组件 | 停止 | 启动 |
|---|---|---|
| server | `kubectl scale deploy/server -n ia-prod --replicas=0` | `kubectl scale deploy/server -n ia-prod --replicas=2` |
| agent | `kubectl scale deploy/agent -n ia-prod --replicas=0` | `kubectl scale deploy/agent -n ia-prod --replicas=2` |
| web | `kubectl scale deploy/web -n ia-prod --replicas=0` | `kubectl scale deploy/web -n ia-prod --replicas=2` |
| neo4j | `kubectl scale sts/neo4j -n ia-prod --replicas=0` | `kubectl scale sts/neo4j -n ia-prod --replicas=1` |
| kafka | `kubectl scale sts/kafka -n ia-prod --replicas=0` | `kubectl scale sts/kafka -n ia-prod --replicas=1` |

#### 3.1.3 重启单个组件

```bash
# 滚动重启（不中断服务，推荐）
kubectl rollout restart deploy/server -n ia-prod
kubectl rollout status deploy/server -n ia-prod

# 强制删除异常 Pod（由 Deployment 自动重建）
kubectl delete pod <pod-name> -n ia-prod --grace-period=30
```

### 3.2 Docker Compose 单机环境（演示/培训）

```bash
cd /opt/industryagent/infra

# 全部启动
docker compose up -d
docker compose ps                  # 全部应为 Up (healthy)

# 按服务操作
docker compose restart server      # 重启业务后端
docker compose stop agent          # 停止智能体服务
docker compose logs -f server --tail=100   # 跟踪日志

# 全部停止（保留数据卷）
docker compose down

# 危险：停止并删除数据卷（仅用于培训数据重置，见培训教材 §9.3）
# docker compose down -v
```

> **启动顺序原则**：存储层（PG/Timescale/Neo4j/MinIO/Kafka）→ Keycloak → server → agent → web。停止顺序相反。

## 4. 日志管理

### 4.1 日志位置

| 服务 | 位置（K8s） | 位置（docker compose） |
|---|---|---|
| server | `kubectl logs deploy/server` + 挂载卷 `/app/logs/server-*.log` | `/opt/industryagent/logs/server/` |
| agent | `kubectl logs deploy/agent` + `/app/logs/agent-*.log` | `/opt/industryagent/logs/agent/` |
| web/Nginx | Ingress 日志 `kubectl logs -n ingress-nginx` | `/opt/industryagent/logs/nginx/` |
| PostgreSQL | `kubectl logs sts/postgresql`，`/var/lib/postgresql/data/log/` | `/opt/industryagent/logs/pg/` |
| Kafka | `kubectl logs sts/kafka` | `/opt/industryagent/logs/kafka/` |
| 审计日志（业务） | PostgreSQL 表 `audit_log`（**非文件日志，保留 1 年**） | 同左 |

### 4.2 常用查询命令

```bash
# 实时跟踪业务后端错误
kubectl logs -f deploy/server -n ia-prod --since=10m | grep -iE 'error|warn'

# 查看某次请求全链路（trace_id 关联 server 与 agent）
kubectl logs deploy/server -n ia-prod | grep 'trace_id=abc123'
kubectl logs deploy/agent  -n ia-prod | grep 'trace_id=abc123'

# 查询审计日志（业务审计）
kubectl exec -n ia-prod deploy/postgresql -- psql -U ia_admin -d ia \
  -c "SELECT created_at, user_id, action, object, result FROM audit_log
      WHERE created_at > now() - interval '24 hours'
      ORDER BY created_at DESC LIMIT 100;"

# 审计日志按操作类型统计（月度合规自查）
kubectl exec -n ia-prod deploy/postgresql -- psql -U ia_admin -d ia \
  -c "SELECT action, count(*) FROM audit_log
      WHERE created_at > now() - interval '30 days' GROUP BY action ORDER BY 2 DESC;"

# 审计日志归档至 MinIO（每月执行）
kubectl exec -n ia-prod deploy/postgresql -- psql -U ia_admin -d ia -c \
  "COPY (SELECT * FROM audit_log WHERE created_at < now()-interval '12 months') TO STDOUT WITH CSV HEADER" \
  | mc pipe local/ia-audit/audit_archive_$(date +%Y%m).csv
```

### 4.3 日志轮转配置与保留策略

| 日志类型 | 轮转机制 | 保留策略 | 配置位置 |
|---|---|---|---|
| server/agent 应用日志 | logrotate（size 100M，rotate 14，compress） | 14 天 | `infra/logrotate/ia-logrotate.conf` |
| Nginx Ingress 日志 | K8s 原生按天轮转 | 7 天 | 节点 `/etc/logrotate.d/kubernetes-logs` |
| PostgreSQL 慢查询日志 | logrotate（weekly，rotate 8） | 60 天 | `postgresql.conf` + logrotate |
| Kafka 日志 | log4j SizeBasedTriggeringPolicy 512M × 10 | ~10 个文件 | `infra/kafka/log4j.properties` |
| Prometheus 数据 | TSDB 保留参数 | 90 天 | `--storage.tsdb.retention.time=90d` |
| **审计日志（数据库）** | 数据库分区按月自动清理 | **1 年（强制）** | TimescaleDB 策略 + `audit_retention.sql` |
| MinIO 对象（缺陷图等） | ILM 生命周期 | 2 年 | `mc ilm add --expiry-days 730 local/ia-files` |

> 审计日志 1 年保留期为合规要求，任何缩短操作需经客户方安全负责人书面批准。

## 5. 备份与恢复

### 5.1 备份计划表

| 备份对象 | 方式 | 频率 | 时间窗口 | 保留 | 存放位置 |
|---|---|---|---|---|---|
| PostgreSQL（业务+审计） | pg_basebackup 全量 | 每日 01:00 | 01:00-02:00 | 14 份 | MinIO ia-backup + 异地 NAS |
| PostgreSQL | WAL 归档增量 | 每小时（连续） | 持续 | 14 天 | 同上 |
| TimescaleDB（时序） | pg_dump 分区导出（近 7 天热数据） | 每日 02:00 | 02:00-03:00 | 14 份 | 同上 |
| Neo4j | neo4j-admin dump | 每周周日 03:00 | 03:00-03:30 | 4 份 | 同上 |
| MinIO | mc mirror 增量 | 每日 03:30 | 03:30-04:00 | 镜像同周期 | 异地 NAS |
| Keycloak realm 配置 | kc.sh export | 每周日 04:00 | - | 8 份 | 配置库 Git + MinIO |
| Grafana/Prometheus 配置 | Git 快照 | 每次变更 | - | 无限 | 配置库 Git |

> 异地存放要求：备份同时写入 MinIO 备份桶与客户异地 NAS（`/backup/industryagent/`），每周校验一次异地副本完整性（`sha256sum -c`）。

### 5.2 各组件备份与恢复命令

#### 5.2.1 PostgreSQL / TimescaleDB

```bash
# 备份（全量）
kubectl exec -n ia-prod sts/postgresql -- bash -c \
  'pg_basebackup -U backup_user -D /tmp/base -Fp -Xs -P' && \
  kubectl cp ia-prod/postgresql-0:/tmp/base /data/backup/pg_base_$(date +%F)

# 备份（逻辑导出，适合部分恢复）
kubectl exec -n ia-prod sts/postgresql -- pg_dump -U ia_admin -d ia -Fc \
  -f /tmp/ia_$(date +%F).dump
kubectl cp ia-prod/postgresql-0:/tmp/ia_$(date +%F).dump /data/backup/

# 恢复步骤（RTO 参考：单库 < 1 小时）
# 1) 停止写入：kubectl scale deploy/server agent -n ia-prod --replicas=0
# 2) 恢复全量：
kubectl exec -n ia-prod sts/postgresql -- bash -c \
  'rm -rf /var/lib/postgresql/data/* && \
   pg_ctl -D /var/lib/postgresql/data start -o "-c restore_command=..."' # 或使用 pgBackRest 一键恢复
# 3) 恢复增量 WAL 至目标时间点（PITR）：配置 recovery_target_time
# 4) 验证：psql 连接、关键表行数抽查（batches/events/audit_log）
# 5) 恢复服务：kubectl scale deploy/server agent -n ia-prod --replicas=2
```

#### 5.2.2 Neo4j

```bash
# 备份
kubectl exec -n ia-prod sts/neo4j -- neo4j-admin database dump neo4j \
  --to-path=/data/backup/neo4j_$(date +%F).dump

# 恢复
# 1) 停库：kubectl exec -n ia-prod sts/neo4j -- neo4j stop
# 2) 恢复：kubectl exec -n ia-prod sts/neo4j -- neo4j-admin database load neo4j \
#    --from-path=/data/backup/neo4j_2026-10-15.dump
# 3) 启库并验证：MATCH (n) RETURN count(n) 应与备份记录一致
```

#### 5.2.3 MinIO

```bash
# 备份（增量镜像到备份卷）
mc mirror local/ia-files /data/backup/minio/ --overwrite

# 恢复
mc cp --recursive /data/backup/minco/* local/ia-files/   # 注意核对桶策略
# 验证：mc ls --recursive local/ia-files | wc -l 与备份清单比对
```

#### 5.2.4 Keycloak

```bash
# 备份 realm
kubectl exec -n ia-prod deploy/keycloak -- /opt/keycloak/bin/kc.sh export \
  --realm xl --users true --file /tmp/xl_realm_$(date +%F).json

# 恢复 realm
kubectl exec -n ia-prod deploy/keycloak -- /opt/keycloak/bin/kc.sh import \
  --file /tmp/xl_realm_2026-10-15.json
# 验证：管理员登录管理台，抽测 2 个业务账号 SSO 登录
```

## 6. 常见故障处理表

| 编号 | 故障现象 | 可能原因 | 处理步骤 |
|---|---|---|---|
| 6.1 | 服务起不来（Pod CrashLoopBackOff） | 镜像损坏/配置错误/依赖未就绪/OOM | ① `kubectl describe pod <pod> -n ia-prod` 看 Events；② `kubectl logs <pod> --previous` 看崩溃前日志；③ 依赖检查（PG/Keycloak 是否就绪）；④ OOM 则调大内存 limit；⑤ 无法定位时回滚上一版本（见 05-回滚方案） |
| 6.2 | 数据库连接满（too many connections） | server 连接池未释放/突发流量 | ① `SELECT count(*),state FROM pg_stat_activity GROUP BY state;` ② 杀掉 idle > 30min 会话；③ 检查 egg-sequelize 连接池配置（pool max 建议按副本数均分 max_connections×0.8）；④ 复发则接入 pgbouncer |
| 6.3 | Kafka 积压（Lag 持续上升） | 消费者挂了/流量突增/消费者处理慢 | ① 确认 agent/流处理 Pod 是否 Running；② 查看消费者组状态；③ 扩容消费副本 `kubectl scale deploy/agent --replicas=4`；④ 检查下游 PG 写入是否成瓶颈（慢查询）；⑤ 积压 > 1 小时按预案降级并上报 |
| 6.4 | 磁盘告警（>85%） | 日志膨胀/备份堆积/时序数据膨胀 | ① `du -sh /data/* \| sort -h` 定位大目录；② 清理超期日志与临时导出；③ 校验并清理过期备份（保留期内不删）；④ 确认 Timescale 压缩与保留策略运行正常；⑤ 扩容 PV |
| 6.5 | Grafana 无数据 | Prometheus 抓取失败/Prometheus 重启/target down | ① Grafana → Status → 检查 datasource 连接；② Prometheus Targets 页找 down 项；③ 修复后等待 2 个抓取周期；④ 检查 Prometheus 磁盘是否写满 |
| 6.6 | 备份失败 | 目标空间不足/凭据过期/网络抖动 | ① 查看备份日志错误行；② 检查 MinIO/NAS 空间与凭据；③ 空间不足清理过期备份后手动补跑；④ 连续两天失败须升级至项目经理 |
| 6.7 | Keycloak 登录失败 | Keycloak 服务异常/PG 后端不可达/时钟漂移/证书过期 | ① `kubectl get pods -n ia-prod \| grep keycloak`；② 看 Keycloak 日志 DB 连接错误；③ `chronyc sources` 校时；④ 证书过期则更换（§7.2） |
| 6.8 | 前端打不开但 API 正常 | web Deployment 异常/Ingress 配置/缓存 | ① `kubectl get pods -n ia-prod \| grep web`；② `kubectl describe ingress ia-ingress`；③ 强刷 Ctrl+F5 清缓存；④ 验证 Nginx 配置中 /api、/agent 路由 |
| 6.9 | WebSocket 推送中断 | Ingress 超时配置/网络策略 | ① 确认 Ingress annotation `proxy-read-timeout` ≥ 3600；② 检查 NetworkPolicy 是否放行 WSS；③ 前端断线重连日志验证 |
| 6.10 | 根因分析超时（>5 分钟） | agent 依赖服务慢/图谱查询慢/LLM 后端超时 | ① agent 日志定位耗时环节（图谱/检索/推理）；② Neo4j 查询 > 10s 则加索引；③ 检查 GPU/LLM 推理服务队列；④ 单事件重试；⑤ 频发则扩展分析 worker 数 |
| 6.11 | Timescale 查询变慢 | 未命中压缩/膨胀/缺索引 | ① `timescaledb_information.job_stats` 确认压缩 job；② EXPLAIN ANALYZE 定位慢查询；③ 重建索引（低峰期）；④ 缩短超 hypertable 保留 |
| 6.12 | Neo4j 内存溢出 | 堆配置不足/Cypher 全表扫描 | ① `kubectl logs sts/neo4j` 查 OOM；② 调整 `server.memory.heap.max_size`；③ 给热点节点属性建索引；④ 重启 Neo4j（图谱服务可短暂中断） |
| 6.13 | MinIO 写入失败 | 桶配额满/磁盘满/时间不同步导致签名错误 | ① `mc admin info local`；② 清理过期对象/扩容；③ 校时 `timedatectl`；④ 核对应用 AK/SK |
| 6.14 | 前端报表导出 502 | 导出耗时超 Ingress 超时 | ① 导出走异步任务队列（server 已支持），确认前端调用了异步接口；② 调大超时或分批导出；③ 查看 server 导出 worker 状态 |
| 6.15 | 审计日志缺失 | server 审计中间件异常/审计写入阻塞 | ① 对比 audit_log 写入曲线与流量曲线；② 重启 server；③ 排查 PG audit 分区是否可用；④ 缺失期间段登记并书面报备客户方 |
| 6.16 | 节点 NotReady | kubelet 异常/资源耗尽/网络故障 | ① `kubectl describe node`；② 恢复 kubelet/释放资源；③ 期间 Pod 漂移到健康节点，验证服务自愈；④ 单节点集群升级为多节点（生产强制要求） |
| 6.17 | 误报率突增 | 数据漂移/传感器故障/阈值未更新 | ① 数据健康度页核对数据源状态；② 复核最近变更（规则/阈值配置）；③ 临时放宽规则阈值并通知工艺；④ 复盘纳入下次模型迭代 |

> 升级路径：值班人员 30 分钟内未定位 → 升级至运维负责人；影响核心链路 → 立即通报项目经理并按《05-回滚方案》评估回滚。

### 7.2 执行步骤

```bash
# 1. 冻结流量窗口（可选：切换维护页）
kubectl apply -f infra/maintenance/on.yaml -n ia-prod

# 2. 更新镜像标签（GitOps：修改配置仓库 tag 后 ArgoCD 同步）
kubectl set image deploy/server server=registry.local/ia/server:v1.1.0 -n ia-prod
kubectl set image deploy/agent agent=registry.local/ia/agent:v1.1.0 -n ia-prod
kubectl set image deploy/web   web=registry.local/ia/web:v1.1.0 -n ia-prod

# 3. 执行数据库迁移（先于 server 滚动，脚本可重入）
kubectl create job --from=cronjob/db-migrate db-migrate-manual-$(date +%s) -n ia-prod
kubectl logs job/db-migrate-manual-<id> -n ia-prod   # 确认成功

# 4. 滚动更新并观察
kubectl rollout status deploy/server -n ia-prod --timeout=600s
kubectl rollout status deploy/agent  -n ia-prod --timeout=600s
kubectl rollout status deploy/web    -n ia-prod --timeout=300s

# 5. 观察 15 分钟（核心指标：错误率、延迟、Agent 成功率）
```

### 7.3 升级后验证清单

| 序号 | 验证项 | 通过标准 |
|---|---|---|
| 1 | 登录冒烟 | Keycloak 登录成功 |
| 2 | 看板加载 | < 3 秒，数据正常 |
| 3 | 实时推送 | 注入测试告警，5 秒内收到 |
| 4 | 根因链路 | 触发一次测试事件，5 分钟内出 Top-3 |
| 5 | 审批链路 | 测试建议通过/驳回流程 |
| 6 | 审计写入 | 新操作正常入 audit_log |
| 7 | 监控恢复 | Prometheus 全部 Target up |
| 8 | 错误率 | 升级后 30 分钟 ERROR 数与基线持平 |

> 任一项不通过且 30 分钟内无法修复 → 立即执行回滚（引用《05-回滚方案》：`kubectl rollout undo deploy/<name>` + 数据库回滚脚本），并记录变更失败复盘。

### 7.4 数据库迁移特别约定

- 迁移脚本必须**可重入**（幂等），命名规范 `V<时间戳>__<描述>.sql`；
- 破坏性变更（删列/改类型）一律采用**双写过渡**：先加新、迁数据、再删旧（跨两次升级完成）；
- 迁移前备份，迁移失败直接走 §5.2 恢复流程。

## 8. 安全维护

### 8.1 账号定期审查

- **每月**（M2 巡检项）：导出用户清单（§7.1 用户管理 + Keycloak 管理台），与 HR 离职/转岗名单比对，离职账号 24 小时内停用；
- **每季度**：清理 90 天未登录的休眠账号（导出审计日志统计最后登录时间）；
- 管理员账号禁止共享，人手一号；管理员操作全部入审计日志。

### 8.2 证书更换

| 证书 | 有效期 | 更换方式 |
|---|---|---|
| 域名 TLS 证书（ia.芯联.local） | 1 年 | 客户 PKI 续签后更新 K8s Secret：`kubectl create tls secret ia-tls --cert=xxx.pem --key=xxx.key --dry-run=client -o yaml \| kubectl apply -f - -n ia-prod`，Ingress 自动热加载；剩余 < 30 天触发 D8 巡检提醒 |
| Keycloak 内部证书 | 1 年 | 随 realm 备份配置，管理台更换 |
| MinIO / Neo4j TLS | 1 年 | 修改对应配置并滚动重启 |

### 8.3 密钥轮换

| 密钥类型 | 存放位置 | 轮换周期 |
|---|---|---|
| 数据库密码 | K8s Secret `ia-db-cred` | 90 天 |
| 服务间 API Token（server↔agent） | K8s Secret `ia-svc-token` | 90 天 |
| MinIO AK/SK | K8s Secret `ia-minio-cred` | 90 天 |
| JWT 签名密钥（Keycloak realm keys） | Keycloak 管理 | 180 天 |

轮换操作规范：先在依赖方配置新值 → 滚动重启消费方 → 撤销旧密钥 → 更新密钥台账（IA-AC-005 §6）。**本手册与台账均不记录明文**。

### 8.4 漏洞扫描

- **每月**（M7）：内网漏扫平台全端口扫描 ia-prod 全部服务；
- **每周**（W7）：跟踪 Keycloak / PostgreSQL / Neo4j / Kafka / MinIO 官方安全通告；
- 高危 CVE 处置时限：可利用且暴露面在外的 ≤ 7 天完成修复或缓解；
- 镜像基线：交付镜像均已过 Trivy 扫描，新增镜像必须扫描通过（无 High/Critical）方可入库。

### 8.5 安全事件响应

发现疑似入侵/数据外泄：立即隔离（NetworkPolicy 拒绝出入站）→ 保全证据（日志快照、etcd 快照）→ 上报客户方安全负责人与项目经理 → 按客户方安全事件预案联合处置。**禁止未授权情况下自行删除"痕迹"**。
