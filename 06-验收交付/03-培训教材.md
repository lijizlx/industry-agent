## 2. 第 1 课：系统日常使用培训（2h，工艺/设备工程师、生产主管）

### 2.1 课程结构

| 节 | 内容 | 时长 | 方式 |
|---|---|---|---|
| 2.1 | 开场：系统解决什么问题（10 分钟） | 10min | 讲授 |
| 2.2 | 登录与首页看板（20 分钟） | 20min | 讲授+跟操 |
| 2.3 | 异常事件监控（20 分钟） | 20min | 讲授+跟操 |
| 2.4 | 根因分析（25 分钟） | 25min | 讲授+跟操 |
| 2.5 | 审批工作台（20 分钟） | 20min | 讲授+跟操 |
| 2.6 | 全流程实战演练：批次 B-2026-1024 良率下降事件（30 分钟） | 30min | 分组实操 |
| 2.7 | 课堂练习与答疑（15 分钟） | 15min | 实操 |

### 2.2 开场白（讲师讲稿要点）

> "各位工程师，先问大家一个问题：良率突然掉了 2 个点，从发现到定位原因，你们平均花多久？——公司基线数据是 8 小时。IndustryAgent 要做的，就是把这件事压缩到半小时以内。它不能替你做决定，但它能把你需要看的证据在 5 分钟内摆到你面前：Top-3 嫌疑、参数曲线、相似案例、因果分析。今天 2 个小时后，每个人都要能独立跑完全流程。"

**五句话讲清系统**：

1. 看板：良率、OEE、异常一目了然；
2. 告警：FDC 异常实时推送，不用刷屏等；
3. 根因：系统给 Top-3 嫌疑和证据链，你看证据拍板；
4. 审批：调参、停线建议必须人工审批，系统不越权；
5. 8D：审批完报告初稿自动生成，质量同事不再熬夜写报告。

### 2.3 登录与首页看板（跟操）

**讲师逐步演示，学员同步操作：**

1. 打开 Chrome，输入 `https://ia-staging.芯联.local`（培训环境）；
2. 用培训账号 trainee01（密码见桌面卡片）登录，首次登录绑定手机号；
3. 观察看板四个区域，讲师逐一讲解（对应《用户操作手册》§2）；
4. 练习时间范围切换：24h → 7d → 30d，注意卡片数字变化；
5. 练习钻取：点击 Top 异常设备第 1 名的条形，跳转到该设备告警列表，再点【重置】返回；
6. 讲师提问检查："今天有几条待处理告警？哪台设备异常最多？"

### 2.4 异常事件监控（跟操）

1. 进入【异常事件】列表，认识表格 8 个字段；
2. 组合筛选练习：设备=ETCH-03 + 级别=严重 + 近 7 天 → 【查询】；
3. 点击任一事件【详情】，依次讲解：基本信息、参数快照（黄线/红线含义）、处置时间线；
4. 讲解状态流转与"标记误报"的规范（误报标记会被统计进 KPI，不要随手点）；
5. 实时推送演示：讲师在后台注入一条测试告警，学员观察右上角通知条与列表插入效果；
6. 讲解连接状态图标（绿点正常/红点断开）与重新连接。

### 2.5 根因分析（跟操，本课重点）

1. 打开一个已完成的根因分析案例，认识 **Top-3 嫌疑卡片**：嫌疑名、置信度、类别、证据角标；
2. 讲师强调**置信度含义表**（≥85% 优先核对；60-85% 结合现场；<60% 务必人工排查），明确"置信度不是正确率，决策责任在你"；
3. 逐个标签页讲解证据链：
   - **图谱关系**：节点=事物（设备方/参数圆/工艺六边/缺陷菱形），连线粗细=历史共现频次；练习滚轮缩放、悬停、双击展开；
   - **参数曲线对比**：绿色基线带 + 蓝色实测 + 红色告警时刻线；练习切换参数、叠加同型设备曲线；
   - **相似案例**：看前人的根因、措施、效果，这是最实用的参考；
   - **因果结论**：结论卡 + 因果方向图 + 推断依据折叠框（可追溯）；
4. 练习【确认】【排除】操作：必须填 ≥10 字理由，理由进审计日志；
5. 讲解【都不对，反馈新根因】：反馈回流用于优化，鼓励多用；
6. 练习导出 PDF 分析报告。

### 2.6 审批工作台（跟操）

1. 进入【审批工作台】，认识"待我审批/我已审批/全部"三个标签页；
2. 讲解卡片要素：建议类型（调参蓝/停线红）、风险等级、影响范围、**30 分钟超时升级**规则；
3. 讲解审批规范：
   - 通过前必看：根因证据、参数对照表、影响范围；
   - 理由必填且写清楚（"同意，按曲线证据执行"而不是"ok"）；
   - 驳回要选原因，这是帮系统变准的反馈；
4. 全员跟操：通过一条练习建议 + 驳回一条练习建议（培训数据已预置）；
5. 查看"我已审批"里的完整审计档案。

### 2.7 全流程实战演练：批次 B-2026-1024 良率下降事件（30 分钟，分组实操）

#### 场景剧本

> **背景**：10 月 24 日 08:15，FAB-A2 产线。FDC 触发严重告警：ETCH-03（刻蚀机 3 号）腔压读数超出上限，同时批次 B-2026-1024 出厂测试良率 92.4%，较目标 95% 下降 2.6 个点。你当班，需要借助系统在 30 分钟内完成定位与决策。
>
> 培训环境已预置该事件全流程数据（数据集 `demo_scenario_B-2026-1024`，每场培训前用重置脚本恢复，见 §9.3）。

#### 演练步骤（学员按步执行，辅导老师巡场）

| 步骤 | 操作 | 预期结果 | 检查点 |
|---|---|---|---|
| 1 | 登录系统，切换看板到"近 24 小时" | 良率曲线出现红色异常点，OEE 下探 | 能口头说出良率掉了多少 |
| 2 | 点击红色异常点 → 查看批次详情 | 气泡显示 B-2026-1024、92.4% | 记录批次号 |
| 3 | 进入【异常事件】，筛选 ETCH-03 + 严重 | 看到 08:15"腔压超限"告警 | 确认状态为"处理中" |
| 4 | 打开事件详情 | 参数快照显示 08:12 起腔压爬升 | 指出拐点时间 |
| 5 | 查看自动生成的根因分析 Top-3 | 嫌疑1：腔压传感器漂移（87%）；嫌疑2：腔体污染（64%）；嫌疑3：Recipe 错配（31%） | 记录三个嫌疑与置信度 |
| 6 | 逐项查看嫌疑1证据链：图谱→曲线→案例→因果 | 曲线显示读数漂移但相邻腔体压力计正常；相似案例 3 起同类事件 | 判断证据是否支持嫌疑1 |
| 7 | 对嫌疑1点击【确认】，填写理由 | 理由示例："相邻腔体压力计读数正常而本腔读数漂移，符合传感器漂移特征，曲线证据充分" | 理由 ≥10 字且引用了证据 |
| 8 | 等待建议 Agent 生成建议（约 1 分钟） | 审批工作台出现"调参建议"：更换/校准腔压传感器并将控制回路切至备用压力计 | 卡片要素完整 |
| 9 | 打开建议详情，核对证据链接与影响范围 | 影响范围：ETCH-03，预计 2 个批次 | 无误 |
| 10 | 点击【通过】，填写审批理由 | 状态变为"已批准" | 理由清晰 |
| 11 | 进入【8D 报告】查看自动生成的初稿 | D1-D8 已自动填充，D4 引用 Top-3 与证据链 | 认识到"初稿"性质 |
| 12 | 导出该事件分析报告 PDF | 浏览器下载 RCA_*.pdf | 导出成功 |

### 2.8 课堂练习（3 道）

**练习 1（看板操作）**：切换看板到"近 30 天"，找出异常次数排名第 2 的设备，并在异常列表中筛出该设备近 7 天的"警告"级告警。说出该设备近 7 天警告级告警条数。
**参考答案**：看板底部条形图从上往下第二条即排名第 2 的设备（培训数据中为 PVD-07）；进入异常事件 → 筛选设备=PVD-07、级别=警告、时间=近 7 天 → 【查询】，计数 4 条。

**练习 2（根因判读）**：打开预置事件 EVT-20261018-0006（Film-02 膜厚异常），查看 Top-3 中置信度最低的嫌疑，说出"为什么不能直接确认它"，并演示把该嫌疑【排除】的完整操作。
**参考答案**：最低置信度嫌疑为"环境温湿度波动"（置信度 42%）；不能直接确认的原因：置信度 <60% 表示证据不足，因果结论中效应量不显著；排除操作：点击卡片【排除】→ 选择/填写依据（如"洁净室温湿度记录在案且稳定"）→ 提交，卡片置灰。

**练习 3（审批规范）**：你的待办里有一条停线建议（PVD-07 真空泵异响），风险等级"高"、影响范围"停线 4 小时"。请判断：① 谁有权审批？② 通过前至少核对哪三项信息？③ 给出一条合格的审批理由。
**参考答案**：① 生产主管（停线建议审批人）；② 根因证据是否充分、影响范围与产能损失是否可接受、有无更温和的替代方案（如先降速不停线）；③ 示例理由："同意停线。真空泵异响 + 膜厚异常证据链完整，继续运行有腔体报废风险，停线 4 小时损失小于整批报废损失，要求 2 小时内完成换泵。"

## 3. 第 2 课：管理层价值汇报（0.5h，生产副总、各部门主管）

### 3.1 汇报提纲（15 分钟演示 + 15 分钟问答）

1. **一句话定位**：IndustryAgent = 半导体良率问题的"自动参谋"，把根因定位从 8 小时压到 30 分钟；
2. **核心指标（试运行 30 天数据）**：

| 指标 | 上线前基线 | 试运行实测 | 目标 | 达成 |
|---|---|---|---|---|
| 根因 Top-3 准确率 | — | 82% | >80% | ✓ |
| MTTR（平均恢复时间） | 8.0 小时 | 3.6 小时 | 降低>50% | ✓（降低 55%） |
| 误报率 | 人工巡检无此口径 | 8% | <10% | ✓ |
| 人工接管率 | — | 24% | <30% | ✓ |
| 端到端延迟 | — | 4.2 分钟 | <5 分钟 | ✓ |

3. **价值量化话术**（供主管们向下传达）：

> - "以前良率一掉，工艺、设备、质量三个部门开会翻历史数据，平均 8 小时找到原因；现在系统 5 分钟把证据摆齐，**MTTR 从 8 小时降到 3.6 小时，降幅 55%**。"
> - "按 FAB-A2 月投 4 万片、单次异常平均损失 120 万估算，**每月少损失的非计划停机时间折算约 200 万元产能**，系统投入 10 个月收回。"
> - "误报率 8%，意味着 10 条告警里 9 条是实的，大家不用再被狼来了消耗注意力。"
> - "人工接管率 24%，四分之三的建议一线直接采纳——说明它真的在干活，而不是在添乱。"
> - "8D 报告自动出初稿，质量部门写报告时间从 4 小时缩短到 40 分钟的审核补充。"

4. **管控要点（回应管理层最关心的问题）**：

| 关注点 | 回应 |
|---|---|
| "会不会哪天系统直接把产线停了？" | 不会。停线/调参建议 100% 人工审批（HITL），系统无执行权限，审批人/时间/理由全程审计 |
| "数据安全吗？" | 全部部署在厂内网，数据不出域；账号用公司统一认证；操作日志保留 1 年可审计 |
| "一线不愿意用怎么办？" | 前提是"好用+有用"：告警实时推送减负、根因证据链免翻数据、反馈机制让系统随反馈变准；建议将"系统反馈率"纳入班组合理化建议统计 |

5. **需要管理层支持的三件事**：指定各级审批人并保持在线响应；鼓励工程师反馈根因标注；每季度参加一次指标复盘会。

### 3.2 演示脚本（5 分钟关键路径）

登录 → 看板展示 30 天良率/OEE → 打开一条真实告警 → 展示 Top-3 + 证据链 → 展示审批记录审计 → 展示 8D 报告初稿 → 收尾在指标看板页。

## 4. 第 3 课：8D 报告专题培训（1h，质量工程师）

### 4.1 8D 方法论简介（15 分钟）

8D（Eight Disciplines，八步法）是汽车/半导体行业通用的结构化问题解决方法：

| 步骤 | 名称 | 核心问题 |
|---|---|---|
| D1 | 成立团队 | 谁来负责解决？跨部门组队 |
| D2 | 问题描述 | 5W2H：什么时间、哪里、什么产品、出了什么问题、程度如何 |
| D3 | 临时围堵措施 | 根因找到前，如何把损失"围住"？（隔离批次、切换设备、降速运行） |
| D4 | 根本原因分析 | 真正的原因是什么？（区分"发生原因"与"流出原因"） |
| D5 | 纠正措施选定 | 用什么方案根治？评估风险与成本 |
| D6 | 措施实施与验证 | 效果数据证明措施有效了吗？（前后对比） |
| D7 | 预防再发生 | 制度、规范、FDC 规则如何更新防止复发？ |
| D8 | 团队祝贺与关闭 | 确认关闭、认可团队、归档经验 |

### 4.2 系统辅助生成流程（15 分钟）

**系统生成链路**：事件处置 + 根因确认 + 建议审批完成后 → 报告 Agent 自动汇总 → 8D 初稿生成 → 质量工程师审核补充 → 发布导出。

**各章节自动填充来源**：

| 章节 | 自动来源 | 审核重点 |
|---|---|---|
| D1 | 建议的相关角色名单 | 核对实际指派人员，补齐部门 |
| D2 | 事件摘要 + 批次良率数据 | 补充客户侧影响、5W2H 完整性 |
| D3 | 审批通过的临时措施 | 与实际执行情况一致性 |
| D4 | Top-3、证据链、确认根因 | **重点**：确认根因表述是否准确，证据是否闭环 |
| D5 | 已批准建议原文 | 措施是否覆盖"发生+流出"双重原因 |
| D6 | 参数变更前后曲线、恢复数据 | 验证窗口是否足够、数据是否支持"有效"结论 |
| D7 | 图谱提炼的关联风险点 | 结合规范修订计划，写具体修订条目 |
| D8 | — | 团队名单、关闭签署 |

### 4.3 人工审核要点（10 分钟）

1. **D4 是灵魂**：系统给出的根因必须与证据链一致；表述用"现象+机制"格式（如"腔压传感器漂移→控制回路误动作→实际腔压偏离 Recipe 窗口→刻蚀速率异常"）；
2. **区分发生原因与流出原因**：系统侧重发生原因，流出原因（为何 FDC/检测没拦住）需人工补充；
3. **D6 必须有验证数据**：恢复后至少 2 个批次的良率/参数对比；
4. **D7 要落地到条款**：写"修订《刻蚀工序控制规范》§5.3，增加腔压传感器月度校准"而不是"加强管理"；
5. 灰色只读区为系统证据，若认为有误请报障核查数据源，**不要**绕开；
6. 导出 PDF 前用预览核对附件勾选（曲线图、图谱截图、案例附录）。

### 4.4 实操练习（15 分钟）

使用 B-2026-1024 培训场景：打开自动生成的初稿 → 补充 D1 团队与 D2 客户影响 → 审核 D4 根因表述 → 补写 D6 验证结论 → 保存 → 提交审核 → 导出 PDF。**通过标准：导出的 PDF 8 个章节无缺项、D4/D6 审核痕迹完整。**

## 5. 第 4 课：系统运维培训（2h，客户方 IT/运维）

### 5.1 课程结构

| 节 | 内容 | 时长 |
|---|---|---|
| 1 | 架构与组件清单（对照《系统维护手册》§1） | 20min |
| 2 | 实操 A：日常巡检 | 25min |
| 3 | 实操 B：服务启停 | 20min |
| 4 | 实操 C：备份与恢复演练 | 30min |
| 5 | 实操 D：故障处理抽考 | 25min |

### 5.2 实操 A：日常巡检（25 分钟）

学员按《系统维护手册》§2.1 每日巡检表逐项执行并填写巡检记录：

1. `kubectl get pods -n ia-staging` —— 识别全部 READY；
2. `kubectl top nodes` —— 记录 CPU/Mem 数值并判断是否 <80%；
3. `df -h /data` —— 判断磁盘水位；
4. `kubectl logs deploy/server --since=12h | grep -iE 'error|fatal' | tail -50` —— 判断错误是否异常；
5. Grafana IA-Overview 看板巡检 + Kafka Lag 面板；
6. 检查备份日志尾部 SUCCESS。

**通过标准**：15 分钟内完成全部 D1~D7 项并正确判断"正常/异常"。

### 5.3 实操 B：服务启停（20 分钟）

1. 滚动重启 server：`kubectl rollout restart deploy/server -n ia-staging`，观察 `rollout status`；
2. 缩容再扩容 agent：`kubectl scale deploy/agent --replicas=0` → 确认 0 → `--replicas=2`；
3. docker compose 环境：`docker compose up -d` / `restart server` / `logs -f server`；
4. 讲解启动顺序原则与禁止事项（生产工作时间禁止整体 stop）。

**通过标准**：独立完成"重启 server 并验证恢复登录冒烟"。

### 5.4 实操 C：备份与恢复演练（30 分钟）

1. 手动执行 PG 逻辑备份（`pg_dump` + `kubectl cp`），校验文件；
2. 在演练命名空间 ia-drill 恢复该备份；
3. 连接恢复库抽查关键表行数（batches/events/audit_log）；
4. 执行 Neo4j dump + load，`MATCH (n) RETURN count(n)` 校验；
5. 填写一次《恢复演练记录表》。

**通过标准**：RTO 实测 < 1 小时（演练环境），数据校验全部通过。

### 5.5 实操 D：故障处理抽考（25 分钟）

讲师在 Staging 注入 3 个故障，学员抽 2 个现场处置（开卷可查《系统维护手册》§6）：

| 注入故障 | 考察点 | 参考处理 |
|---|---|---|
| kill agent Pod（制造 CrashLoop） | 事件定位、Pod 修复 | describe/logs → 删除 Pod 自动重建 → 验证链路 |
| server 配置错误导致起不来 | 回滚意识 | rollout undo 回滚上一版本 → 上报变更 |
| 人为制造 Kafka 积压（暂停消费者） | 监控定位、扩容处置 | Lag 面板定位 → 恢复消费者 → 必要时扩副本 |

**通过标准**：30 分钟内处置完成且处置动作正确；错误动作（如直接 rm 数据卷）视为不通过，补训后重考。

### 8.3 演示数据集重置脚本说明

**用途**：每场培训开课前 10 分钟执行，将培训环境数据恢复到剧本初始状态（学员上一场的操作全部清除）。

**脚本执行内容**（顺序）：

1. 停止 server/agent（隔离写入）；
2. 恢复 PG 培训库快照（`pg_restore` 至基准 dump `training_base.dump`）；
3. 清空并重放 Kafka 培训 topic 初始事件流（`kafkacat` 回放 `demo_events.jsonl`）；
4. Neo4j 载入基准图谱 dump；
5. MinIO 同步基准对象清单（缺陷图、文档附件）；
6. 重置 Keycloak 培训账号密码为初始密码；
7. 启动 server/agent，注入"当前时间"偏移使场景数据时间戳显示为"今天"；
8. 冒烟验证：脚本自动调用 `/api/v1/health` 与一条测试告警推送，输出 `RESET OK`。

**执行示例**：

```bash
cd /opt/industryagent/infra/training
./reset_demo.sh            # 输出 RESET OK 即就绪，全程约 3 分钟
```

> 注意：重置只作用于培训命名空间/培训 compose 项目；脚本内置保护（检查 `.env` 中 `IA_ENV=training` 才允许执行，防止误在生产运行）。误执行生产环境的兜底见《系统维护手册》§5 恢复流程。
