## 1. 目的与范围

本矩阵建立"用户需求（UR）→ 软件需求（FR）→ 用例（UC）→ 设计文档章节（HLD）→ 测试用例（TC）→ 迭代"的双向追踪关系，用于：

1. 需求覆盖率验证（M1 基线冻结的必要条件）；
2. 变更影响分析（第 4 章）；
3. 验收完备性核对（M6）。

追踪对象：IA-RM-001 的 UR-001~UR-030；IA-RM-002 的 FR-001~FR-084；IA-RM-003 的 UC-001~UC-010；NFR（IA-RM-005）另以第 3 章专项矩阵追踪。

**设计文档章节引用约定**：引用《系统概要设计说明书》（文档编号 IA-DD-001，按 IA-PM-002 §2 WBS 1.3 产出）章节号。

**测试用例编号约定**：TC-模块前缀-序号，模块前缀 A/H 组（AUTH）、B（DATA）、C（FDC）、D（RCA）、E（APRV）、F（RPT）、G（DASH）。

## 3. 覆盖率统计

### 3.1 覆盖率定义

- 正向覆盖：UR 有对应 FR / UC / TC / 迭代，记为已覆盖；
- 反向覆盖：FR 能回溯到至少一条 UR，记为已覆盖（支撑性 FR 如 FR-019/020/075 等标注为"支撑需求"，归属其服务的主 UR）。

### 3.2 统计结果（M1 基线）

| 追踪方向 | 覆盖率 | 说明 |
|---|---|---|
| UR → FR | 30/30 = 100% | 全部 UR 至少映射 1 条 FR |
| UR → UC | 30/30 = 100% | UR-020/023 等 6 项以扩展分支或兼参与者覆盖，均显式标注 |
| UR → TC | 30/30 = 100% | 共规划 78 组测试用例（TC-AUTH 25、DATA 13、FDC 16、RCA 17、APRV 18、RPT 9、DASH 14，去重合并后 112 条） |
| UR → 迭代 | 30/30 = 100% | 见矩阵末列，与《迭代计划》（IA-PM-004）一致 |
| FR → UR（反向） | 84/84 = 100% | 其中 9 条 FR 标注为"支撑需求"（FR-019/020/033/045/075/078/081~083），归属最近主 UR |
| NFR 覆盖 | 47/47 = 100% | NFR-001~047 全部绑定验证方法与执行迭代（见 IA-RM-005 各条目"验证迭代"列） |
| UC → TC | 10/10 = 100% | 每个 UC 至少 1 组 TC，含主场景与关键扩展流 |

### 3.3 无孤儿需求核查

- 孤儿 UR：0 条；
- 无法回溯 UR 的 FR：0 条（支撑性 FR 已归并）；
- 无测试用例的 FR：0 条；
- 无迭代安排的需求：0 条。

## 4. 变更影响分析流程

### 4.1 变更流程

```
变更申请（任意干系人提交）
  → 登记变更请求 CR（编号 CR-<日期>-<序号>）
  → RTM 定位影响面（本矩阵正向+反向检索）
  → 影响评估（需求/设计/代码/测试/进度/风险六维）
  → CCB 决议（IA-PM-001 §10：发起人+PM+架构代表）
  → 决议执行（更新基线、矩阵同步、通知干系人）
  → 关闭与追溯（变更记录挂接本矩阵修订）
```

### 4.2 影响评估输出模板

| 评估维度 | 内容 |
|---|---|
| 需求影响 | 受影响 UR/FR/NFR 清单（由矩阵检索得出） |
| 设计影响 | 受影响 HLD 章节与 ADR |
| 开发影响 | 模块/工作量估算（人日） |
| 测试影响 | 需新增/修改的 TC 清单；回归范围 |
| 进度影响 | 里程碑/迭代变化 |
| 风险影响 | 新增/升级的风险登记项（RSK-xxx） |

### 4.3 变更控制规则

1. M1 基线后，每迭代仅受理一次需求变更批量评审（迭代计划会上）；
2. 变更工作量累计不超过基线总量 10%（IA-PM-002 §10 假设），超出须发起人专项批准；
3. 任何不得削弱三条硬约束：数据不出域、关键建议人工审批、RBAC+全链路审计——此类变更一律否决；
4. 矩阵与代码同源管理：FR 变更未更新 RTM 的 PR 不予合入（CI 检查文档变更关联）。
