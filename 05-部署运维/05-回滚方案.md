## 1. 概述

本文档定义 IndustryAgent 的回滚原则、版本与制品管理约束、L1~L4 分级回滚策略、各场景标准操作程序（SOP）、回滚演练机制、不可回滚场景的前滚策略以及备份恢复方案。适用 Compose（Staging）与 k3s（生产）两种形态。**回滚不是失败的补救，而是部署设计的一部分：任何一次发布前，回滚预案必须随发布单一并就绪。**

---

## 2. 回滚原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | 可回滚性是部署前提 | 发布评审必含回滚预案；无法回滚的变更按 §8 前滚策略单独评审 |
| 2 | 决策时间线 | **P1 事故 15 分钟内做出回滚/前滚决策**（由值班负责人决策，事后追认）；P2 事故 30 分钟内；犹豫时倾向回滚——回滚成本 5 分钟，止损收益远大于面子 |
| 3 | 回滚优先于定位 | 生产事故处理顺序：先恢复服务（能回滚先回滚），后根因分析（IA-OPS-005） |
| 4 | 镜像不可变 | 回滚=切回旧镜像 tag，绝不"改一下再发"（那是 hotfix，走 §7.4） |
| 5 | 数据库变更先于应用回滚评估 | 应用回滚前必须先确认 DB 是否需要回滚（详见 §5.2 危险操作警示） |
| 6 | 回滚后必复盘 | 每次真实回滚 48 小时内在部署群发布简报（原因/操作/结果），并按 IA-OPS-005 复盘 |
| 7 | 演练常态化 | 每迭代至少一次回滚演练（§7 演练表），未演练过的回滚预案视为无效预案 |

## 3. 版本与制品管理

### 3.1 语义版本与制品约束

| 项 | 规则 |
|----|------|
| 版本号 | semver：v主.次.修；不兼容 API/迁移变更 → 主版本；新功能 → 次版本；修复 → 修订号 |
| 镜像不可变 | 同一 tag 一经推送永不覆盖（ghcr/Harbor 禁止 overwrite）；生产只能部署 git-sha 或 semver tag，latest 禁止上生产（IA-OPS-002 §4.2） |
| 制品保留 | semver 永久保留；git-sha ≥ 90 天，保证任意历史版本可回滚 |
| 部署记录 | 每次发布记录到 `deploy/releases.tsv`：`服务\t镜像tag\tcommit\t时间\t工单号\t操作人`，回滚时从此台账取上一稳定版本 |

### 3.2 数据库迁移向前兼容原则（扩"展-收缩"两阶段）

为让 L1 应用回滚始终可行，数据库 schema 变更必须**向前兼容两个应用版本**：

| 阶段 | 允许的操作 | 禁止的操作 |
|------|------------|------------|
| 阶段一：扩展（随 v(N) 发布） | 加可空列、加带默认值列、加表/索引、**双写**（新旧列同时写） | 删列、改列类型、加 NOT NULL 无默认约束、改名 |
| 阶段二：收缩（v(N+1) 确认稳定后） | 停旧写、数据回填校验、**删列**（此时 v(N) 已确认不再回滚） | 跳过回填直接删 |

示例：v1.2.0 为审计表加 `trace_id` 列（可空）+ 双写 `trace_id` 与旧 `request_id`；v1.3.0 验证 7 天后删 `request_id`。**判据：只有当 v(N) 在生产稳定运行 ≥7 天且无回滚可能时，才允许执行收缩迁移。**

### 3.3 发布前回滚预案检查单（随发布单输出）

```markdown
- [ ] 上一稳定版本镜像 tag：server=___ / agent=___ / web=___（取自 releases.tsv）
- [ ] 本次是否含 DB 迁移：是/否；迁移文件列表：___；是否向前兼容：是/否
- [ ] 是否含 Keycloak/OPA 配置变更：是/否；回滚方式：§5.3
- [ ] 回滚验证命令：curl /healthz + Grafana 错误率面板链接
- [ ] 回滚决策人（P1 15 分钟内）：___
```

## 4. 分级回滚策略表

| 级别 | 场景 | 手段 | 目标耗时 | 风险 |
|------|------|------|----------|------|
| L1 应用回滚 | 新版本代码缺陷、启动失败、错误率/延迟劣化 | 切回上一稳定镜像 tag + 重启（compose 重新 up / kubectl rollout undo） | **≤ 5 分钟** | 低（前提：迁移向前兼容） |
| L2 配置回滚 | 环境变量错误、配置文件/ConfigMap 错误、告警/路由配置失误 | 回退 .env / ConfigMap / OPA 策略文件并重启相关服务 | ≤ 10 分钟 | 低 |
| L3 数据库回滚 | 迁移执行失败、迁移导致数据异常 | 迁移 down 脚本 + 数据修复（**必须先备份后操作**，见 §5.2 警示） | ≤ 60 分钟（含备份校验） | **高：可能丢数据** |
| L4 全量回滚 | 平台级故障：升级核心组件（PG/Kafka/Keycloak 版本）后整体不可用、多服务交叉故障 | 上一稳定版本整体切换：全部镜像+配置+（如需）恢复备份至新卷后切换 | ≤ 2 小时 | 高，需发布负责人+运维负责人双人执行 |

## 5. 各场景回滚 SOP

### 5.1 场景一：正常发布回滚（应用层）

**判断标准**：发布后 30 分钟观察窗内，出现任一：健康检查失败、API 5xx > 0.5%、P95 延迟劣化 > 50%、Agent 任务失败率 > 10%、核心功能人工验证不通过。

**操作步骤（Compose / Staging）**：

```bash
cd /data/app/industryagent
# 1) 确认当前版本与上一稳定版本
grep -E 'server|agent|web' deploy/releases.tsv | tail -6
# 2) 切回上一稳定 tag（示例回滚到 v1.1.0）
sed -i 's/^IMAGE_TAG=.*/IMAGE_TAG=v1.1.0/' deploy/.env
# 3) 拉取并重建三个应用服务（数据层不动）
docker compose -f deploy/docker-compose.yml pull server web agent
docker compose -f deploy/docker-compose.yml up -d server web agent
# 4) 验证
docker compose -f deploy/docker-compose.yml ps
curl -sf http://127.0.0.1:7001/healthz && curl -sf http://127.0.0.1:8000/healthz
```

**操作步骤（k3s / 生产）**：

```bash
# 1) 查看发布历史，确认回滚目标 revision
kubectl -n industryagent-app rollout history deployment/industryagent-server
# 2) 一键回滚上一版本（推荐；或 set image 指定具体 tag）
kubectl -n industryagent-app rollout undo deployment/industryagent-server
kubectl -n industryagent-app rollout undo deployment/industryagent-agent
kubectl -n industryagent-app rollout undo deployment/industryagent-web
# 3) 等待滚动完成
kubectl -n industryagent-app rollout status deployment/industryagent-server --timeout=300s
kubectl -n industryagent-app rollout status deployment/industryagent-agent --timeout=300s
kubectl -n industryagent-app rollout status deployment/industryagent-web --timeout=300s
```

**验证清单**：

- [ ] `kubectl get pods` / `docker compose ps` 全部 healthy；
- [ ] `curl /healthz`（server/agent）返回 200；
- [ ] Grafana：API 错误率回落 < 0.1%，P95 恢复基线；
- [ ] 发起 1 次端到端 RCA 任务，P95 < 300s；
- [ ] Prometheus 无新增 P1 告警，持续观察 15 分钟。

**通知要求**：回滚执行后 5 分钟内在值班群通报"版本 vX→vY 已回滚，原因摘要"；回滚后 30 分钟内填写 releases.tsv 回滚记录行；24 小时内出简报并关联 IA-OPS-005 复盘单。

### 5.2 场景二：数据库迁移失败回滚

**判断标准**：`migrate:up` 中途报错退出；迁移后应用无法启动并报 schema 错误；迁移引发数据查询异常。

**操作步骤**：

```bash
cd /data/app/industryagent
# 0) 停止应用写入，防止半迁移状态被继续写脏
docker compose -f deploy/docker-compose.yml stop industryagent-server industryagent-agent

# 1) 【强制】先做全量备份（危险操作前的唯一保险）
source deploy/.env
TS=$(date +%Y%m%d%H%M%S)
docker compose -f deploy/docker-compose.yml exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc \
  > /data/backup/pg/pre_rollback_${TS}.dump
ls -lh /data/backup/pg/pre_rollback_${TS}.dump   # 确认非空且大小合理

# 2) 执行 down 迁移（项目约定每个迁移必须带可逆 down 脚本）
cd services/server
npm run migrate:down -- --to 0041   # 回退 0042_add_audit_trace_idx 之类
# 校验 schema 状态
psql "$DATABASE_URL" -c "\d audit_log" | head -30

# 3) 如 down 不可用或失败：不盲目重试，改为从备份恢复（见 §9.2 流程）
#    并同时评估前滚（§8）修复迁移脚本重新执行

# 4) 恢复应用
cd /data/app/industryagent
docker compose -f deploy/docker-compose.yml up -d industryagent-server industryagent-agent
curl -sf http://127.0.0.1:7001/healthz
```

> **危险操作警示：down 迁移可能丢数据，必须先备份。**
> 1. down 脚本会删除 down 迁移之后产生的数据（如新列写入的值、新表数据）；
> 2. 任何 down 迁移前必须完成 §1 的 pg_dump 全量备份且**校验文件完整**（`pg_restore --list` 可列目录）；
> 3. down 迁移必须双人操作：一人执行、一人核对迁移文件内容与影响范围；
> 4. TimescaleDB 超表上禁止直接 DROP 列：需先 `drop_continuous_aggregate`（如有连续聚合）再处理超表列，普通 down 脚本对超表结构变更必须使用 `timescaledb` 兼容写法并预先测试；
> 5. 若备份恢复不可避免，RPO 之内的增量数据会丢失，需业务方书面确认。

**验证清单**：应用两服务 healthy；核心表抽样查询正常（RCA 任务、审计各 1 条）；TimescaleDB `timescaledb_information.hypertables` 数量与基线一致；增量数据丢失评估已通报。

**通知要求**：L3 回滚必须同步值班负责人与技术负责人；数据影响评估 1 小时内出结论。

### 5.3 场景三：Keycloak / OPA 配置回滚

**判断标准**：认证/授权异常——全员 401/403、登录失败、权限误开放/误收紧。

**Keycloak 操作步骤**：

```bash
# 1) Keycloak realm 配置以 JSON 导入文件为源（deploy/keycloak/industryagent-realm.json）
#    回滚 = 恢复上一版本 JSON 并重新导入
cd /data/app/industryagent
git log --oneline -5 -- deploy/keycloak/
git checkout v1.1.0 -- deploy/keycloak/industryagent-realm.json
# 2) 导入（--override true 覆盖现配置；生产建议在维护窗口执行）
docker compose -f deploy/docker-compose.yml exec -T keycloak \
  /opt/keycloak/bin/kc.sh import --realm industryagent \
  --file /opt/keycloak/data/import/industryagent-realm.json --override true
# 3) 验证登录与角色
curl -sk -X POST https://staging.industryagent.internal/auth/realms/industryagent/protocol/openid-connect/token \
  -d "grant_type=password&client_id=industryagent-web&username=li.gongyi&password=<口令>" | head -c 120
```

> Keycloak 用户数据存在 PG（`keycloak` schema），realm 导入覆盖的是配置而非用户表；若误删用户/角色，走 §5.2 数据恢复路径。

**OPA 操作步骤**：

```bash
# 1) 策略以 git 为源，回退到上一版本策略文件
git checkout v1.1.0 -- deploy/opa/policies/
# 2) 重新推送（compose 卷挂载方式重启即生效；REST 推送方式重新 PUT）
docker compose -f deploy/docker-compose.yml restart opa
# 3) 验证三个角色的授权决策
for ROLE in process-engineer quality-engineer admin; do
  curl -s -X POST http://127.0.0.1:8181/v1/data/industryagent/rca/allow \
    -H "Content-Type: application/json" \
    -d "{\"input\":{\"user\":{\"roles\":[\"$ROLE\"]},\"action\":\"view_rca_report\",\"resource\":\"rca:lot:TEST\"}}"
  echo " <= $ROLE"
done
```

**验证清单**：三类角色决策结果与权限矩阵一致；一次真实登录+一次 RCA 查看+一次审批操作全通过；审计表正常记录。

### 5.4 场景四：紧急 Hotfix 流程

> Hotfix = 回滚不可解（缺陷也在上一版本存在）或需立即修复的线上问题。流程与"直接改生产"的区别：**必须走完整构建门禁，只压缩评审窗口。**

```text
1. 拉 hotfix 分支     git checkout -b hotfix/INC-xxxx v1.2.0
2. 修复 + 最小化验证  单测/针对性集成测试（PR 流水线完整跑，不可跳门禁）
3. 构建镜像           打 tag v1.2.1，推送 ghcr（Trivy 阻断策略不变）
4. 双人评审           1 名架构/模块 owner + 1 名值班负责人，窗口 30 分钟
5. Staging 冒烟       10 分钟核心链路（登录/RCA 任务/审计）
6. 生产部署           kubectl set image → rollout status（同 IA-OPS-002 §3.3）
7. 观察与回滚判定     30 分钟观察窗，异常执行 §5.1 回滚
8. 合回主干           hotfix 分支 PR 合并 main，releases.tsv 登记 v1.2.1
```

### 5.5 通知要求（全场景通用）

| 时机 | 动作 | 渠道 |
|------|------|------|
| 决策时 | "判定回滚 vX→vY，原因：___" | 值班群（P1 电话同步值班负责人） |
| 完成时 | "回滚完成，验证通过，观察 30 分钟" | 值班群 + 相关业务群 |
| 24h 内 | 回滚简报（原因/操作/影响/后续） | 部署群，关联 IA-OPS-005 |

## 6. 不可回滚场景处理（前滚策略 Forward Fix）

**识别**：数据结构不兼容（如收缩迁移已执行、旧版本不认新 schema）、备份恢复窗口外的数据损坏、镜像不可变约束被破坏（tag 被覆盖）等——回滚旧应用比当前故障更危险。

**前滚流程**：

```text
1. 决策：P1 事故由值班负责人拍板"前滚"，15 分钟决策线同样适用
2. 冻结写入：停应用写入、必要时 Kafka 消费暂停（数据保留在 topic，修复后回放）
3. 修复优先级排序：恢复 schema 一致性 > 恢复服务 > 数据修复
4. 走 §5.4 hotfix 通道构建修复版本
5. 验证后发布，Kafka 数据回放（消费者 offset 按时间戳 seek 到冻结点）
6. 数据修复脚本双人评审执行，修复结果对账（条数/金额/时间窗）
7. 事后必须复盘，并评审"为何走到不可回滚"（通常指向 §3.2 两阶段流程未被执行）
```

## 7. 回滚演练（每迭代一次）

| 迭代 | 演练场景 | 结果 | 实测耗时 | 问题与改进 |
|------|----------|------|----------|------------|
| I2 | L1 应用回滚（compose 切回上一 tag） | 通过 | 4 分 12 秒 | 无 |
| I3 | L1 应用回滚（k3s rollout undo） | 通过 | 3 分 05 秒 | kubectl timeout 未预设，已补 300s |
| I4 | L2 配置回滚（OPA 策略回退） | 通过 | 6 分 40 秒 | 策略验证脚本需固化为一键脚本 |
| I5 | L3 数据库迁移回滚（staging，down+备份） | 通过 | 38 分 | pg_dump 在 2G 库上耗时 11 分钟，需预留窗口 |
| 下一迭代 | L4 全量回滚（备份恢复+整体切版本） | 计划中 | — | 计划于升级演练环境执行 |

演练要求：在 Staging 执行并录屏；耗时超目标值必须写改进措施；I2~I5 迭代每迭代至少覆盖一个未演练过的级别。

## 8. 备份恢复

### 8.1 备份策略总表（RPO < 15 分钟 / RTO < 1 小时）

| 对象 | 方式 | 频率 | 保留 | RPO |
|------|------|------|------|-----|
| PostgreSQL（含 TimescaleDB） | pg_dump 全量 + WAL 连续归档 | 全量每日 02:00；WAL 持续 | 全量 30 天（周日全量保留 1 年） | < 15 分钟（WAL） |
| Neo4j | neo4j-admin database dump | 每周日 03:00 | 4 份 | ≤ 7 天（图谱可由种子重建） |
| MinIO | mc mirror 增量（audit 桶版本化） | 每日 03:30 | 增量 90 天 | ≤ 24h（审计桶靠版本化即时） |
| Keycloak | realm 导出 JSON + PG 备份覆盖 | 随发布变更导出 | 随 git 永久 | ≤ 24h |
| 配置与策略 | git 仓库（含 compose/opa/keycloak JSON） | 实时 | 永久 | ≈ 0 |
| 审计日志归档 | PG→MinIO audit-archive | 每日 | ≥ 400 天 | 合规要求 |

### 8.2 PostgreSQL 备份命令（cron 02:00 执行）

```bash
#!/usr/bin/env bash
# /data/scripts/pg_backup.sh  —— 每日全量 + WAL 归档
set -euo pipefail
source /data/app/industryagent/deploy/.env
TS=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR=/data/backup/pg
mkdir -p "$BACKUP_DIR"

# 1) 全量逻辑备份（-Fc 自定义格式，支持并行恢复与选择性恢复）
docker exec ia-postgres pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  -Fc --file "/tmp/pg_${TS}.dump"
docker cp "ia-postgres:/tmp/pg_${TS}.dump" "$BACKUP_DIR/pg_${TS}.dump"
docker exec ia-postgres rm "/tmp/pg_${TS}.dump"

# 2) 完整性校验
pg_restore --list "$BACKUP_DIR/pg_${TS}.dump" > /dev/null || { echo "backup verify failed"; exit 1; }

# 3) 清理 30 天前的全量（周日全量除外，保留一年）
find "$BACKUP_DIR" -name 'pg_*.dump' -mtime +30 -not -name 'pg_*_Sun_*' -delete
```

> **TimescaleDB 注意点**：① pg_dump 需带 `--no-toast-compression` 选项兼容部分 hypertable 大对象；② 恢复前目标库必须先安装 timescaledb 扩展（`CREATE EXTENSION timescaledb`），且版本一致或高版本兼容；③ 连续聚合（continuous aggregates）在恢复后需 `refresh` 重建；④ 生产建议同时启用 `pgbackrest` 或 WAL 归档（`archive_command` 拷贝至 MinIO）达成 RPO<15min，pg_dump 全量仅作兜底。

### 8.6 恢复流程（RTO < 1 小时）

```bash
# 1) PostgreSQL 恢复（示例恢复到故障前 WAL 位置）
docker exec ia-postgres psql -U industryagent -d postgres -c "DROP DATABASE industryagent;"
docker exec ia-postgres psql -U industryagent -d postgres -c "CREATE DATABASE industryagent;"
docker exec -i ia-postgres pg_restore -U industryagent -d industryagent \
  /tmp/pg_20261015_020000.dump            # 先 restore 全量
# 2) 回放 WAL 至目标时间点（restore_command 指向 MinIO/WAL 目录）
# 3) Neo4j 恢复
docker compose -f deploy/docker-compose.yml stop neo4j
docker run --rm -v ia-neo4j_data:/data -v /data/backup/neo4j:/backup \
  neo4j:5.20-community neo4j-admin database load neo4j --from-path=/backup
docker compose -f deploy/docker-compose.yml up -d neo4j
# 4) 验证四件套
psql "$DATABASE_URL" -c "SELECT count(*) FROM audit_log;"     # 审计条数对账
docker exec ia-neo4j cypher-shell -a bolt://localhost:7687 "MATCH (n) RETURN count(n);"

```
