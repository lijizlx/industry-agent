## 1. 概述

### 1.1 目的

本文档提供 IndustryAgent 生产与 Staging 事故复盘的**可直接套用模板**，统一事故记录格式、根因分析方法（5Why）与改进措施管理要求，确保每起事故"发现→响应→定位→处置→恢复→复盘"全过程可追溯，并转化为系统性改进，防止同类事故复发。

### 1.2 使用范围

- P1/P2 级事故**必须**出具正式复盘报告；
- P3 级事故在迭代回顾中简表记录，不强制开会；
- 混沌工程演练触发的"计划内事故"使用本模板记录，但等级标注为"演练"。

### 1.3 核心原则

1. **Blameless（对事不对人）**：复盘只讨论系统和流程如何让事故成为可能，不追究个人责任；
2. **恢复优先**：先恢复服务，再做复盘，不在事故处理中"边修边追责"；
3. **闭环要求**：每条改进措施必须有负责人、截止日期、验收标准，未闭环不销项。

## 2. 事故等级定义表

| 等级 | 定义 | 判定标准（满足其一） | 示例 |
|------|------|----------------------|------|
| P1 | 核心功能不可用 / 严重数据风险 | 生产入口不可达超 5 分钟；根因分析服务完全无法出报告；API 5xx 错误率 > 1% 持续 5 分钟；Kafka 积压导致端到端延迟 > 5 分钟 SLA 且持续恶化；数据库不可达；审计日志中断写入 | Kafka 积压导致根因分析大面积延迟；PG 连接耗尽导致全站 5xx |
| P2 | 重要功能劣化 / 冗余受损 | API P95 > 1s 持续 5 分钟；Agent 任务失败率 > 20%；单节点宕机但服务降级可用；磁盘使用率 > 90% | 根因 Agent 偶发超时成功率降至 82%；Prometheus 磁盘告警 |
| P3 | 轻微异常 / 无用户影响 | 单次任务失败；非关键组件重启；告警噪声；页面样式缺陷不影响功能 | 单批 RCA 任务失败后自动重试成功；Kafka UI 短暂不可用 |

等级在处置过程中允许升降级：升级/降级必须在时间线中记录时间点与决策理由。

## 3. 事故基本信息表（模板）

| 字段 | 内容 |

## 5. 根因分析

### 5.1 5Why 分析模板（示例：Kafka 积压事故完整链条）

| 层级 | 问题 | 回答 |
|------|------|------|
| Why 1 | 为什么根因分析端到端延迟超标（>5 分钟）？ | Kafka topic `wafer.sensor.readings` 消费积压（Lag 峰值 31,000），消费滞后导致触发事件进入根因 Agent 平均延迟 4.5 分钟，叠加分析耗时击穿 SLA。 |
| Why 2 | 为什么消费积压？ | 消费速率（约 1.9k msg/s）远低于生产速率（峰值 12k msg/s），且单条消息处理耗时从 1.2s 劣化至 6.8s。 |
| Why 3 | 为什么单条消息处理耗时劣化 5 倍多？ | 处理链路中 Neo4j 图谱查询 P95 从 0.8s 涨至 5.9s——页面缓存命中率从 92% 跌至 41%，大量查询走磁盘。 |
| Why 4 | 为什么 Neo4j 页面缓存命中崩塌？ | 突发流量下根因任务并发升高，Neo4j 读取的工作集（活跃子图）超出 pagecache 配置（1G），且堆内存 2G 下并发查询产生大量临时对象、未释放事务拖慢整体；容器内存 limits（4G）未给缓存扩容留余量。 |
| Why 5（根因） | 为什么突发流量没有被系统提前消化或拦截？ | **技术根因**：容量规划缺失——消费组固定单副本、无自动扩缩容，Neo4j 缓存按日常 2k msg/s 配置，未按峰值 6 倍做容量设计；**流程根因**：数据生产者（合成数据/上游批次重叠）无速率契约与限流，发布容量评审（IA-OPS-001 §3）未把"上游突发速率"作为输入。 |

### 5.2 根因分类（必须双列）

| 分类 | 根因描述 | 对应措施 |
|------|----------|----------|
| 技术根因 | ① 消费者单副本无法水平扩展应对突发；② Neo4j pagecache/堆配置不足；③ 无背压/限流机制 | 改进措施 #1 #2 #3（见 §7） |
| 流程根因 | ① 上游数据生产无速率契约；② 容量评审未纳入峰值输入；③ Lag 告警阈值 10000 过高（触发时已不可逆） | 改进措施 #4（见 §7） |

**5Why 停止规则**：当回答指向"可执行的系统/流程改进"（而不是"某人不该犯错"）时停止；禁止以"人为失误"作为根因终点。

## 6. 影响评估

| 维度 | 评估 | 记录（示例值） |
|------|------|----------------|
| 用户影响 | 受影响用户群与体验 | Staging+生产 3 名工艺工程师的 RCA 报告延迟；期间发起的 14 个分析任务全部超时延迟，其中 6 个超出 SLA 5 分钟，最差 12 分钟；无任务失败 |
| 业务指标影响 | 核心业务 SLI 偏差 | 当日根因分析 P95 时延 428s（SLA 300s）；任务成功率维持 96%（未跌破 90% 底线）；月度错误预算本次消耗 45 分钟中的 12 分钟（对外可见时段），剩余 31 分钟 |
| 数据影响 | 数据完整性/一致性 | 重复批次数据落库 1 段（10:00–10:20），已按 lot_id+时间戳去重清理；审计日志无中断；无数据丢失 |
| 成本影响 | 资源与人力 | 3 人×1 小时应急处置；扩容 agent 临时多占 12G 内存 2 小时 |

## 9. 经验教训

| 类别 | 内容 |
|------|------|
| 做对的 | ① 告警在 0 分钟内触发、5 分钟内认领升级，符合 P1 SLA；② 先恢复（扩容+跳过重复窗）后根因，未在事故中过度排查；③ traceId 贯穿使 15 分钟内定位到 Neo4j 缓存问题；④ 临时处置均有决策记录，可回溯 |
| 做错的 | ① 容量规划只按日常流量设计，未考虑上游突发 6 倍场景；② Lag 告警阈值（10000）过高，触发时已不可逆；③ agent 无自动扩容能力，扩展靠人肉命令 |
| 幸运的 | ① 事故发生在上午在线人数低谷时段，未撞上批次分析高峰；② 重复数据可按时间窗精确剔除，未造成脏数据扩散；③ Neo4j 重启未引发连锁故障（数据层本应更谨慎，不应依赖运气） |

## 10. 复盘会议要求

| 项 | 要求 |
|----|------|
| 时间 | 恢复后 5 个工作日内召开（P1 事故建议 48 小时内初稿、5 日内定稿） |
| 参与人 | 事故处理全体、复盘负责人、受影响业务方代表（工艺工程师侧 1 人）、值班负责人、部门技术负责人（P1 必须） |
| 主持 | 复盘负责人（非当班处置人优先，保持视角中立） |
| 氛围原则 | **Blameless，对事不对人**：禁止"谁的责任"式提问；聚焦"系统为何允许它发生""流程为何没拦住"；主持人有权打断追责类发言 |
| 会前材料 | 时间线、5Why 草稿、影响评估须在会前 24 小时发群，参会者带修改意见参会 |
| 会议产出 | 改进措施定稿（负责人+截止日期）、风险登记项、是否需要修订告警/回滚等运维文档 |
| 决议跟踪 | 措施录入任务看板，每周例会过进度；全部"已验证"后方可将事故状态改为"已闭环" |

## 13. P3 级事故简表（免开会记录）

P3 事故不强制召开复盘会，但必须在迭代结束时以简表归档，防止"小问题黑洞"：

| 字段 | 记录 |
|------|------|
| 编号 | INC-YYYYMMDD-NNN |
| 日期时间 | YYYY-MM-DD HH:MM |
| 等级 | P3 |
| 现象 | 一句话描述 |
| 处置 | 一句话描述（自动重试成功/重启恢复等） |
| 是否需要建改进措施 | 是/否（是则并入 §8 改进措施表跟踪） |
| 记录人 | 姓名 |

示例：

| 字段 | 记录 |
|------|------|
| 编号 | INC-20261008-003 |
| 日期时间 | 2026-10-08 15:22 |
| 等级 | P3 |
| 现象 | 单批 RCA 任务因 LLM 推理服务瞬时 503 失败，自动重试第 2 次成功，无用户可见影响 |
| 处置 | 无人工干预，自动重试机制生效；确认 LLM 服务当日有发布 |
| 是否需要建改进措施 | 否（重试机制已覆盖，观察两次同类事件再立项） |
| 记录人 | 李吉 |

## 14. 混沌工程演练事故记录

计划内演练（如"设备断线""Kafka 积压""数据库延迟"注入）同样使用本模板记录，但需额外标注演练属性，用于区分真实故障率与演练结论：

| 字段 | 记录要求 |
|------|----------|
| 编号 | DRILL-YYYYMMDD-NNN（区别于真实事故 INC 前缀） |
| 演练场景 | 如：Kafka 消费者全停 10 分钟 / PG 注入 2s 延迟 / Neo4j 断连 |

| 实际结果 | 达标/未达标及偏差说明 |
| 暴露问题 | 演练发现的系统脆弱点（进入 §8 改进措施表） |
