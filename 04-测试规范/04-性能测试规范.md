## 1. 目的与适用范围

本规范定义 IndustryAgent 平台性能测试的目标基线、场景设计、执行方法与结果分析方法，使用 **k6** 作为主负载工具，覆盖业务 API 与智能体链路两条线。性能测试在 Staging（生产同构）环境执行，数据规模为生产三年预估的 50%（时序约 5000 万行聚合数据）。

## 2. 性能目标表（SLO）

| 编号 | 指标 | 目标 | 测量点 | 验收方式 |
|---|---|---|---|---|
| P-01 | API P95 延迟 | < 500ms | 全部读接口（看板/列表/详情） | k6 thresholds 硬门禁 |
| P-02 | API P99 延迟 | < 1s | 全部读接口 | k6 thresholds |
| P-03 | 写接口 P95（告警确认/审批提交） | < 800ms | 写接口 | k6 thresholds |
| P-04 | 并发用户 | 200 VU 稳定运行 ≥30min | 登录态并发混合场景 | 错误率与延迟同时达标 |
| P-05 | 根因分析端到端 | < 5 分钟（P100） | 异常注入→Top-3 展示 | E2E + k6 双验证 |
| P-06 | Kafka 消费 Lag | < 1000（稳态） | sensor-events 消费组 | exporter 观测 |
| P-07 | 错误率 | < 0.1%（含 5xx/超时） | 全场景 | k6 thresholds |
| P-08 | 8D 报告生成 | < 60s（P95） | 审批通过→报告可下载 | 智能体专项 |
| P-09 | 可用性（长跑） | 无内存泄漏/连接池耗尽，soak 2h 稳定 | 全栈 | soak 场景 + Grafana |

## 3. k6 脚本完整示例（登录 + 看板查询）

```javascript
// perf/scripts/dashboard-mix.js
// 场景：登录 → 看板聚合查询 → 异常详情 → 告警确认（读写混合，贴近真实 8:2）
import http from 'k6/http';
import { check, sleep, group } from 'k6';
import { Trend, Rate } from 'k6/metrics';

const loginLatency = new Trend('login_latency');
const detailLatency = new Trend('anomaly_detail_latency');
const errorRate = new Rate('business_error_rate');

const BASE = __ENV.BASE_URL || 'https://staging-industryagent.local';
const USERNAME = __ENV.PERF_USER || 'perf_process_engineer';
const PASSWORD = __ENV.PERF_PWD || 'Perf!Passw0rd';

export const options = {
  scenarios: {
    dashboard_mix: {
      executor: 'ramping-vus',
      startPAUses: 0,
      stages: [
        { duration: '2m', target: 50 },   // 爬坡
        { duration: '5m', target: 200 },  // 目标并发（P-04）
        { duration: '30m', target: 200 }, // 稳定段
        { duration: '2m', target: 0 },    // 下降
      ],
      gracefulRampDown: '30s',
    },
  },
  thresholds: {
    // —— 硬门禁：任一失败 k6 退出码非 0，CI 性能回归即失败 ——
    'http_req_failed': ['rate<0.001'],                    // P-07 错误率 <0.1%
    'http_req_duration{scenario:dashboard_mix}': ['p(95)<500', 'p(99)<1000'], // P-01/02
    'http_req_duration{type:write}': ['p(95)<800'],       // P-03 写接口
    'login_latency': ['p(95)<1000'],
    'business_error_rate': ['rate<0.001'],
    'checks': ['rate>0.99'],
  },
  ext: {
    loadimpact: { name: 'IndustryAgent Dashboard Mix (Staging)' },
  },
};

function login() {
  const res = http.post(`${BASE}/api/v1/auth/login`,
    JSON.stringify({ username: USERNAME, password: PASSWORD }),
    { headers: { 'Content-Type': 'application/json' }, tags: { type: 'auth' } });
  check(res, { 'login 200': r => r.status === 200 });
  loginLatency.add(res.timings.duration);
  return res.json('data.token');
}

export default function () {
  const token = login();
  const auth = { headers: { Authorization: `Bearer ${token}` } };

  group('看板聚合查询', () => {
    const board = http.get(`${BASE}/api/v1/dashboard/anomalies?page=1&pageSize=20&level=P1`, auth);
    check(board, {
      'board 200': r => r.status === 200,
      'board has data': r => (r.json('data.total') ?? 0) >= 0,
    });
  });

  group('异常详情', () => {
    const id = __ENV.ANOMALY_ID || 'ANM-PERF-0001';
    const detail = http.get(`${BASE}/api/v1/anomalies/${id}`, auth);
    detailLatency.add(detail.timings.duration);
    check(detail, { 'detail 200': r => r.status === 200 });
  });

  group('告警确认（写路径）', () => {
    const res = http.post(`${BASE}/api/v1/anomalies/${__ENV.ANOMALY_ID || 'ANM-PERF-0001'}/ack`,
      JSON.stringify({ note: 'perf-run' }),
      { ...auth, tags: { type: 'write' } });
    check(res, { 'ack 2xx': r => r.status >= 200 && r.status < 300 });
    errorRate.add(res.status >= 400);
  });

  sleep(3 + Math.random() * 4); // 思考时间 3~7s，模拟真实节奏
}
```

执行：`k6 run -e BASE_URL=https://staging... -e ANOMALY_ID=ANM-PERF-0001 perf/scripts/dashboard-mix.js`

## 4. 场景设计

| 场景 | 目的 | 负载模型 | 时长 | 通过标准 |
|---|---|---|---|---|
| 基准（Baseline） | 单用户建立延迟基线，供后续对比 | 1 VU | 10min | 记录基线，无门槛 |
| 负载（Load） | 验证 200 并发日常负载 | ramping-vus → 200 | 30min 稳定段 | P-01/02/03/07 全达标 |
| 峰值（Peak/Spike） | 突发流量（批次放行高峰） | 50→400 VU 阶跃 5min，回落 | 15min | 允许延迟劣化 ≤50%，不崩溃、自动恢复 |
| 浸泡（Soak） | 内存泄漏/连接池/GC 长期问题 | 100 VU 恒压 | **2h** | P-06 Lag<1000；RSS/连接数平稳；错误率<0.1% |
| 压力（Stress） | 找到系统拐点与失效模式 | 阶梯 +50 VU/5min 递增 | 至失败 | 记录拐点 VU 与首要瓶颈，验证优雅降级 |

执行节奏：I5 首轮全场景 → I6 发布前 Load + Soak 复验 → 每次大版本回归 Load 场景。

## 5. 智能体专项性能测试

### 5.1 LLM 延迟模拟与并发根因任务

真实 LLM 延迟方差大且不可控，性能测试采用**延迟注入模拟**（可复现），验收用少量真实调用交叉验证：

| 项 | 方法 | 目标 |
|---|---|---|
| LLM 延迟模拟 | mock 服务注入固定延迟：P50=8s / P95=25s / P99=45s（对标真实 GLM 类模型） | 验证 5min 端到端预算在 P99 LLM 延迟下仍成立 |
| Token 吞吐 | 记录每次调用的 input/output token 数与耗时，计算 tokens/s | 输出吞吐基线，纳入报告；成本=Σtokens×单价 |
| 并发根因任务 | k6 触发 `POST /anomalies/:id/rca` 至 20 个并发任务 | 任务队列无死锁，全部在 5min 内完成（P-05） |
| 8D 报告生成 | 审批完成→报告可下载计时 | P95 < 60s（P-08） |
| 降级路径 | LLM mock 超时 60s | 熔断降级返回缓存嫌疑（degraded），不拖垮全链路 |

```javascript
// perf/scripts/rca-concurrent.js（片段）：并发根因任务专项
export const options = {
  scenarios: {
    rca_burst: {
      executor: 'per-vu-iterations',
      vus: 20, iterations: 1, maxDuration: '6m',
    },
  },
  thresholds: {
    'http_req_failed': ['rate<0.001'],
    'rca_e2e_duration': ['p(100)<300000'], // P-05：P100 < 5min
  },
};

export default function () {
  const token = login();
  const start = Date.now();
  const res = http.post(`${BASE}/api/v1/anomalies/ANM-PERF-RCA/rca`,
    JSON.stringify({ topK: 3 }),
    { headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' } });
  const taskId = res.json('data.taskId');
  let done = false;
  while (!done && Date.now() - start < 300000) {
    sleep(5);
    const poll = http.get(`${BASE}/api/v1/rca-tasks/${taskId}`,
      { headers: { Authorization: `Bearer ${token}` } });
    done = poll.json('data.status') === 'done';
    check(poll, { 'task poll 200': r => r.status === 200 });
  }
  rcaE2e.add(Date.now() - start);
  check(null, { 'rca within 5min': () => Date.now() - start < 300000 });
}
```

### 5.2 数据要求

评估/性能数据用 Staging 冻结数据集（含漂移、尖峰特征模板），任务输入从预置异常池轮询，避免同一异常的缓存命中干扰并发测量。

## 6. 数据库性能测试

| 项 | SQL/方法 | 目标/基线 |
|---|---|---|
| 时序聚合查询（看板 24h 窗口） | `SELECT time_bucket('5min', ts), avg(value) FROM sensor_events WHERE equipment=$1 AND ts > now()-interval '24h' GROUP BY 1` | P95 < 300ms |
| 连续超高负载查询 | 200 VU 并发下重复上述查询 | 无锁等待 >1s，无慢查询风暴 |
| 索引验证 | `EXPLAIN ANALYZE` 确认命中 `(equipment_id, ts DESC)` 与 hypertable 压缩 | Index Scan / Chunk Scan，非 Seq Scan |
| 慢查询基线 | 开启 `pg_stat_statements`，`total_exec_time > 500ms` 的语句清单 | 每轮性能测试后输出清单，Top5 须有优化结论 |
| 连接池 | Egg.js `agent/mysql pg pool` 在 400 VU 峰值下的等待队列 | 无 `timeout exceeded` 错误 |

规则：任何新增列表类 API 必须先过 `EXPLAIN ANALYZE` 评审（进入 IA-QA-002 评审清单），防止上线后拖库。

## 7. 监控联动（k6 + Prometheus + Grafana）

1. k6 启动 `--out experimental-prometheus-rw`，指标实时写入 Prometheus Remote Write。
2. Grafana 建立"性能测试实时大盘"：VU 曲线、RPS、P95/P99 叠加曲线、错误率、与应用侧指标（Node 事件循环延迟、pg 连接池占用、Kafka Lag、LLM mock 延迟）同屏对照。
3. 关键对照看板面板：
   - k6 P95 vs 应用 P95（差异大=网络/网关问题）
   - Kafka consumer Lag vs VU 数（Lag 随负载线性增长=消费能力不足，联动 P-06）
   - DB 慢查询计数 vs RPS
4. 每轮测试导出 Grafana 快照（PNG/JSON）作为 IA-QA-006 附件，报告中给出指标曲线截图而非纯数字。

```bash
  -e BASE_URL=https://staging-industryagent.local \
  perf/scripts/dashboard-mix.js
```

## 8. 结果分析方法

### 8.1 报告解读要点

1. **先看错误率再延迟**：错误率 >0.1% 时延迟数据不可信（快速失败会美化 P95）。
2. **看分位形态而非均值**：P95 与 P50 差距 >5 倍说明长尾问题（GC、锁、慢查询）。
3. **区分冷启动**：排除前 2 分钟爬坡段数据再评估 thresholds。
4. **soak 看趋势**：内存/RSS/连接数曲线斜率非零即疑似泄漏，即使阈值达标也要记录。

### 8.2 瓶颈定位决策树

```
延迟超标/错误率超标
│
├─▶ 1. 网络层（首先排除）
│     k6 P95 ≈ 应用侧 P95 + 常数？ 传输耗时 >10ms？
│     ├─ 是 → 检查：k6 压力机带宽/ TLS/ 反向代理(Nginx)缓冲
│     └─ 否 ↓
│
├─▶ 2. 应用层
│     Node 事件循环延迟 >50ms？ CPU 饱和？ Egg worker 队列堆积？
│     ├─ 是 → 定位：同步阻塞调用 / JSON 大对象序列化 / 缺缓存(Redis)
│     │       验证：加 Redis 缓存后同场景复测对比
│     └─ 否 ↓
│
├─▶ 3. 数据库层
│     pg 慢查询清单有新增？ 连接池等待？ 锁等待？
│     ├─ 是 → EXPLAIN ANALYZE → 补索引/改写 SQL/加大 time_bucket 粒度
│     │       时序表确认压缩(chunk)与保留策略生效
│     └─ 否 ↓
│
├─▶ 4. LLM/智能体层（仅根因分析等智能体场景）
│     根因任务耗时 = LLM 耗时 + 工具(KG/RAG)耗时？
│     ├─ LLM 占大头 → 并发 LLM 调用/流式输出/提示词瘦身/缓存相似问询
│     ├─ 工具占大头 → Neo4j 查询超时？ pgvector 索引(ivfflat)失效？
│     └─ 队列积压 → Kafka Lag(P-06) 超 1000 → 扩消费者/背压
│
└─▶ 5. 仍未定位 → 开 OpenTelemetry 追踪，按 span 耗时瀑布定位热点
```

### 8.3 结果记录规范

每轮性能测试在 `perf/reports/` 归档：k6 summary JSON、Grafana 快照、pg_stat_statements Top 清单、结论与改进项。格式统一以便纵向（跨迭代）对比。

## 9. 性能回归门禁

1. **CI 层（每次合入 main）**：跑 10 分钟"冒烟性能"（50 VU / 5min，仅看板混合场景），thresholds 同 P-01/02/07，失败阻断合并。
2. **迭代层（I5 起）**：Load + Soak 全场景达标，未达标项进入发布评审决策。
3. **趋势门禁**：核心接口 P95 相比上一轮基线劣化 >10% 即告警，>20% 阻断发布（防"渐变劣化"）。
4. 基线冻结：每个发布版本的性能基线存入 `perf/baselines/{version}.json`，作为下一版本对比锚点。
5. 豁免规则：性能门禁失败如需豁免，须由产品负责人与测试工程师联合签署，写入 IA-QA-006 遗留风险。

## 10. 执行前提与环境约束

1. Staging 独占执行（性能测试期间封板，禁止他人使用）。
2. 压力机与被测环境同机房/同云可用区，避免公网抖动。
3. 测试前采集一轮基线监控快照（Grafana 面板 15min），确认系统空载健康。
4. 每轮结束输出对比表（本轮 vs 基线 vs SLO），直接引用进 IA-QA-006 报告模板的"性能测试结果表"。
