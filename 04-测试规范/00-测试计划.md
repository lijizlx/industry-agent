## 1. 引言

### 1.1 项目背景

IndustryAgent 是面向芯联半导体（虚拟沙盒）12 英寸晶圆厂的良率根因分析智能体平台。系统通过 监控Agent → 根因Agent（Top-3嫌疑） → 建议Agent → 审批Agent（HITL） → 报告Agent（8D） 五级智能体链路，实现良率异常的自动检测、根因定位、调参建议、人工审批与 8D 报告闭环。

技术栈：Egg.js 4.0 业务后端、React 18 + TypeScript + Ant Design 前端、Python FastAPI + LangGraph 智能体服务、PostgreSQL + TimescaleDB + pgvector、Neo4j 知识图谱、Kafka 消息队列、Redis 缓存、MinIO 对象存储。

### 1.2 测试代码示例（冒烟用例）

测试计划本身通过代码落地。以下为 CI 冒烟阶段第一条用例，验证三大服务连通性：

```javascript
// test/smoke/health.test.js — 三大服务连通性冒烟测试
const { expect } = require('chai');
const request = require('supertest');

describe('冒烟测试 /health', () => {
  it('GET /api/v1/health 应返回 200 且三大依赖健康', async () => {
    const res = await request(app)
      .get('/api/v1/health')
      .expect(200);
    expect(res.body).to.have.property('db', 'ok');
    expect(res.body).to.have.property('redis', 'ok');
    expect(res.body).to.have.property('agentService', 'ok');
  });
});
```

## 2. 测试范围与目标

### 2.1 项目质量目标（对齐第 12 章评估体系）

| 编号 | 指标 | 目标值 | 验证手段 |
|---|---|---|---|
| G1 | 根因 Top-3 准确率 | > 80% | 离线评估集（SECOM/WM-811K 标注 + 合成标注） |
| G2 | MTTR 降低 | > 50% | E2E 全链路计时 vs 人工基线（8h→<4h） |
| G3 | 误报率 | < 10% | 监控 Agent 评估集跑批统计 |
| G4 | 人工接管率 | < 30% | Staging 两周运行统计审批/接管日志 |
| G5 | 端到端延迟（异常→8D报告） | < 5 分钟 | E2E 计时 + 性能测试 |
| G6 | API P95 / P99 | < 500ms / < 1s | k6 性能测试 |
| G7 | 并发用户 | 200 | k6 负载/峰值场景 |
| G8 | 系统可用性 | 99.9% | 混沌工程 + Staging 长跑 |
| G9 | 覆盖率 | 后端语句/分支 ≥80%，前端 ≥70% | CI 覆盖率门禁 |

### 2.2 测试范围（In Scope）

| 模块 | 范围说明 |
|---|---|
| 监控 Agent 链路 | FDC 异常检测规则、传感器时序消费（Kafka）、异常事件生成 |
| 根因 Agent 链路 | Top-3 嫌疑生成、知识图谱查询（Neo4j）、RAG 检索（pgvector）、因果推断调用 |
| 建议 Agent | 调参/停线建议生成、风险等级标注 |
| 审批 Agent（HITL） | 审批流状态机、审计日志、RBAC 权限校验 |
| 报告 Agent | 8D 报告生成、MinIO 归档、导出 |
| 业务后端 | 认证授权、告警/工单 CRUD、报表 API、参数校验、事务 |
| 前端 | 登录、实时看板、异常详情、审批工作台、报告查看 |
| 非功能 | 性能（G5~G8）、安全（RBAC/审计/脱敏）、可观测性（指标埋点验证） |
| 混沌/鲁棒性 | 脏数据注入（缺失/漂移/尖峰/重复/延迟）、依赖故障（DB/Redis/Kafka/LLM 宕机） |

### 2.3 不测范围（Out of Scope）

- 第三方库（Egg.js、React、LangGraph）内部实现
- 基础设施自身（PostgreSQL、Kafka 引擎内部）
- 真实 MES/SCADA 系统（虚拟沙盒以模拟器代替）
- 真实 LLM 供应商侧的可用性（以 mock + 延迟模拟覆盖）

## 3. 测试策略

### 3.1 测试金字塔

```
        ▲  E2E 10%（≤30 条）   Playwright，只覆盖核心业务闭环
      ▲▲▲  集成 20%            supertest + docker-compose test stack
  ▲▲▲▲▲▲  单元 70%             mocha/vitest/pytest，CI 强制覆盖率门禁
```

| 层级 | 用例占比 | 工具 | 执行时机 | 反馈目标 |
|---|---|---|---|---|
| 单元测试 | 70% | 后端 mocha+chai+sinon；前端 vitest+RTL；智能体 pytest | 每次提交（pre-push + CI） | < 10 分钟 |
| 集成测试 | 20% | supertest + docker-compose test stack（pg+redis+kafka+minio） | 每次合入 main | < 25 分钟 |
| E2E 测试 | 10% | Playwright（≤30 条核心闭环） | 每日夜间 + 发布前 | < 40 分钟 |
| 性能测试 | 专项 | k6 | 迭代末 + 发布前 | 按场景 |
| 智能体评估 | 专项 | pytest + 自研评估脚本 + 标注评估集 | 每迭代末 + 提示词/模型变更时 | 按 G1~G4 |
| 混沌工程 | 专项 | 故障注入脚本（依赖摘除、延迟注入） | I5 起，每迭代一次 | 按 G8 |

### 3.2 分层策略说明

- **单元层快速反馈**：Service 层业务逻辑、工具函数、智能体工具函数必须单测覆盖（详见 IA-QA-002）。
- **集成层验证契约**：模块间接口（Egg.js↔DB、Egg.js↔Python 服务、Kafka、Neo4j、MinIO）以真实容器验证（详见 IA-QA-003）。
- **E2E 只做业务闭环**：登录→看板→异常→根因→审批→8D 报告等 5~8 条主链路（详见 IA-QA-004）。
- **智能体确定性策略**：LLM 输出非确定，功能测试一律 mock LLM；质量指标走独立离线评估集，不混入功能回归。

## 4. 测试环境矩阵

| 环境 | 构成 | 数据库初始化 | 用途 | 执行频率 |
|---|---|---|---|---|
| 本地（Local） | 开发机 Docker Compose 全栈（pg+timescale、redis、kafka、neo4j、minio、agent-svc、backend、frontend） | 合成数据 seed 脚本，按需 `make seed` | 开发自测、冒烟、单测 | 每日 |
| CI | GitHub Actions + Services 容器（隔离临时实例） | 每次任务全新拉起，seed 后执行，测毕销毁 | 单元/集成测试、覆盖率门禁 | 每次提交/合入 |
| Staging | 与生产同构的 Docker Compose 集群 + Prometheus/Grafana + Keycloak | 每迭代重置；含 SECOM/WM-811K 基线数据 + 15% 脏数据注入 | E2E、性能、智能体评估、混沌、长跑 | 每迭代末 + 发布前 |

环境管理约束：

1. Staging 配置与生产一致（版本、环境变量、资源限额），仅数据与域名不同。
2. CI 数据库实例完全隔离，任务结束即销毁，杜绝用例间残留。
3. 本地环境允许开发者自由改造，但跑集成测试前必须执行 `make seed` 保证基线一致。

## 6. 入口准则与退出准则

### 6.1 测试入口准则（Test Entry Criteria）

1. 需求/故事已评审通过，验收标准（AC）明确且可测。
2. 开发完成并合入迭代分支，CI 单元测试全部通过。
3. 冒烟测试（health + 登录 + 数据管道）通过。
4. 测试环境就绪（Staging 已部署对应版本，seed 完成）。
5. 测试数据已准备（合成数据 + 脏数据注入到位）。

### 6.2 测试退出准则（Test Exit Criteria）

1. 计划用例执行率 100%，无未执行用例（阻塞除外且已记录）。
2. 用例通过率 ≥ 98%，P0/P1 缺陷全部修复并回归通过。
3. 遗留缺陷 ≤ 5 个（均为 P2/P3），每条有风险说明与规避方案。
4. 性能指标全部达标（G5~G8），或未达标项已由发布评审豁免并留档。
5. 覆盖率门禁通过（后端 ≥80%、前端 ≥70%）。
6. 智能体评估指标（G1~G4）达标。
7. IA-QA-006 测试报告编制完成并通过评审。

## 7. 测试数据管理策略

### 7.1 数据来源三层结构

| 层 | 来源 | 用途 | 管理方式 |
|---|---|---|---|
| L1 公开数据 | SECOM（591 特征良率数据）、WM-811K（晶圆缺陷图） | 智能体评估基线、回归评估集 | 版本化存于 MinIO，清洗版与原始版双轨 |
| L2 合成数据 | Faker/SDV/TimeGAN 生成传感器时序、Recipe、告警、工单、用户；LLM 生成工艺文档（RAG 语料） | 功能测试、性能测试、E2E | seed 脚本 + 工厂函数，可确定重放 |
| L3 脏数据注入 | 在 L2 基础上按规则注入 | 鲁棒性/混沌测试 | 注入器脚本，比例可配置 |

### 7.2 脏数据注入策略（占合成数据 15%）

| 脏数据类型 | 注入比例（占脏数据） | 典型注入方式 | 验证目标 |
|---|---|---|---|
| 缺失 | 30% | 随机删除字段、连续 30 分钟时序空洞 | 监控 Agent 不崩溃、告警提示数据缺失 |
| 漂移 | 20% | 传感器均值偏移 +3σ、方差放大 | FDC 能检出漂移而非误报尖峰 |
| 尖峰 | 15% | 单点突变 10 倍、阶跃 | 异常检测触发、不产生级联误报 |
| 重复 | 15% | 重复工单、重复传感器读数 | 幂等消费、去重逻辑 |
| 延迟 | 20% | Kafka 注入积压、事件时间戳乱序 | 端到端延迟可控、乱序容忍 |

### 7.3 数据管理规则

1. 评估集（L1 + 标注）冻结版本，提示词/模型/工具链任何变更必须重跑。
2. 功能测试使用清洗版数据，鲁棒性测试使用原始 + 注入版数据。
3. 所有测试数据为虚拟生成，不含真实个人信息；虚拟工号/姓名由 Faker 生成。
4. seed 脚本幂等（可重复执行），CI 每任务重建，Staging 每迭代重建。
5. 性能测试数据量按生产三年规模预估的 50% 构造（时序约 5 亿行聚合后约 5000 万行）。

## 10. 缺陷管理流程

### 10.1 缺陷等级定义

| 等级 | 定义 | 示例 |
|---|---|---|
| P0 致命 | 系统不可用、核心链路中断、数据丢失/越权、智能体全链路阻塞 | 根因 Agent 服务不可用；审批数据丢失；未授权用户可调用审批 API |
| P1 严重 | 主要功能未按预期，无可用替代方案 | Top-3 输出为空；8D 报告生成失败；Kafka 消费中断导致告警丢失 |
| P2 一般 | 次要功能失效或有替代方案 | 报表导出偶发格式错误；看板图表刷新延迟；非关键页面文案错误 |
| P3 轻微 | 界面/体验/文档问题，不影响功能 | 错别字；UI 对齐；日志冗余 |

### 10.2 缺陷 SLA

| 等级 | 响应时限 | 修复时限 | 回归验证时限 | 修复策略 |
|---|---|---|---|---|
| P0 | 立即（< 30 分钟） | < 4 小时 | 修复后立即回归 | 阻塞一切发布，现修现发 |
| P1 | < 4 小时 | < 2 个工作日 | 当迭代内 | 阻塞发布，须当迭代修复 |
| P2 | < 1 个工作日 | < 5 个工作日 | 下一迭代 | 不阻塞发布，遗留须风险评估 |
| P3 | < 2 个工作日 | 排期修复 | 下一迭代 | 不阻塞发布 |

补充规则：

1. 每条缺陷必填：等级、复现步骤、期望/实际结果、环境版本、日志/截图、所在模块。
2. Reopened 超过 2 次升级为 P1 处理，并在迭代复盘会分析。
3. 缺陷按模块与迭代双维度统计，趋势进入 IA-QA-006 报告。
4. 线上类问题（Staging 长跑发现）直接 P0/P1 起步，须事故复盘（参照手册 14.3 模板）。
