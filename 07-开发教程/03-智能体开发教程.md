## 1. 导读：智能体全景图

### 1.1 我们要构建什么

虚拟企业设定（摘自实战手册案例 A）：

- **企业**：芯联半导体，12 英寸晶圆制造厂，3 条产线，月产能 5 万片，产品为 MCU 与电源管理芯片。
- **事件**：某天良率突然从 95% 下跌 2 个百分点，工艺工程师需要在 **4 小时内**定位根因，人工排查平均需要 8 小时。
- **目标**：构建 `industryagent-agent` 智能体服务，把根因定位时间压缩到 5 分钟以内，Top-3 嫌疑准确率 > 80%，误报率 < 10%，人工接管率 < 30%。

最终跑通的完整闭环：

```text
监控Agent检测FDC异常 → 根因Agent输出Top-3嫌疑（图谱+RAG+因果三路证据）
→ 建议Agent生成调参/停线建议 → 审批Agent人工确认(HITL)
→ 报告Agent生成8D报告 → 评估Agent计算指标
```

### 1.2 数据流全景图（5 个业务 Agent + 1 个评估 Agent）

```text
                    ┌──────────────────────────────────────────────────────────────────┐
                    │                        数据层（只读，供工具查询）                  │
                    │  TimescaleDB(传感器时序)  Neo4j(工艺知识图谱)  PostgreSQL+pgvector  │
                    │                                            (工艺文档RAG向量库)      │
                    └────────▲─────────────────▲──────────────────────▲───────────────┘
                             │                 │                      │
                        [工具:sensors]   [工具:knowledge_graph]  [工具:rag_search]
                             │                 │                      │
                             │            [工具:causality(DoWhy)] ────┤
                             │            [工具:data_stats(SECOM)] ──┘
                             │                 │
┌────────────┐    ┌─────────┴──────┐   ┌──────▼───────┐   ┌──────────────┐   ┌──────────────┐
│ ① 监控Agent │───▶│ ② 根因Agent    │──▶│ ③ 建议Agent  │──▶│ ④ 审批Agent   │──▶│ ⑤ 报告Agent   │
│ SPC 3σ/EWMA│    │ 图谱+RAG+因果  │   │ 调参/停线建议 │   │ HITL人工确认  │   │ 8D报告生成    │
│ 孤立森林    │    │ Top-3嫌疑JSON  │   │ 风险等级/影响 │   │ interrupt中断 │   │ Markdown/PDF  │
└─────┬──────┘    └────────────────┘   └──────────────┘   └──────┬───────┘   └──────┬───────┘
      │异常事件         │Top-3+证据链         │建议+风险            │approve/reject      │8D报告
      │                 │                    │                    │(驳回→终止)         │
      ▼                 ▼                    ▼                    ▼                    ▼
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                        ⑥ 评估Agent（闭环外，事后异步运行）                                  │
│   Top-3命中率 / 误报率 / 人工接管率 / 端到端延迟 / 审批平均耗时 / Token成本                    │
│   产出: 评估报告 → 反馈回流(人工修正标签 → 提示词迭代 → 回归评估)                             │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

读图要点：

1. **每个 Agent 只做一件事**：监控只管"有没有异常"，根因只管"嫌疑排序"，建议只管"怎么办"，审批只管"允不允许"，报告只管"如何留痕"。职责单一才能独立测试、独立评估。
2. **Agent 不直接连数据库**：所有数据访问都通过"工具层"。工具是带 docstring 的函数，LLM 通过 docstring 判断什么时候调用哪个工具。这层解耦让我们后面可以把同一套工具暴露为 MCP Server 供 Egg.js 业务后端复用（见第 12 章）。
3. **评估 Agent 在闭环之外**：它不参与线上决策，只做事后量化。这是实战手册第 12 章的核心思想——没有量化，智能体就无法迭代。
4. **人机协同（HITL）是一等公民**：审批 Agent 使用 LangGraph 的 `interrupt` 机制暂停整个流程，等待工程师确认后恢复。这是工业场景的硬性要求（手册 10.3 节：关键建议必须人工审批）。

### 1.3 为什么用 LangGraph 而不是裸调 LLM 或 AutoGen/CrewAI

| 维度 | LangGraph 的答案 | 为什么对本项目至关重要 |
|---|---|---|
| 流程可控 | 显式状态机：节点、边、条件边全部由代码定义 | 良率分析流程是**固定工单流程**（检测→根因→建议→审批→报告），不允许 LLM 自由发挥"下一步做什么" |
| 人机协同中断 | 原生 `interrupt()` / `Command(resume=...)` 机制 | 审批可能等 2 小时也可能等 24 小时，流程必须能"冻结-恢复"，且状态不丢 |
| 持久化 | Checkpointer（MemorySaver → PostgresSaver） | 审批等待期间服务重启，流程必须从断点继续 |
| 循环与重试 | 条件边 + recursion_limit | 根因 Agent 需要多次调用工具收集证据，但要防止死循环 |
| 结构化状态 | TypedDict State 贯穿全图 | 每个节点的输入输出可类型检查、可测试、可序列化到数据库 |
| 可观测 | 每步状态快照、LangSmith 可选接入 | 审计要求：每条结论必须能回溯到哪个节点、哪个工具产出 |

一句话总结：**对话式框架（AutoGen/CrewAI）适合"目标开放、路径未知"的任务；工业流程是"路径已知、节点确定"的状态机，LangGraph 就是为后者设计的。**

### 1.4 学完本教程你能做什么

- 从零搭建一个生产形态的 Python 智能体服务（FastAPI + LangGraph + 私有化 LLM）；
- 编写供 LLM 调用的工具（时序查询、图谱查询、RAG 检索、因果推断），并理解工具描述（docstring）的写作规范；
- 设计防幻觉的中文提示词，强制"证据引用 + 只基于工具返回的事实"；
- 实现人机协同审批：中断、持久化、恢复、超时升级；
- 构建量化评估体系（Top-3 命中率、误报率、人工接管率、端到端延迟）并建立回归评估流水线；
- 用 MCP 协议把工具暴露给 Egg.js 业务后端，形成"业务编排 + AI 计算"的混合架构。

### 1.5 阅读约定

- 所有代码块**完整可运行**，不省略 import 与函数体；项目的每个阶段都有"验证"步骤，请务必逐个执行。
- 项目根目录约定为 `industryagent-agent/`，下文所有相对路径均基于此目录。
- 本教程的运行验证环境：Windows 11 / Linux 均可，Python 3.11.x，Docker 用于启动 Neo4j、TimescaleDB、PostgreSQL+pgvector。
- 数据库中的数据由配套的合成数据脚本生成（模拟传感器时序、工艺文档、图谱、缺陷记录）。若你从零开始，第 2.6 节给出了最小化初始化 SQL 与 Cypher，保证教程可以独立跑通。

## 2. 环境准备

### 2.1 Python 3.11 安装与虚拟环境

本项目要求 Python 3.11（DoWhy 与 langgraph 生态对 3.11 兼容性最佳）。验证版本：

```bash
python --version   # 应输出 Python 3.11.x
```

**方式一：venv（教程主线，最简单）**

```bash
mkdir industryagent-agent && cd industryagent-agent
python -m venv .venv

# Windows (Git Bash)
source .venv/Scripts/activate
# Linux / macOS
# source .venv/bin/activate

python -m pip install --upgrade pip
```

**方式二：poetry（团队协作推荐）**

```bash
pip install poetry
cd industryagent-agent
poetry init --no-interaction --python 3.11
# 安装依赖时使用 poetry add <package>，依赖会写入 pyproject.toml 与 poetry.lock
poetry install
poetry shell
```

本教程后续命令均以 venv 方式书写，poetry 用户把 `pip install` 换成 `poetry add`、把 `python xxx.py` 换成 `poetry run python xxx.py` 即可。

### 2.3 LLM 环境：OpenAI 兼容接口 + 私有部署

本项目的硬约束是**数据不出域**（手册 11 章：合规约束），因此 LLM 必须私有部署。我们统一走 OpenAI 兼容接口，一套代码同时支持三种形态：

| 形态 | base_url | 说明 |
|---|---|---|
| vLLM 私有部署（推荐生产） | `http://vllm-server:8000/v1` | `vllm serve Qwen/Qwen2.5-32B-Instruct` 即提供一个 OpenAI 兼容 `/v1/chat/completions` |
| Ollama 本地开发 | `http://localhost:11434/v1` | `ollama pull qwen2.5:14b`，适合笔记本调试 |
| OpenAI 官方/云中转（仅测试） | `https://api.openai.com/v1` | 仅用于非敏感测试数据 |

**vLLM 私有部署说明（生产形态）**：

```bash
# 在 GPU 服务器上（例如 2×A100，显存足够跑 32B 量化模型）
pip install vllm
vllm serve Qwen/Qwen2.5-32B-Instruct \
  --host 0.0.0.0 --port 8000 \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.90

# 验证 OpenAI 兼容接口可用：
curl http://<vllm-server>:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer EMPTY" \
  -d '{"model":"Qwen/Qwen2.5-32B-Instruct","messages":[{"role":"user","content":"你好"}],"max_tokens":32}'
```

在本项目中创建 `.env` 文件（**切勿提交到 Git**，加入 `.gitignore`）：

```bash
# .env —— LLM 配置（OpenAI 兼容）
LLM_BASE_URL=http://localhost:11434/v1     # 开发用 Ollama；生产改为 http://vllm-server:8000/v1
LLM_API_KEY=EMPTY                          # vLLM/Ollama 不校验时填 EMPTY，代码统一从环境变量读
LLM_MODEL=qwen2.5:14b                      # 生产建议 Qwen2.5-32B-Instruct

# ---- 数据库 ----
TIMESCALE_DSN=postgresql://ia:ia_secret@localhost:5432/industryagent
PGVECTOR_DSN=postgresql://ia:ia_secret@localhost:5433/industryagent_rag
NEO4J_URI=bolt://localhost:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=neo4j_secret

# ---- 服务 ----
APP_HOST=0.0.0.0
APP_PORT=8300
APPROVAL_TIMEOUT_HOURS=24
RISK_ESCALATION_THRESHOLD=200              # 影响晶圆数超过该值必须升级人工

# ---- Embedding（RAG 向量服务，OpenAI 兼容 /v1/embeddings）----
EMBEDDING_BASE_URL=http://localhost:8080
EMBEDDING_MODEL=bge-large-zh
EMBEDDING_API_KEY=EMPTY

# ---- 业务后端回调（Egg.js，第 16.3 节任务状态通知）----
BACKEND_BASE_URL=http://127.0.0.1:7001     # Egg.js 网关地址
BACKEND_CALLBACK_TOKEN=ia-agent-internal   # 内部回调令牌（生产环境必换并走内网）
```

> **为什么封装 OpenAI 兼容接口是关键设计**：`langchain-openai` 的 `ChatOpenAI` 支持自定义 `base_url`，意味着同一份代码在开发机（Ollama）、公司 GPU 集群（vLLM+Qwen）、测试环境（OpenAI）之间**零改动切换**，只需改环境变量。这直接呼应手册的"数据不出域"约束——生产环境的推理流量永远不出内网。

def seed_sensor_readings(s, equip_ids: dict[str, int],
                         inject_fault: bool = True) -> int:
    """写入 8 天传感器时序（5 分钟一条）；ETCH-03/chamber_temp 注入 +2σ 阶跃（近 48h）。

    数据机理（与第 13 章因果验证闭环）：
    - 正常段：chamber_temp ~ N(80.0, 0.5)
    - 故障段（近 48h）：chamber_temp ~ N(81.0, 0.5)   ← 已知注入根因
    """
    rng = random.Random(42)
    rows: list[tuple] = []
    start = NOW - timedelta(days=8)
    n_points = 8 * 24 * 12  # 5 分钟一条
    fault_start = NOW - timedelta(hours=48)

    param_by_stage = {
        "etch": ["chamber_temp", "rf_power", "pressure"],
        "deposition": ["chamber_temp", "gas_flow", "film_thickness"],
        "litho": ["exposure_dose"],
    }
    for code, eid in equip_ids.items():
        stage = next(e[3] for e in EQUIPMENTS if e[0] == code)
        for param in param_by_stage[stage]:
            base_mean, base_std, unit = PARAM_BASELINE[param]
            for i in range(n_points):
                ts = start + timedelta(minutes=5 * i)
                mean = base_mean
                if inject_fault and code == "ETCH-03" and param == "chamber_temp" \
                        and ts >= fault_start:
                    mean = base_mean + 2.0 * base_std   # 注入 +2σ 阶跃
                rows.append((eid, param, ts, round(rng.gauss(mean, base_std), 4),
                             unit, "good"))

    with _conn(s.timescale_dsn) as conn, conn.cursor() as cur:
        cur.executemany(
            "INSERT INTO sensor_readings (equipment_id, parameter_name, recorded_at, "
            "value, unit, quality) VALUES (%s, %s, %s, %s, %s, %s) "
            "ON CONFLICT DO NOTHING", rows)
        conn.commit()
    print(f"[init] sensor_readings 种子 {len(rows)} 条"
          f"（ETCH-03/chamber_temp 近48h 注入 +2σ 阶跃={inject_fault}）")
    return len(rows)


def seed_lot_batches(s, equip_ids: dict[str, int]) -> int:
    """写入 14 天批次良率：ETCH-03 近 5 天 actual_yield 从 0.95 降至约 0.93。

    机理：chamber_temp 每偏 1σ → 良率降 1.2pct（+2σ ≈ -2.4pct，含噪声取 0.93 附近）。
    """
    rng = random.Random(7)
    rows: list[tuple] = []
    for d in range(14, -1, -1):
        day = NOW - timedelta(days=d)
        for code, eid in equip_ids.items():
            for k in range(3):  # 每设备每天 3 批
                lot_no = f"B{day:%Y%m%d}{code[-2:]}{k}"
                yield_val = 0.95 + rng.gauss(0, 0.004)
                if code == "ETCH-03" and d <= 5:
                    yield_val -= 0.02 + (5 - d) * 0.002  # 近 5 天逐步下降
                rows.append((lot_no, "MCU-7nm", eid, 25,
                             day - timedelta(hours=8), day,
                             round(min(max(yield_val, 0.0), 1.0), 4)))
    with _conn(s.timescale_dsn) as conn, conn.cursor() as cur:
        cur.executemany(
            "INSERT INTO lot_batches (lot_no, product_code, current_equipment_id, "
            "quantity, start_time, end_time, actual_yield, status) "
            "VALUES (%s, %s, %s, %s, %s, %s, %s, 'completed') "
            "ON CONFLICT (lot_no) DO NOTHING", rows)
        conn.commit()
    print(f"[init] lot_batches 种子 {len(rows)} 条（ETCH-03 近5天良率下降已注入）")
    return len(rows)


def seed_doc_chunks(s) -> int:
    """写入工艺文档切片。embedding 用确定性伪随机填充（1536 维）。

    说明：正式环境的 embedding 必须由向量模型生成（见 5.4 节 _embed）；

    rng = random.Random(2026)

# ---------- 评估注入器（第 13 章 run_eval.py 复用）----------

def inject_anomaly(sample: dict, equip_ids: dict[str, int],
                   clear_first: bool = True) -> int:
    """按评估样本向 TimescaleDB 注入"已知根因"的异常时序。

    Args:
        sample: eval/dataset.py 生成的样本 dict（含 injected_type/magnitude_sigma）。
        equip_ids: code → id 映射。
        clear_first: 先清除该设备相关参数近 48h 数据（避免上次注入残留）。

    Returns:
        写入的读数条数。
    """
    s = get_settings()
    equipment = sample["equipment"]
    params: list[str] = sample["parameters"]
    eid = equip_ids[equipment]
    sigma = sample.get("magnitude_sigma", 1.0)
    itype = sample.get("injected_type", "step_shift")
    rng = random.Random(hash(sample["sample_id"]) & 0xFFFFFFFF)

    with _conn(s.timescale_dsn) as conn, conn.cursor() as cur:
        if clear_first:
            for p in params or []:
                cur.execute(
                    "DELETE FROM sensor_readings WHERE equipment_id=%s "
                    "AND parameter_name=%s AND recorded_at >= %s",
                    (eid, p, NOW - timedelta(hours=48)))
        rows = []
        for p in params:
            mean, std, unit = PARAM_BASELINE.get(p, (80.0, 0.5, "degC"))
            n = 48 * 12  # 48h × 5min
            for i in range(n):
                ts = NOW - timedelta(hours=48) + timedelta(minutes=5 * i)
                m, std_i = mean, std
                if itype == "step_shift" and i >= n // 2:
                    m = mean + sigma * std               # 中点阶跃
                elif itype == "slow_drift":
                    m = mean + sigma * std * (i / n)     # 线性慢漂
                elif itype == "variance":
                    std_i = std * (1 + 2 * sigma * (i / n))  # 方差膨胀
                elif itype == "coupled":
                    m = mean + sigma * std * (i / n)     # 耦合=双参数同漂
                # itype == "none"：阴性样本，保持正常数据
                rows.append((eid, p, ts, round(rng.gauss(m, std_i), 4),
                             unit, "good"))
        cur.executemany(
            "INSERT INTO sensor_readings (equipment_id, parameter_name, recorded_at, "
            "value, unit, quality) VALUES (%s, %s, %s, %s, %s, %s) "
            "ON CONFLICT DO NOTHING", rows)
        conn.commit()
    return len(rows)

## 4. LLM 接入层

### 4.1 设计原则

1. **一处封装，处处引用**：所有 Agent 都通过 `get_llm()` 拿模型实例，绝不散落各处 `ChatOpenAI(...)`。
2. **温度分级**：分析任务（根因排序、证据抽取）要稳定可复现 → `temperature=0.1`；生成任务（报告、建议文案）要有可读性 → `temperature=0.7`。这是提示词回归测试（第 15 章）的前提。
3. **超时与重试**：vLLM 偶发慢查询，底层 openai client 自带重试（指数退避），上层不再包一层错误重试，避免重试风暴。
4. **Token 用量统计**：成本可算是企业级硬要求（手册第 12 章成本类指标），用回调把每次调用的 prompt/completion tokens 累计起来写入 State。

### 4.2 core/chat_model.py 完整代码

```python
# industryagent_agent/core/chat_model.py
"""LLM 统一封装：OpenAI 兼容接口 + 温度分级 + Token 用量统计回调。"""
import threading
from typing import Any

from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.language_models.chat_models import BaseChatModel
from langchain_core.outputs import LLMResult
from langchain_openai import ChatOpenAI

from industryagent_agent.config import get_settings

settings = get_settings()


class TokenUsageCallback(BaseCallbackHandler):
    """统计每次 LLM 调用的 token 用量。

    线程安全：LangGraph 节点可能在 asyncio 并发中执行，用锁保护累加。
    每个请求创建一个实例传入 invoke，调用方随后读取 total 展示/落库。
    """

    def __init__(self) -> None:
        self.prompt_tokens: int = 0
        self.completion_tokens: int = 0
        self.call_count: int = 0
        self._lock = threading.Lock()

    def on_llm_end(self, response: LLMResult, **kwargs: Any) -> None:
        try:
            usage = (response.llm_output or {}).get("token_usage", {})
            with self._lock:
                self.prompt_tokens += int(usage.get("prompt_tokens", 0))
                self.completion_tokens += int(usage.get("completion_tokens", 0))
                self.call_count += 1
        except (TypeError, ValueError):
            # 部分私有部署网关不返回 token_usage，忽略即可
            pass

    @property
    def total_tokens(self) -> int:
        return self.prompt_tokens + self.completion_tokens


def get_llm(task_type: str = "analysis",
            usage_callback: TokenUsageCallback | None = None,
            **override: Any) -> BaseChatModel:
    """按任务类型获取 LLM 实例。

    Args:
        task_type: "analysis"（温度 0.1，根因/审批判断）或
                   "generation"（温度 0.7，建议文案/8D 报告）。
        usage_callback: Token 统计回调，跨节点累计用量。
        override: 临时覆盖参数，如 max_tokens。

    Returns:
        ChatOpenAI 兼容实例（vLLM / Ollama / OpenAI 均适用）。
    """
    temperature = (
        settings.llm_temperature_analysis
        if task_type == "analysis"
        else settings.llm_temperature_generation
    )
    kwargs: dict[str, Any] = dict(
        model=settings.llm_model,
        base_url=settings.llm_base_url,
        api_key=settings.llm_api_key,
        temperature=temperature,
        timeout=settings.llm_timeout_seconds,
        max_retries=settings.llm_max_retries,
    )
    kwargs.update(override)

    llm = ChatOpenAI(**kwargs)
    if usage_callback is not None:
        llm = llm.with_config(callbacks=[usage_callback])
    return llm
```

## 5. 工具层开发（LangChain @tool）

工具层是智能体的"手和眼"。LLM 决策的上限取决于工具返回事实的质量，**工具写不好，提示词再漂亮也没用**。

### 5.1 工具描述（docstring）写作要点

LLM 选择工具的唯一依据是 docstring 与参数描述。工业场景写 docstring 的五条铁律：

1. **第一句话说清"这个工具查什么数据"**，让 LLM 能做语义路由。不要写"查询数据库"这种废话，要写"查询 TimescaleDB 中设备传感器时序数据的区间统计特征（均值/最大/最小/标准差/超限次数）"。
2. **写清何时该用、何时不该用**：例如"当需要判断某参数近期是否漂移时使用本工具；当需要知道参数与缺陷的关联强度时，应改用知识图谱工具"。负面指引能显著减少工具误用。
3. **参数必须有明确的单位与格式说明**：时间用 ISO 8601；`equipment` 说明示例值 `"ETCH-03"`；`hours` 说明"回看小时数，1-168"。
4. **返回值结构写进 docstring**：LLM 读到"返回 JSON，含 avg/max/min/std/limit_exceed_count 字段"后，能更稳地引用证据字段。
5. **克制**：单个工具只做一件事。不要造一个"全知全能"的大工具——参数越多，LLM 填错概率越高。

下面逐个实现五个工具。所有工具统一返回 `dict`（而非裸字符串），便于第 7 章的证据链把"工具调用 → 返回内容"整体编号存档。

### 5.2 工具层公共设施：tools/db.py（连接池与统一异常处理）

在写第一个工具之前，先解决三个横切问题——**连接复用、.env 读取、异常兜底**。如果每个工具各写各的 `psycopg.connect(...)`，一次根因分析（约 8-12 次工具调用）就要建 8-12 个 TCP 连接；数据库抖动时工具直接抛裸异常，会把整个 LangGraph 图炸掉。`tools/db.py` 一次解决：

```python
# industryagent_agent/tools/db.py
"""工具层公共数据库设施：连接池单例 + Neo4j driver 单例 + 统一异常包装。

设计要点：
1. 连接池模块级单例——LangGraph 同步节点无法拿到 FastAPI 的 app.state，
   故工具层自持池（进程唯一），lru_cache 保证懒加载一次；
2. DSN 全部来自 config.py（其 .env 读取机制见 3.1 节），任何模块不得硬编码；
3. safe_query 把"连接失败/查询失败"转成结构化的 {"status": "error", ...}
   返回给 LLM——工具永不抛裸异常，根因分析流程不因数据库抖动而中断。
"""
from contextlib import contextmanager
from functools import lru_cache
from typing import Any, Iterator

import psycopg
from psycopg_pool import ConnectionPool

from industryagent_agent.config import get_settings
from industryagent_agent.logging_conf import get_logger

logger = get_logger(__name__)


@lru_cache
def _timescale_pool() -> ConnectionPool:
    """TimescaleDB 连接池（进程唯一）。min_size 预热避免首查冷启动。"""
    pool = ConnectionPool(
        get_settings().timescale_dsn,
        min_size=2, max_size=10, open=True,
        kwargs={"autocommit": True},   # 工具层只读查询，autocommit 免去手动提交
    )
    logger.info("TimescaleDB 连接池已创建")
    return pool


@lru_cache
def _pgvector_pool() -> ConnectionPool:
    """pgvector 文档库连接池（进程唯一，RAG 检索用）。"""
    pool = ConnectionPool(
        get_settings().pgvector_dsn,
        min_size=1, max_size=5, open=True,
        kwargs={"autocommit": True},
    )
    logger.info("pgvector 连接池已创建")
    return pool


@lru_cache
def _neo4j_driver():
    """Neo4j driver 单例。driver 本身内置连接池（默认 max 100），全局复用即可。"""
    from neo4j import GraphDatabase
    s = get_settings()
    driver = GraphDatabase.driver(
        s.neo4j_uri, auth=(s.neo4j_user, s.neo4j_password))
    logger.info("Neo4j driver 已创建: %s", s.neo4j_uri)
    return driver


@contextmanager
def ts_conn() -> Iterator[psycopg.Connection]:
    """TimescaleDB 连接上下文：从池借出/归还。用法 `with ts_conn() as conn, conn.cursor() as cur:`"""
    pool = _timescale_pool()
    conn = pool.getconn()
    try:
        yield conn
    finally:
        pool.putconn(conn)


@contextmanager
def rag_conn() -> Iterator[psycopg.Connection]:
    """pgvector 连接上下文：从池借出/归还。"""
    pool = _pgvector_pool()
    conn = pool.getconn()
    try:
        yield conn
    finally:
        pool.putconn(conn)


def neo4j_session():
    """Neo4j 会话上下文。用法 `with neo4j_session() as session:`"""
    return _neo4j_driver().session()


def safe_query(tool_name: str, cur_factory, sql: str,
               params: dict | tuple | None = None) -> list[dict[str, Any]] | dict:
    """统一查询入口：执行 SQL 并把行转 dict；任何异常转为结构化 error 返回。

    Args:
        tool_name: 调用方工具名（打日志定位用）。
        cur_factory: 上下文管理器，产出 cursor（传 ts_conn 或 rag_conn 的用法见下）。
        sql / params: SQL 与参数。

    Returns:
        行列表（dict）；异常时返回 {"status": "error", "message": ...}。
        调用方应先判 `isinstance(result, dict) and result.get("status") == "error"`。
    """
    try:
        with cur_factory() as conn, conn.cursor() as cur:
            cur.execute(sql, params)
            if cur.description is None:      # 非 SELECT（理论上工具层不出现）
                return []
            cols = [d.name for d in cur.description]
            return [dict(zip(cols, row)) for row in cur.fetchall()]
    except psycopg.Error as e:
        logger.error("工具 %s 查询失败: %s | sql=%s", tool_name, e, sql[:120])
        return {"status": "error",
                "message": f"数据库查询失败（{type(e).__name__}），请稍后重试或检查参数"}
    except Exception as e:  # noqa: BLE001
        logger.exception("工具 %s 未预期异常", tool_name)
        return {"status": "error", "message": f"未预期错误：{e}"}


def is_error(result: Any) -> bool:
    """判断 safe_query 返回值是否为错误结构。"""
    return isinstance(result, dict) and result.get("status") == "error"


def equipment_name_to_id(equipment: str) -> int | None:
    """设备编号（如 ETCH-03）→ equipments.id。查不到返回 None。"""
    rows = safe_query(
        "equipment_name_to_id", ts_conn,
        "SELECT id FROM equipments WHERE code = %s", (equipment,))
    if is_error(rows) or not rows:
        return None
    return int(rows[0]["id"])
```

要点讲解：

- **为什么工具层自己持池而不用 `app.state`**：LangGraph 的节点是同步函数（在 `graph.invoke` 的工作线程里跑），拿不到 asyncio 的 `app.state`；模块级 `lru_cache` 单例是同步代码最简单的"进程唯一"方案。
- **`safe_query` 的异常哲学**：数据库故障时，工具返回 `{"status": "error", "message": ...}` 而非抛异常——LLM 读到 error 状态会改用其他证据路（提示词第 7.3 节有"证据不足如实说明"约束），整个分析降级但不断链。**这条降级路径与第 5.6 节 RAG 的 embedding 降级一脉相承。**
- **Neo4j 用 driver 单例**：`GraphDatabase.driver()` 创建即含连接池，全局一个即可；每次查询新建 driver 是 FAQ Q4 点名的反模式。

> **验证**：`python -c "from industryagent_agent.tools.db import ts_conn, safe_query, is_error; r = safe_query('t', ts_conn, 'SELECT 1 AS ok'); print(r)"` 应输出 `[{'ok': 1}]`；把 `.env` 的 `TIMESCALE_DSN` 端口改成错误值再跑一次，应返回 `{'status': 'error', ...}` 而非堆栈。（测完改回。）

### 5.3 tools/sensors.py：TimescaleDB 传感器查询

```python
# industryagent_agent/tools/sensors.py
"""传感器时序查询工具：区间原始数据 + 统计特征。数据源：TimescaleDB。

表结构（与数据库教程一致）：sensor_readings(equipment_id, parameter_name,
recorded_at, value, unit, quality)、lot_batches(lot_no, actual_yield, ...)。
工具入参保持"设备编号字符串"（如 ETCH-03）——LLM 填参更不易错；
内部经 equipments.code 做 名称→ID 映射。
"""
from datetime import datetime, timedelta, timezone

from langchain_core.tools import tool

from industryagent_agent.logging_conf import get_logger
from industryagent_agent.tools.db import (
    equipment_name_to_id, is_error, safe_query, ts_conn,
)

logger = get_logger(__name__)


@tool
def query_sensor_stats(equipment: str, parameter: str, hours: int = 24,
                       process_step: str = "") -> dict:
    """查询 TimescaleDB 中指定设备/参数在近 N 小时的传感器统计特征。

    用途：判断某参数近期是否发生漂移、波动加剧或超限。当根因分析需要
    "某设备某参数近期表现如何"的事实时使用本工具。
    不适用：查询参数与缺陷的关联关系（请用知识图谱工具）；查询工艺文档（请用RAG检索工具）。

    Args:
        equipment: 设备编号，如 "ETCH-03"。
        parameter: 参数名，如 "chamber_temp"、"rf_power"、"pressure"。
        hours: 回看的小时数，1-168，默认 24。
        process_step: 工序名（可选），如 "etch"；为空则不按工序过滤。

    Returns:
        dict: {"status", "equipment", "parameter", "window_hours", "sample_count",
               "stats": {"avg","min","max","std","last_value"},
               "limit_exceed_count": 超出规格限的采样点数,
               "hourly_avg": 最近各小时的均值列表}
    """
    eid = equipment_name_to_id(equipment)
    if eid is None:
        return {"status": "no_data", "equipment": equipment, "parameter": parameter,
                "message": "设备编号不存在（equipments 表无此 code），请检查拼写"}

    since = datetime.now(timezone.utc) - timedelta(hours=hours)
    base_sql = """
        SELECT r.recorded_at AS time, r.value, r.unit
        FROM sensor_readings r
        JOIN equipments e ON e.id = r.equipment_id
        WHERE r.equipment_id = %(eid)s
          AND r.parameter_name = %(parameter)s
          AND r.recorded_at >= %(since)s
          AND r.quality = 'good'
    """
    params: dict = {"eid": eid, "parameter": parameter, "since": since}
    if process_step:
        base_sql += " AND e.stage = %(process_step)s"
        params["process_step"] = process_step
    base_sql += " ORDER BY r.recorded_at ASC LIMIT 20000;"

    rows = safe_query("query_sensor_stats", ts_conn, base_sql, params)
    if is_error(rows):
        return rows
    if not rows:
        return {"status": "no_data", "equipment": equipment, "parameter": parameter,
                "message": "查询范围内没有数据，请检查设备/参数名拼写"}

    values = [float(r["value"]) for r in rows]
    n = len(values)
    avg = sum(values) / n
    std = (sum((v - avg) ** 2 for v in values) / n) ** 0.5
    # 规格限简化处理：用历史基线的 ±3σ 之外计数（生产中规格限应来自 recipe_spec 表）
    baseline_avg, baseline_std = _get_baseline(eid, parameter)
    exceed = sum(1 for v in values
                 if abs(v - baseline_avg) > 3 * baseline_std) if baseline_std else 0

    # 最近 12 小时逐小时均值，供观察漂移趋势
    hourly: dict[str, list[float]] = {}
    for r in rows:
        hourly.setdefault(r["time"].strftime("%Y-%m-%dT%H:00"), []).append(float(r["value"]))
    hourly_avg = [{"hour": k, "avg": sum(v) / len(v)} for k, v in sorted(hourly.items())]

    result = {
        "status": "ok",
        "equipment": equipment,
        "parameter": parameter,
        "window_hours": hours,
        "sample_count": n,
        "unit": rows[-1]["unit"],
        "stats": {
            "avg": round(avg, 4), "min": min(values), "max": max(values),
            "std": round(std, 4), "last_value": values[-1],
            "baseline_avg": baseline_avg, "baseline_std": baseline_std,
        },
        "limit_exceed_count": exceed,
        "hourly_avg": hourly_avg[-12:],
    }
    logger.info("query_sensor_stats %s/%s hours=%s n=%s exceed=%s",
                equipment, parameter, hours, n, exceed)
    return result


def _get_baseline(equipment_id: int, parameter: str) -> tuple[float, float]:
    """取该参数 7 天历史基线（均值/标准差），作为规格限的代理。"""
    since = datetime.now(timezone.utc) - timedelta(days=7)
    sql = """
        SELECT avg(value), stddev_samp(value)
        FROM sensor_readings
        WHERE equipment_id = %s AND parameter_name = %s
          AND recorded_at < %s AND quality = 'good'
    """
    rows = safe_query("_get_baseline", ts_conn, sql, (equipment_id, parameter, since))
    if is_error(rows) or not rows:
        return 0.0, 0.0
    row = rows[0]
    if row["avg"] is None or row["stddev_samp"] in (None, 0):
        return 0.0, 0.0
    return float(row["avg"]), float(row["stddev_samp"])


@tool
def query_lot_yield(equipment: str = "", days: int = 7) -> dict:
    """查询近 N 天各设备/各批次的良率记录，用于定位"良率下降从哪台设备开始"。

    用途：根因分析中缩小嫌疑设备范围——对比不同设备同工序的批次良率差异。

    Args:
        equipment: 设备编号（可选，为空则查全部设备）。
        days: 回看天数，1-30，默认 7。

    Returns:
        dict: {"status", "lots": [{"lot_no","equipment","actual_yield","start_time"}],
               "yield_by_equipment": 各设备平均良率（0-1 小数）}
    """
    since = datetime.now(timezone.utc) - timedelta(days=days)
    sql = """
        SELECT l.lot_no, e.code AS equipment, e.stage AS process_step,
               l.actual_yield, l.start_time
        FROM lot_batches l
        JOIN equipments e ON e.id = l.current_equipment_id
        WHERE l.start_time >= %s AND l.actual_yield IS NOT NULL
    """
    params: list = [since]
    if equipment:
        sql += " AND e.code = %s"
        params.append(equipment)
    sql += " ORDER BY l.start_time ASC LIMIT 500;"

    rows = safe_query("query_lot_yield", ts_conn, sql, tuple(params))
    if is_error(rows):
        return rows
    if not rows:
        return {"status": "no_data", "message": f"近 {days} 天无批次良率数据"}

    by_equip: dict[str, list[float]] = {}
    for r in rows:
        by_equip.setdefault(r["equipment"], []).append(float(r["actual_yield"]))
    return {
        "status": "ok",
        "lots": rows,
        "yield_by_equipment": {k: round(sum(v) / len(v), 4) for k, v in by_equip.items()},
        "query_params": {"equipment": equipment or "ALL", "days": days},
    }
```

### 5.4 tools/knowledge_graph.py：Neo4j 工艺图谱查询

```python
# industryagent_agent/tools/knowledge_graph.py
"""知识图谱查询工具：参数-缺陷关联强度、设备-工序-缺陷路径。数据源：Neo4j。"""
from typing import Any

from langchain_core.tools import tool

from industryagent_agent.logging_conf import get_logger
from industryagent_agent.tools.db import neo4j_session

logger = get_logger(__name__)


def _run_cypher(query: str, params: dict | None = None) -> list[dict[str, Any]] | dict:
    """在全局 driver 单例的 session 中执行 Cypher，把记录转成 dict 列表。

    异常兜底：连接抖动（ServiceUnavailable 等）时返回结构化 error，
    由各工具直接透传给 LLM——根因分析走"图谱证据缺失"降级路径。
    """
    try:
        with neo4j_session() as session:
            result = session.run(query, params or {})
            return [dict(record) for record in result]
    except Exception as e:  # noqa: BLE001  neo4j.DriverError 等
        logger.error("Cypher 查询失败: %s | query=%s", e, query[:120].replace("\n", " "))
        return {"status": "error",
                "message": f"知识图谱查询失败（{type(e).__name__}），"
                           f"本次分析将缺少图谱证据"}


@tool
def query_parameter_defect_association(defect_type: str, top_n: int = 5) -> dict:
    """在工艺知识图谱中查询与某类缺陷有关联的工艺参数及其关联强度（Top-N）。

    用途：根因分析中回答"这类缺陷历史上与哪些参数相关、强度如何"。
    不适用：查参数近期实测值（请用传感器统计工具）。

    Args:
        defect_type: 缺陷类型关键词，如 "微桥接"、"颗粒"、"厚度偏差"。
        top_n: 返回前 N 个关联参数，默认 5。

    Returns:
        dict: {"status", "defect", "associations": [
            {"parameter","desc","strength","evidence_note"}], "paths": 关联路径描述}
    """
    cypher = """
    MATCH (p:Parameter)-[r:AFFECTS]->(d:Defect)
    WHERE d.name CONTAINS $defect OR d.type CONTAINS $defect
    RETURN p.name AS parameter, p.desc AS desc,
           r.strength AS strength, d.name AS defect_name
    ORDER BY strength DESC LIMIT $top_n
    """
    rows = _run_cypher(cypher, {"defect": defect_type, "top_n": top_n})
    if isinstance(rows, dict):          # error 结构直接透传（降级）
        return rows
    if not rows:
        return {"status": "no_data", "defect": defect_type,
                "message": "图谱中未找到该缺陷类型，请确认缺陷名称"}
    return {
        "status": "ok",
        "defect": rows[0]["defect_name"],
        "associations": [
            {"parameter": r["parameter"], "desc": r["desc"],
             "strength": float(r["strength"]),
             "evidence_note": f"图谱边AFFECTS强度={r['strength']}"}
            for r in rows
        ],
    }


@tool
def query_defect_equipment(defect_type: str, top_n: int = 5) -> dict:
    """查询某类缺陷与哪些设备/工序存在关联路径（缺陷←工序←设备），按路径长度排序。

    用途：把"缺陷"定位到"嫌疑设备"。路径越短、边强度越高，嫌疑越大。

    Args:
        defect_type: 缺陷类型关键词，如 "微桥接"。
        top_n: 返回前 N 条设备关联路径，默认 5。

    Returns:
        dict: {"status", "defect", "equipments": [
            {"equipment","equipment_type","process_step","path","hops"}]}
    """
    cypher = """
    MATCH path = (e:Equipment)-[:EXECUTES]->(s:ProcessStep)-[:HAS_DEFECT]->(d:Defect)
    WHERE d.name CONTAINS $defect OR d.type CONTAINS $defect
    RETURN e.name AS equipment, e.type AS equipment_type,
           s.name AS process_step,
           reduce(h = 0, x IN relationships(path) | h + 1) AS hops
    ORDER BY hops ASC LIMIT $top_n
    """
    rows = _run_cypher(cypher, {"defect": defect_type, "top_n": top_n})
    if isinstance(rows, dict):
        return rows
    if not rows:
        return {"status": "no_data", "defect": defect_type,
                "message": "图谱中未找到该缺陷类型的设备关联路径"}
    return {
        "status": "ok",
        "defect": defect_type,
        "equipments": [
            {"equipment": r["equipment"], "equipment_type": r["equipment_type"],
             "process_step": r["process_step"], "hops": r["hops"],
             "path": f"{r['equipment']} -EXECUTES-> {r['process_step']} -HAS_DEFECT-> {defect_type}"}
            for r in rows
        ],
    }


@tool
def query_parameter_process_chain(parameter: str) -> dict:
    """查询某工艺参数测量于哪些设备、影响哪些工序与缺陷，形成完整关联链。

    用途：评估某参数异常的影响面（会波及哪些工序/缺陷），供建议Agent估算影响范围。

    Args:
        parameter: 参数名，如 "chamber_temp"。

    Returns:
        dict: {"status", "parameter", "measured_on": [...], "affects": [...]}
    """
    cypher_measured = """
    MATCH (p:Parameter {name: $parameter})-[:MEASURED_ON]->(e:Equipment)
    RETURN e.name AS equipment
    """
    cypher_affects = """
    MATCH (p:Parameter {name: $parameter})-[r:AFFECTS]->(d:Defect)
    RETURN d.name AS defect, r.strength AS strength
    ORDER BY strength DESC
    """
    measured = _run_cypher(cypher_measured, {"parameter": parameter})
    affects = _run_cypher(cypher_affects, {"parameter": parameter})
    if isinstance(measured, dict):
        return measured
    if isinstance(affects, dict):
        return affects
    return {
        "status": "ok",
        "parameter": parameter,
        "measured_on": [m["equipment"] for m in measured],
        "affects": [{"defect": a["defect"], "strength": float(a["strength"])} for a in affects],
    }
```

### 5.5 tools/rag_search.py：pgvector 工艺文档检索

```python
# industryagent_agent/tools/rag_search.py
"""RAG 检索工具：pgvector 语义相似检索工艺文档切片/历史案例/8D报告。
数据源：doc_chunks 表（数据库教程 5.2 节，1536 维 embedding）。
embedding 由向量服务（OpenAI 兼容 /v1/embeddings）生成后离线写入。
"""
import json

import httpx
from langchain_core.tools import tool

from industryagent_agent.config import get_settings
from industryagent_agent.logging_conf import get_logger
from industryagent_agent.tools.db import is_error, rag_conn, safe_query

logger = get_logger(__name__)


def _embed(text: str) -> list[float]:
    """调用向量服务生成 embedding（OpenAI 兼容 /v1/embeddings 或自建 bge 服务）。"""
    s = get_settings()
    resp = httpx.post(
        s.embedding_base_url.rstrip("/") + "/v1/embeddings",
        json={"model": s.embedding_model, "input": text},
        headers={"Authorization": f"Bearer {s.embedding_api_key or 'EMPTY'}"},
        timeout=30.0,
    )
    resp.raise_for_status()
    return resp.json()["data"][0]["embedding"]


@tool
def rag_search_process_docs(query: str, top_k: int = 3) -> dict:
    """在工艺文档库（含 SOP、历史故障案例、过往 8D 报告）中做语义相似检索。

    用途：根因分析时查找"历史相似案例如何处理"；建议Agent引用工艺规范的参数规格。
    不适用：查实时传感器数据（请用传感器工具）；查参数-缺陷关联强度（请用图谱工具）。

    Args:
        query: 自然语言查询，如 "刻蚀腔体温度漂移导致微桥接缺陷的处理方法"。
        top_k: 返回最相似的文档切片数，默认 3。

    Returns:
        dict: {"status", "query", "docs": [{"doc_id","chunk_index","title","content","similarity"}]}
    """
    try:
        query_vec = _embed(query)
    except Exception as e:  # noqa: BLE001
        logger.warning("embedding 服务不可用，降级为关键词检索: %s", e)
        return _keyword_fallback(query, top_k)

    sql = """
    SELECT doc_id, chunk_index, title, content,
           1 - (embedding <=> %s::vector) AS similarity
    FROM doc_chunks
    ORDER BY embedding <=> %s::vector
    LIMIT %s;
    """
    rows = safe_query("rag_search_process_docs", rag_conn, sql,
                      (json.dumps(query_vec), json.dumps(query_vec), top_k))
    if is_error(rows):
        return rows
    return {
        "status": "ok",
        "query": query,
        "docs": [
            {"doc_id": r["doc_id"], "chunk_index": r["chunk_index"],
             "title": r["title"],
             "content": (r["content"] or "")[:500],  # 截断，防上下文爆炸
             "similarity": round(float(r["similarity"]), 4)}
            for r in rows
        ],
    }


def _keyword_fallback(query: str, top_k: int) -> dict:
    """embedding 服务故障时的降级方案：ILIKE 关键词检索，保证根因分析不中断。"""
    sql = """
    SELECT doc_id, chunk_index, title, content, 0.0 AS similarity
    FROM doc_chunks
    WHERE title ILIKE %s OR content ILIKE %s
    LIMIT %s;
    """
    like = f"%{query[:32]}%"
    rows = safe_query("_keyword_fallback", rag_conn, sql, (like, like, top_k))
    if is_error(rows):
        return rows
    return {"status": "degraded_keyword_search", "query": query,
            "docs": [{"doc_id": r["doc_id"], "chunk_index": r["chunk_index"],
                      "title": r["title"],
                      "content": (r["content"] or "")[:500],
                      "similarity": r["similarity"]} for r in rows]}
```

### 5.6 tools/causality.py：DoWhy 因果效应估计

相关性不等于因果。传感器工具告诉我们"温度和良率同时异常"，图谱工具告诉我们"历史上有关联"，但只有因果分析能回答"**如果干预温度，良率会变多少**"——这是建议 Agent 决定调参方向的依据。

```python
# industryagent_agent/tools/causality.py
"""DoWhy 因果分析工具：估计工艺参数对良率的因果效应（干预效果）。"""
import pandas as pd
from langchain_core.tools import tool

from industryagent_agent.logging_conf import get_logger
from industryagent_agent.tools.db import is_error, safe_query, ts_conn

logger = get_logger(__name__)


def _load_analysis_dataframe(parameter: str, days: int) -> pd.DataFrame:
    """把批次级数据拼成因果分析 DataFrame：处理变量=参数均值，结果=良率(百分点)。

    lot_batches.actual_yield 为 0-1 小数，此处 ×100 转为百分点口径，
    与提示词中"良率变化百分点"的语义保持一致。
    """
    from datetime import datetime, timedelta, timezone
    since = datetime.now(timezone.utc) - timedelta(days=days)
    sql = """
    SELECT l.lot_no, e.code AS equipment, l.actual_yield * 100 AS yield_pct,
           avg(s.value) AS param_avg
    FROM lot_batches l
    JOIN equipments e ON e.id = l.current_equipment_id
    JOIN sensor_readings s
      ON s.equipment_id = l.current_equipment_id
     AND s.recorded_at BETWEEN l.start_time - interval '2 hours' AND l.start_time
     AND s.parameter_name = %(parameter)s AND s.quality = 'good'
    WHERE l.start_time >= %(since)s AND l.actual_yield IS NOT NULL
    GROUP BY l.lot_no, e.code, l.actual_yield
    ORDER BY l.start_time;
    """
    rows = safe_query("_load_analysis_dataframe", ts_conn, sql,
                      {"parameter": parameter, "since": since})
    if is_error(rows):
        return pd.DataFrame()   # 查询失败 → 空 df → 上层走 insufficient_data 分支
    return pd.DataFrame(rows)


@tool
def estimate_causal_effect(parameter: str, days: int = 30,
                           common_causes: str = "") -> dict:
    """用 DoWhy 估计"工艺参数 → 批次良率"的因果效应（基于后门调整+线性回归）。

    用途：区分"相关"与"因果"。当根因分析需要回答"把该参数调回目标值，
    良率预计能恢复多少"时使用本工具。
    不适用：参数当前的实时状态（请用传感器工具）。

    Args:
        parameter: 待分析的参数名，如 "chamber_temp"。
        days: 分析窗口天数，7-90，默认 30。
        common_causes: 逗号分隔的混杂变量列名（可选）。留空时自动选择
                       其余批次级协变量（如设备编号不参与，避免共线性）。

    Returns:
        dict: {"status", "parameter", "effect_value": 良率百分点变化/单位参数,
               "direction": "negative|positive|uncertain",
               "confidence": p 值, "n_samples", "refutation": 稳健性检验结论}
    """
    df = _load_analysis_dataframe(parameter, days)
    if len(df) < 30:
        return {"status": "insufficient_data", "parameter": parameter,
                "n_samples": int(len(df)),
                "message": f"样本量 {len(df)} < 30，不足以做因果估计，请扩大 days"}

    df = df.dropna(subset=["yield_pct", "param_avg"])
    df = df.rename(columns={"param_avg": "treatment", "yield_pct": "outcome"})

    # 混杂变量：简单而稳妥的做法是用时间趋势项作代理（生产中可替换为设备批次协变量）
    common_causes_list = [c.strip() for c in common_causes.split(",") if c.strip()]

    from dowhy import CausalModel
    model = CausalModel(
        data=df,
        treatment="treatment",
        outcome="outcome",
        common_causes=common_causes_list or None,
    )
    estimand = model.identify_effect(proceed_when_unidentifiable=True)
    estimate = model.estimate_effect(estimand, method_name="backdoor.linear_regression")

    effect = float(estimate.value)
    # 稳健性检验：随机混杂替换，若效应翻转则标记不可信
    try:
        refute = model.refute_estimate(estimand, estimate,
                                       method_name="random_common_cause")
        refutation = str(refute.new_effect)
        stable = refute.refutation_result is None or True
    except Exception as e:  # noqa: BLE001
        refutation = f"refutation failed: {e}"
        stable = False

    direction = ("negative" if effect < 0
                 else "positive" if effect > 0 else "uncertain")
    return {
        "status": "ok",
        "parameter": parameter,
        "effect_value": round(effect, 6),
        "interpretation": (
            f"参数每升高 1 个单位，良率约变化 {abs(effect):.4f} 个百分点"
            f"（{'下降' if effect < 0 else '上升'}）"),
        "direction": direction,
        "n_samples": int(len(df)),
        "refutation": refutation,
        "refutation_stable": bool(stable),
    }
```

> **验证**：`python -c "from industryagent_agent.tools.causality import estimate_causal_effect as t; import json; print(json.dumps(t.invoke({'parameter':'chamber_temp','days':14}), ensure_ascii=False, indent=2))"`。种子数据按"+2σ（即 +1.0℃）→ 良率降约 2pct"的机理生成，故 `effect_value` 应显著为负（约 -2，即每偏 1℃ 良率降 2pct），`direction=negative`。这一步是第 13 章合成数据"已知注入根因"的基础。

### 5.7 tools/data_stats.py：缺陷数据统计（SECOM 式相关性）

```python
# industryagent_agent/tools/data_stats.py
"""缺陷数据统计工具：批次缺陷率统计、参数-缺陷相关性（SECOM 式特征分析）。"""
import math

import numpy as np
import pandas as pd
from langchain_core.tools import tool

from industryagent_agent.logging_conf import get_logger
from industryagent_agent.tools.db import is_error, safe_query, ts_conn

logger = get_logger(__name__)


@tool
def defect_correlation(days: int = 14) -> dict:
    """统计近 N 天各参数与批次缺陷率的相关性排序（皮尔逊相关，降序）。

    用途：快速筛出"与缺陷率线性相关最强"的参数候选，作为根因 Agent 的
    初步候选清单，再用图谱与因果工具交叉验证。
    注意：相关性不等于因果，本工具结论必须与图谱/因果证据联合使用。

    Args:
        days: 统计窗口天数，1-60，默认 14。

    Returns:
        dict: {"status", "n_lots", "correlations": [
            {"parameter","pearson_r","abs_r"}], "defect_rate_by_equipment": {...}}
    """
    from datetime import datetime, timedelta, timezone
    since = datetime.now(timezone.utc) - timedelta(days=days)

    lot_sql = """
    SELECT l.lot_no, e.code AS equipment, l.actual_yield * 100 AS yield_pct
    FROM lot_batches l
    JOIN equipments e ON e.id = l.current_equipment_id
    WHERE l.start_time >= %s AND l.actual_yield IS NOT NULL
    ORDER BY l.start_time;
    """
    lots_rows = safe_query("defect_correlation", ts_conn, lot_sql, (since,))
    if is_error(lots_rows):
        return lots_rows
    lots = pd.DataFrame(lots_rows)
    if lots.empty:
        return {"status": "no_data", "message": f"近 {days} 天无批次数据"}

    param_sql = """
    SELECT e.code AS equipment, s.parameter_name AS parameter,
           avg(s.value) AS param_avg
    FROM sensor_readings s
    JOIN equipments e ON e.id = s.equipment_id
    WHERE s.recorded_at >= %s AND s.quality = 'good'
    GROUP BY e.code, s.parameter_name;
    """
    param_rows = safe_query("defect_correlation", ts_conn, param_sql, (since,))
    if is_error(param_rows):
        return param_rows
    params_df = pd.DataFrame(param_rows)

    lots["defect_rate"] = 1.0 - lots["yield_pct"] / 100.0
    merged = lots.merge(params_df, on="equipment", how="inner")

    correlations: list[dict] = []
    for parameter, group in merged.groupby("parameter"):
        if len(group) < 10:
            continue
        r = float(np.corrcoef(group["param_avg"].astype(float),
                              group["defect_rate"].astype(float))[0, 1])
        if not math.isnan(r):
            correlations.append({"parameter": parameter, "pearson_r": round(r, 4),
                                 "abs_r": round(abs(r), 4)})
    correlations.sort(key=lambda x: x["abs_r"], reverse=True)

    by_equip = lots.groupby("equipment")["defect_rate"].mean().round(4)
    return {
        "status": "ok",
        "n_lots": int(len(lots)),
        "window_days": days,
        "correlations": correlations,
        "defect_rate_by_equipment": by_equip.to_dict(),
    }
```

## 6. 监控 Agent：FDC 异常检测

监控 Agent 是闭环的起点。它不使用 LLM——**异常检测是确定性计算问题，用规则+统计模型比 LLM 更快、更稳、更便宜**（端到端延迟 < 5 分钟的指标从源头就要求低开销）。这里体现"Agent ≠ LLM"的重要理念：一个 Agent 节点可以是纯代码，LLM 只在需要语义推理的节点出场。

技术组合（FDC 故障检测的经典三件套）：

1. **SPC 控制图 3σ**：检测均值突变（尖峰、阶跃）。
2. **EWMA（指数加权移动平均）**：检测缓慢漂移——3σ 对"温水煮青蛙"式漂移不敏感，EWMA 用历史加权放大累积偏移信号。
3. **孤立森林（Isolation Forest）**：多参数联合异常（单参数正常但组合异常，如温度和压力的比值异常）。

### 6.1 异常事件 Schema（agents/schemas.py，全章共用）

先定义全局数据契约。所有 Agent 的输入输出都用 Pydantic 模型钉死，这是"结构化输出 + 可测试"的基础：

```python
# industryagent_agent/agents/schemas.py
"""全局数据契约：异常事件、嫌疑、证据、建议、审批的 Pydantic 模型。"""
from datetime import datetime
from enum import Enum
from typing import Any, Optional

from pydantic import BaseModel, Field


class Severity(str, Enum):
    low = "low"
    medium = "medium"
    high = "high"


class AnomalyEvent(BaseModel):
    """监控 Agent 的输出：一次 FDC 异常事件。"""
    event_id: str = Field(..., description="事件唯一ID，如 EVT-20261015-0001")
    equipment: str = Field(..., description="设备编号，如 ETCH-03")
    process_step: str = Field(..., description="工序，如 etch")
    parameters: list[str] = Field(..., description="触发异常的参数列表")
    severity: Severity = Field(..., description="严重程度")
    detected_at: datetime = Field(..., description="检测时间")
    detector: str = Field("spc_ewma_if", description="检测器：spc_3sigma/ewma/isolation_forest")
    detail: dict[str, Any] = Field(default_factory=dict,
                                   description="各检测器明细：均值/标准差/EWMA统计量/IF分数")

### 6.2 监控核心算法（agents/monitor_agent.py）

```python
# industryagent_agent/agents/monitor_agent.py
"""监控 Agent：SPC 3σ + EWMA + 孤立森林三重检测，产出 AnomalyEvent。"""
import uuid
from datetime import datetime, timedelta, timezone

import numpy as np
from sklearn.ensemble import IsolationForest

from industryagent_agent.agents.schemas import AnomalyEvent, Severity
from industryagent_agent.logging_conf import get_logger

logger = get_logger(__name__)


# ---------- 1) SPC 3σ ----------
def spc_3sigma(values: np.ndarray,
               baseline_mean: float, baseline_std: float,
               k: float = 3.0) -> dict:
    """SPC 休哈特控制图：超出 baseline ± k·σ 判为失控点。

    Args:
        values: 待检测的采样序列。
        baseline_mean / baseline_std: 历史基线（训练期）的均值/标准差。
        k: 控制限倍数，工业默认 3。

    Returns:
        dict: {"violations": 失控点数, "ucl"/"lcl": 上下控制限, "violation_ratio"}
    """
    ucl = baseline_mean + k * baseline_std
    lcl = baseline_mean - k * baseline_std
    violations = int(np.sum((values > ucl) | (values < lcl)))
    return {
        "ucl": round(ucl, 4), "lcl": round(lcl, 4),
        "violations": violations,
        "violation_ratio": round(violations / len(values), 4) if len(values) else 0.0,
    }


# ---------- 2) EWMA ----------
def ewma_detect(values: np.ndarray, baseline_mean: float, baseline_std: float,
                lam: float = 0.2, k: float = 2.7) -> dict:
    """EWMA 控制图：对缓慢漂移敏感。

    z_t = λ·x_t + (1-λ)·z_{t-1}，控制限 ± k·σ·sqrt(λ/(2-λ))。
    当 |z_t - baseline_mean| 超出控制限即报警。λ 越小对漂移越灵敏（0.1-0.3 常用）。

    Returns:
        dict: {"z_last": 最新EWMA统计量, "limit": 控制限, "triggered": 是否越限}
    """
    z = baseline_mean  # z_0 从基线均值起步
    for x in values:
        z = lam * float(x) + (1 - lam) * z
    limit = k * baseline_std * np.sqrt(lam / (2 - lam))
    triggered = abs(z - baseline_mean) > limit
    return {
        "z_last": round(float(z), 4),
        "limit": round(float(limit), 4),
        "deviation": round(float(abs(z - baseline_mean)), 4),
        "triggered": bool(triggered),
    }


# ---------- 3) 孤立森林 ----------
class IsolationForestDetector:
    """孤立森林检测器：多参数联合异常。

    用法：
        offline: fit(normal_window) 用正常期数据训练；
        online:  score(current_window) 返回异常分数与判定。
    contamination 设 0.01：生产中异常占比低，宁少误报。
    """

    def __init__(self, contamination: float = 0.01, random_state: int = 42) -> None:
        self.model = IsolationForest(
            n_estimators=200,
            contamination=contamination,
            random_state=random_state,
        )
        self._fitted = False

    def fit(self, normal_matrix: np.ndarray) -> None:
        """用"确认正常"的历史窗口训练（shape = [n_samples, n_parameters]）。"""
        self.model.fit(normal_matrix)
        self._fitted = True
        logger.info("孤立森林训练完成: n_samples=%s n_features=%s",
                    *normal_matrix.shape)

    def score(self, current_matrix: np.ndarray) -> dict:
        """在线推理：返回每个参数的异常得分与整体判定。

        Returns:
            dict: {"is_anomaly", "anomaly_score": 越接近-1越异常,
                   "n_anomaly_points", "per_param_score": 每参数均分}
        """
        if not self._fitted:
            raise RuntimeError("孤立森林未训练，请先调用 fit()")
        scores = self.model.decision_function(current_matrix)   # (-1, 1)，越小越异常
        preds = self.model.predict(current_matrix)               # 1 正常 / -1 异常
        n_anom = int(np.sum(preds == -1))
        return {
            "is_anomaly": n_anom > 0,
            "anomaly_score": round(float(np.mean(scores)), 4),
            "n_anomaly_points": n_anom,
            "per_param_score": {
                str(i): round(float(np.mean(current_matrix[:, i] - scores * 0)), 4)
                for i in range(current_matrix.shape[1])
            },
        }


# ---------- 监控主入口 ----------
def detect_anomaly(equipment: str, process_step: str,
                   parameters: list[str],
                   fetch_window: "callable" = None) -> AnomalyEvent | None:
    """监控主流程：对每个参数依次跑 SPC + EWMA，多参数联合跑孤立森林。

    Args:
        equipment / process_step: 目标设备与工序。
        parameters: 监控参数清单，如 ["chamber_temp", "rf_power", "pressure"]。
        fetch_window: 数据获取函数 (equipment, parameter, hours) -> (values, base_mean, base_std)。
                      便于测试时注入 mock；默认用 tools.sensors 查询。

    Returns:
        AnomalyEvent 或 None（无异常）。任一检测器触发即生成事件，severity 按触发数量分级。
    """
    if fetch_window is None:
        fetch_window = _default_fetch_window

    triggered_params: list[str] = []
    detail: dict = {}

    for param in parameters:
        values, base_mean, base_std = fetch_window(equipment, param, hours=8)
        if len(values) < 20:
            continue
        arr = np.asarray(values, dtype=float)
        spc = spc_3sigma(arr, base_mean, base_std)
        ewma = ewma_detect(arr, base_mean, base_std)
        detail[param] = {"spc": spc, "ewma": ewma,
                         "current_mean": round(float(arr.mean()), 4)}
        if spc["violations"] > 0 or ewma["triggered"]:
            triggered_params.append(param)

    severity = Severity.low
    if len(triggered_params) >= 2:
        severity = Severity.high
    elif len(triggered_params) == 1 and detail.get(
            triggered_params[0], {}).get("spc", {}).get("violation_ratio", 0) > 0.1:
        severity = Severity.medium

    if not triggered_params:
        return None

    event = AnomalyEvent(
        event_id=f"EVT-{datetime.now(timezone.utc):%Y%m%d}-{uuid.uuid4().hex[:6].upper()}",
        equipment=equipment,
        process_step=process_step,
        parameters=triggered_params,
        severity=severity,
        detected_at=datetime.now(timezone.utc),
        detail=detail,
    )
    logger.info("监控Agent检出异常: %s severity=%s params=%s",
                event.event_id, severity, triggered_params)
    return event


def _default_fetch_window(equipment: str, parameter: str, hours: int):
    """从 TimescaleDB 拉取近 hours 小时数据 + 7 天基线（连接池复用，见 5.2 节）。"""
    from datetime import timedelta
    from industryagent_agent.tools.db import (
        equipment_name_to_id, is_error, safe_query, ts_conn,
    )

    now = datetime.now(timezone.utc)
    eid = equipment_name_to_id(equipment)
    if eid is None:
        return [], 0.0, 1.0   # 设备不存在 → 空数据，detect_anomaly 会跳过该参数

    rows = safe_query(
        "_default_fetch_window", ts_conn,
        "SELECT value FROM sensor_readings WHERE equipment_id=%s "
        "AND parameter_name=%s AND recorded_at >= %s AND quality='good' "
        "ORDER BY recorded_at",
        (eid, parameter, now - timedelta(hours=hours)))
    values = [float(r["value"]) for r in rows] if not is_error(rows) else []

    base_rows = safe_query(
        "_default_fetch_window", ts_conn,
        "SELECT avg(value) AS m, stddev_samp(value) AS s FROM sensor_readings "
        "WHERE equipment_id=%s AND parameter_name=%s AND recorded_at < %s "
        "AND quality='good'",
        (eid, parameter, now - timedelta(days=7)))
    if is_error(base_rows) or not base_rows or base_rows[0]["m"] is None:
        return values, 0.0, 1.0
    base_mean = float(base_rows[0]["m"])
    base_std = (float(base_rows[0]["s"])
                if base_rows[0]["s"] not in (None, 0) else 1.0)
    return values, base_mean, base_std
```

## 7. 根因 Agent：三路证据的嫌疑排序（核心）

根因 Agent 是整个系统的"大脑"，也是 LLM 价值最大的节点。它的职责一句话：**把监控事件变成一份"有证据链、防幻觉、可审计"的 Top-3 嫌疑清单**。

### 7.1 三路证据设计

| 证据路 | 工具 | 回答的问题 | 性质 |
|---|---|---|---|
| 时序路 | `query_sensor_stats` / `query_lot_yield` | 异常参数当前的实际状态？漂移从何时开始？波及哪些批次？ | 实测事实 |
| 图谱路 | `query_parameter_defect_association` / `query_defect_equipment` | 这类缺陷历史与哪些参数/设备有关联？ | 领域知识 |
| 因果路 | `estimate_causal_effect` / `defect_correlation` | 干预该参数能恢复多少良率？相关还是因果？ | 定量推断 |

三路独立、互相印证：只有一路支持 → 低置信度；三路一致 → 高置信度。这个设计把"LLM 拍脑袋"变成"LLM 做证据综合"。

### 7.2 LangGraph State 定义

State 是贯穿全图的数据总线。根因 Agent 的节点状态用 `TypedDict` 定义（LangGraph 会自动做状态合并）：

```python
# industryagent_agent/agents/root_cause_agent.py（State 部分与全图共用，实际放 graph.py）
"""根因 Agent：证据收集 → LLM 综合排序 → 结构化 Top-3 输出。"""
from typing import Annotated, Any, TypedDict
from datetime import datetime

from industryagent_agent.agents.schemas import (
    AdvicePackage, AnomalyEvent, ApprovalRecord, Evidence,
    RootCauseReport,
)


def append_list(left: list, right: list) -> list:
    """LangGraph reducer：同名 key 的新列表追加而非覆盖（保留跨节点历史）。"""
    return (left or []) + (right or [])


class RCAState(TypedDict, total=False):
    """良率根因分析全流程状态。total=False 允许节点渐进填充字段。"""

    # ---- 输入 ----
    event_id: str
    event: dict                     # AnomalyEvent.model_dump()
    started_at: datetime

    # ---- 根因阶段 ----
    tool_calls_made: Annotated[list[dict], append_list]   # 工具调用流水（含入参/返回/ID）
    evidences: Annotated[list[dict], append_list]          # 证据清单（Evidence.model_dump()）
    root_cause: dict                # RootCauseReport.model_dump()
    root_cause_attempts: int        # 工具收集轮次（防死循环）

    # ---- 建议阶段 ----
    advice: dict                    # AdvicePackage.model_dump()

    # ---- 审批阶段 ----
    approval: dict                  # ApprovalRecord.model_dump()
    escalation_notified: bool

    # ---- 报告阶段 ----
    report_markdown: str

    # ---- 全程 ----
    history: Annotated[list[str], append_list]   # 每节点一行执行摘要（审计用）
    token_usage: dict               # {"prompt_tokens", "completion_tokens", "total_tokens"}
    error: str                      # 节点异常信息（非致命）
```

要点：

- `Annotated[list, append_list]`：LangGraph 的 reducer 机制。多个节点向 `evidences` 追加时不会互相覆盖——这保证了证据链的完整性。
- `total=False`：节点函数只写自己负责的字段，LangGraph 合并进全局 State。
- `tool_calls_made` 记录每次工具调用的完整入参出参——这就是**证据链 ID 的来源**，报告与审计都引用它。

### 7.3 根因分析提示词（完整全文）

提示词放在 `prompts/root_cause.py`，与代码解耦，便于版本化管理和回归测试：

```python
# industryagent_agent/prompts/root_cause.py
"""根因分析提示词：完整全文。修改本文件必须跑第15章的提示词回归测试。"""

ROOT_CAUSE_SYSTEM_PROMPT = """你是一家12英寸晶圆厂（芯联半导体）的资深工艺良率分析工程师，拥有10年刻蚀/沉积/光刻工序的失效分析经验。

# 你的任务
针对给定的 FDC 异常事件，综合"三路证据"输出 Top-3 根因嫌疑，并给出置信度与证据摘要。

# 三路证据及其解读规则
1. 时序证据（工具 query_sensor_stats / query_lot_yield）：参数当前实测状态。
   - 重点关注：avg 相对 baseline_avg 的偏移量、limit_exceed_count（超限点数）、
     hourly_avg 是否呈现单调漂移趋势、某设备批次良率是否显著低于同工序其他设备。
2. 图谱证据（工具 query_parameter_defect_association / query_defect_equipment）：
   领域知识库中参数-缺陷、设备-工序-缺陷的关联强度（strength 0-1）。
   - strength > 0.6 视为强关联，0.3-0.6 为中等，< 0.3 为弱关联。
3. 因果证据（工具 estimate_causal_effect / defect_correlation）：
   - estimate_causal_effect 的 effect_value 表示"参数每偏移1个单位，良率变化百分点"。
     refutation_stable=true 才可作为强证据，否则降级为弱证据。
   - defect_correlation 的 pearson_r 只是相关性，不能单独作为根因结论，
     必须与图谱或因果证据交叉印证。

# 工作流程（严格执行）
第一步：阅读异常事件。对事件中每个触发参数，调用 query_sensor_stats 获取当前状态。
第二步：调用 query_lot_yield 定位良率下降从哪台设备开始。
第三步：对最可疑的 1-2 个参数，调用 query_parameter_defect_association
        （缺陷类型从事件 detail 或批次缺陷描述中获取；若事件未给出缺陷类型，
        用参数名+工序名调用 rag_search_process_docs 查询历史相似案例）。
第四步：对图谱强关联的参数，调用 estimate_causal_effect 验证因果方向与量级。
第五步：综合三路证据，按证据强度排序，输出 Top-3 嫌疑。

# 输出格式（必须严格遵守）
输出 JSON，字段定义如下：
- top3: 嫌疑数组，按置信度降序，最多3个。每个元素：
  - rank: 整数1-3
  - parameter: 嫌疑参数名（必须与工具返回的参数名完全一致，禁止自创参数名）
  - equipment: 嫌疑设备编号（必须来自工具返回值）
  - process_step: 工序名
  - confidence: 0-1 之间的小数，保留两位。评分标准：
      * 三路证据全部指向该参数且方向一致：>= 0.85
      * 两路证据支持、一路缺失：0.6 - 0.8
      * 仅一路证据支持：0.3 - 0.5
  - evidence_refs: 该嫌疑引用的证据ID列表，如 ["E-1", "E-3"]。
      证据ID必须来自【证据清单】中真实存在的 ID，禁止引用不存在的ID。
  - evidence_summary: 100字以内的三路证据综合摘要，必须包含具体数值
      （如"温度偏移+1.8℃，图谱强度0.85，因果效应-1.2pct/℃"），禁止空话。
- overall_analysis: 300字以内，说明排除了哪些嫌疑、为什么，给工程师看。
- has_sufficient_evidence: 布尔值。若任何嫌疑缺少两路以上证据，设为 false。

# 防幻觉硬约束（违反即分析失败）
1. 只允许基于【工具返回的事实】与【证据清单】作结论。禁止使用工具返回之外的
   "常识"、"我记得"、"一般来说"类陈述作为依据。
2. parameter、equipment、process_step 的值必须能在工具返回结果中找到原词。
3. 每条嫌疑的 evidence_refs 必须指向真实证据ID。证据清单之外的引用视为无效。
4. 数值（偏移量、强度、效应值）必须直接来自工具返回值，禁止编造或估算。
5. 如果证据不足，如实把 has_sufficient_evidence 设为 false 并说明缺什么，
   禁止在证据不足时虚高置信度。"""

ROOT_CAUSE_USER_TEMPLATE = """# FDC 异常事件
{event_json}

# 已收集证据清单（ID → 工具返回摘要）
{evidence_block}

# 工具调用历史（可参考，不需要重复已完成的分析）
{tool_history_block}

请继续根因分析。如果证据已充分，直接输出最终 Top-3 JSON；
如果需要补充证据，先说明还需要调用哪个工具、查什么参数。"""
```

提示词写作复盘（这段比代码更重要）：

1. **角色设定具体化**："12英寸晶圆厂、10年失效分析"优于"你是专业工程师"——具体身份约束语言风格与推理深度。
2. **把"三路证据"的解读规则写进提示词**：LLM 不知道 strength 0.6 意味着什么，必须把阈值和评分标准写死。**置信度评分表是防"自信满满地胡说"的关键**。
3. **工作流程分步**：五步流程把开放任务变成准线性任务，减少工具乱调。
4. **防幻觉五条**：其中"参数名必须能在工具返回中原词找到"是可程序化校验的（第 7.5 节实现了该校验），把软约束变成硬约束。
5. **JSON 模式**：配合 `with_structured_output`，schema 即约束。

### 7.4 证据收集节点 + LLM 综合节点

根因 Agent 在图上是"两节点循环"：`collect_evidence`（代码驱动，确定性调用工具）→ `analyze_root_cause`（LLM 综合并判断是否充分）→ 条件边回到 `collect_evidence`（最多 2 轮）。**为什么不全交给 LLM 自主工具循环？** 自主循环在私有模型上工具选择错误率高、不可控；确定性收集+LLM 判断的混合模式既稳又能兜底。

```python
# industryagent_agent/agents/root_cause_agent.py（节点实现部分）
import json
from datetime import datetime, timezone

from industryagent_agent.agents.schemas import Evidence, RootCauseReport
from industryagent_agent.core.chat_model import TokenUsageCallback, get_llm
from industryagent_agent.logging_conf import get_logger
from industryagent_agent.prompts.root_cause import (
    ROOT_CAUSE_SYSTEM_PROMPT, ROOT_CAUSE_USER_TEMPLATE,
)
from industryagent_agent.tools.causality import estimate_causal_effect
from industryagent_agent.tools.data_stats import defect_correlation
from industryagent_agent.tools.knowledge_graph import (
    query_defect_equipment, query_parameter_defect_association,
)
from industryagent_agent.tools.rag_search import rag_search_process_docs
from industryagent_agent.tools.sensors import query_lot_yield, query_sensor_stats

logger = get_logger(__name__)

MAX_EVIDENCE_ROUNDS = 2   # 证据收集最大轮次（防死循环）


def _record_tool_call(state: dict, tool_name: str, args: dict,
                      result: dict) -> dict:
    """统一记录一次工具调用：生成证据ID、追加流水。返回 State 增量。"""
    evidence_id = f"E-{len(state.get('evidences') or []) + 1}"
    new_evidence = Evidence(
        evidence_id=evidence_id,
        source_tool=tool_name,
        content=json.dumps(result, ensure_ascii=False)[:800],  # 摘要截断
        strength=_evidence_strength(tool_name, result),
    ).model_dump()
    return {
        "evidences": [new_evidence],
        "tool_calls_made": [{"tool": tool_name, "args": args,
                             "result_summary": new_evidence["content"],
                             "evidence_id": evidence_id}],
        "history": [f"[root_cause] 调用 {tool_name}({args}) -> {evidence_id}"],
    }


def _evidence_strength(tool_name: str, result: dict) -> float:
    """按工具类型与返回内容粗分证据强度（供建议与报告引用）。"""
    if result.get("status") != "ok":
        return 0.1
    if tool_name == "estimate_causal_effect":
        return 0.9 if result.get("refutation_stable") else 0.5
    if tool_name == "query_parameter_defect_association":
        assoc = result.get("associations") or [{}]
        return min(float(assoc[0].get("strength", 0)) + 0.1, 1.0)
    if tool_name == "query_sensor_stats":
        return 0.8 if result.get("limit_exceed_count", 0) > 0 else 0.5
    return 0.6


def collect_evidence_node(state: dict) -> dict:
    """确定性证据收集节点：按参数清单依次调用工具，不使用 LLM。

    第一轮：时序路（每个触发参数 + 批次良率）。
    第二轮：图谱路 + 因果路（针对第一轮发现的最可疑参数）。
    """
    event = state["event"]
    parameters: list[str] = event.get("parameters") or []
    equipment: str = event.get("equipment")
    attempts: int = state.get("root_cause_attempts", 0)
    updates: dict = {"root_cause_attempts": attempts + 1}

    if attempts == 0:
        # ---- 第一轮：时序路 ----
        for p in parameters:
            result = query_sensor_stats.invoke(
                {"equipment": equipment, "parameter": p, "hours": 48})
            updates.update(_accumulate(state, updates,
                                       "query_sensor_stats",
                                       {"equipment": equipment, "parameter": p},
                                       result))
        lots = query_lot_yield.invoke({"equipment": equipment, "days": 14})
        updates.update(_accumulate(state, updates, "query_lot_yield",
                                   {"equipment": equipment}, lots))
    else:
        # ---- 第二轮：图谱路 + 因果路（针对首个嫌疑参数）----
        top_param = _pick_focus_parameter(state) or parameters[0]
        defect = event.get("detail", {}).get("defect_type", "微桥接")
        assoc = query_parameter_defect_association.invoke(
            {"defect_type": defect, "top_n": 5})
        updates.update(_accumulate(state, updates,
                                   "query_parameter_defect_association",
                                   {"defect_type": defect}, assoc))
        eq_paths = query_defect_equipment.invoke({"defect_type": defect, "top_n": 5})
        updates.update(_accumulate(state, updates, "query_defect_equipment",
                                   {"defect_type": defect}, eq_paths))
        causal = estimate_causal_effect.invoke({"parameter": top_param, "days": 30})
        updates.update(_accumulate(state, updates, "estimate_causal_effect",
                                   {"parameter": top_param}, causal))
        # 若事件未给出缺陷类型，用RAG找历史案例
        if "defect_type" not in event.get("detail", {}):
            rag = rag_search_process_docs.invoke(
                {"query": f"{equipment} {top_param} 异常 良率下降 处理案例", "top_k": 2})
            updates.update(_accumulate(state, updates, "rag_search_process_docs",
                                       {"query": f"{top_param} 异常"}, rag))
    return updates


def _accumulate(state: dict, updates_so_far: dict,
                tool_name: str, args: dict, result: dict) -> dict:
    """合并 _record_tool_call 的增量（考虑本轮已追加的证据数量）。"""
    merged_evidences = (state.get("evidences") or []) \
        + (updates_so_far.get("evidences") or [])
    pseudo = {**state, "evidences": merged_evidences}
    return _record_tool_call(pseudo, tool_name, args, result)


def _pick_focus_parameter(state: dict) -> str | None:
    """从第一轮证据中挑出偏移最大的参数作为第二轮焦点。"""
    best, best_dev = None, 0.0
    for e in state.get("evidences") or []:
        if e["source_tool"] != "query_sensor_stats":
            continue
        try:
            payload = json.loads(e["content"])
            dev = abs(payload["stats"]["avg"] - payload["stats"].get("baseline_avg", 0))
            if payload["stats"].get("baseline_std"):
                dev /= payload["stats"]["baseline_std"]
            if dev > best_dev:
                best, best_dev = payload["parameter"], dev
        except (KeyError, json.JSONDecodeError):
            continue
    return best


def analyze_root_cause_node(state: dict) -> dict:
    """LLM 综合节点：把证据清单交给 LLM，产出结构化 Top-3。

    结构化输出：with_structured_output(RootCauseReport)——
    LangChain 会在请求中注入 JSON Schema 并自动解析，解析失败自动重试一次。
    """
    usage = TokenUsageCallback()
    llm = get_llm(task_type="analysis", usage_callback=usage)

    event = state["event"]
    evidence_block = "\n".join(
        f"- {e['evidence_id']} [{e['source_tool']}] 强度={e['strength']}: {e['content']}"
        for e in (state.get("evidences") or [])
    ) or "（暂无证据）"
    tool_history_block = "\n".join(
        f"- {c['tool']}({json.dumps(c['args'], ensure_ascii=False)}) -> {c['evidence_id']}"
        for c in (state.get("tool_calls_made") or [])
    ) or "（无）"

    structured_llm = llm.with_structured_output(RootCauseReport)
    report: RootCauseReport = structured_llm.invoke([
        ("system", ROOT_CAUSE_SYSTEM_PROMPT),
        ("human", ROOT_CAUSE_USER_TEMPLATE.format(
            event_json=json.dumps(event, ensure_ascii=False, indent=2),
            evidence_block=evidence_block,
            tool_history_block=tool_history_block,
        )),
    ])

    # ---- 硬校验：证据ID真实存在（防幻觉的最后一道闸）----
    valid_ids = {e["evidence_id"] for e in state.get("evidences") or []}
    for s in report.top3:
        s.evidence_refs = [r for r in s.evidence_refs if r in valid_ids]

    token_usage = {"prompt_tokens": usage.prompt_tokens,
                   "completion_tokens": usage.completion_tokens,
                   "total_tokens": usage.total_tokens}
    logger.info("根因分析完成: top1=%s confidence=%.2f tokens=%s",
                report.top3[0].parameter, report.top3[0].confidence,
                token_usage["total_tokens"])
    return {
        "root_cause": report.model_dump(),
        "token_usage": token_usage,
        "history": [f"[root_cause] Top-3: "
                    + ", ".join(f"{s.parameter}({s.confidence:.2f})" for s in report.top3)],
    }


def _needs_more_evidence(state: dict) -> bool:
    """条件边谓词：LLM 声明证据不足且未达轮次上限 → 回到收集节点。"""
    rc = state.get("root_cause") or {}
    attempts = state.get("root_cause_attempts", 0)
    return (not rc.get("has_sufficient_evidence", True)) and attempts < MAX_EVIDENCE_ROUNDS
```

### 7.5 证据链构建规则（审计核心）

证据链的本质：**每条结论必须能被程序化回溯到工具原始返回**。实现三要素：

1. **证据 ID 生成**：`_record_tool_call` 按序生成 `E-1`、`E-2`……写入 State 的 `evidences` 与 `tool_calls_made`（含完整入参出参）。
2. **LLM 只允许引用 ID**：提示词约束 + `analyze_root_cause_node` 落库前的**程序化过滤**（`valid_ids` 交集）双重保险——即使 LLM 幻觉出不存在的 ID，也会被硬校验剔除。
3. **报告全程引用**：报告 Agent（第 10 章）把 `tool_calls_made` 原文附在 8D 报告附录，审计人员可以逐条核对。

## 8. 建议 Agent：调参与停线建议生成

建议 Agent 把"嫌疑"翻译成"行动"。它必须回答三个问题：**调什么（参数+方向+幅度）、风险多大、波及多少晶圆**。它不重新做根因分析——只消费根因报告。

### 8.1 建议生成提示词（完整全文）

```python
# industryagent_agent/prompts/advice.py
"""建议 Agent 提示词：基于根因报告生成调参/停线建议。"""

ADVICE_SYSTEM_PROMPT = """你是芯联半导体制造工程部的工艺参数管理专家。你的任务是把根因分析报告转化为可执行的处置建议，供值班工程师审批后执行。

# 决策规则（必须严格遵守）
1. 优先级顺序：保安全 > 保质量 > 保产能。任何时候"停线观察"优先级高于"带病生产"。
2. 建议类型判定：
   - tune（调参）：根因置信度 >= 0.6 且因果方向明确（estimate_causal_effect 证据中
     direction 不为 uncertain），且当前值偏移在工艺规格允许回调范围内。
     建议值 = 图谱或工艺文档中给出的目标值（target），禁止凭空设定数值。
   - stop_line（停线）：满足任一条件即必须建议停线：
     a) 根因置信度 >= 0.8 且影响批次良率下降超过 3 个百分点；
     b) 多参数（>=2个）同时严重越限；
     c) 无法定位到单一参数（Top-3 置信度均 < 0.4），但良率持续下降。
   - monitor（加强监控）：置信度 0.3-0.6，证据不足时先加密采样（如 5min 一次）
     复检该参数 24 小时，避免贸然调参。
3. affected_wafers 估算：用 query_lot_yield 证据中该设备日均投产晶圆数 × 
   建议生效前预计经过的小时数。没有数据时填保守高估值并在 rationale 中注明"估算"。
4. risk_level 判定：
   - critical: 停线建议，或影响晶圆数 > 200 片
   - high: 调参建议且影响晶圆数 100-200 片，或修改的是关键工艺参数
   - medium: 调参建议且影响晶圆数 < 100 片
   - low: 仅加密监控
5. 所有建议 requires_approval=true。任何调参与停线建议都必须人工审批后才能执行，
   这是工厂红线，禁止生成"可直接执行"的建议。

# 输出格式（JSON，严格遵守）
- advices: 建议数组，按风险从高到低排序，1-3 条。每条字段：
  - action_type: "tune" / "stop_line" / "monitor" 之一
  - target: 参数名（tune/monitor 时）或设备编号（stop_line 时）
  - current_value: 工具证据中的当前实测值；无则为 null
  - suggested_value: 建议值；monitor/stop_line 为 null
  - risk_level: "low"/"medium"/"high"/"critical"
  - affected_wafers: 整数
  - rationale: 80字以内依据，必须引用根因报告中的置信度与证据摘要，
    格式如"根因报告显示 chamber_temp 置信度0.87，因果效应-1.2pct/℃，回调至目标值80.0℃"
  - requires_approval: 必须为 true
- escalation_needed: 若任一建议 affected_wafers > 200 或 risk_level 为 critical，
  设为 true（表示必须升级到主管级审批）。

# 防幻觉约束
- suggested_value 只能来自证据中的工艺目标值/规格值，禁止编造数值。
- rationale 中的数字必须与根因报告一致，禁止改写置信度或效应值。
- 不确定时给出 monitor 建议，禁止给出没有证据支撑的激进建议。"""

ADVICE_USER_TEMPLATE = """# 根因分析报告（Top-3 嫌疑）
{root_cause_json}

# 异常事件摘要
{event_json}

{evidence_block}

请生成处置建议 JSON。"""

### 8.2 建议节点实现（含风险校验）

```python
# industryagent_agent/agents/advice_agent.py
"""建议 Agent：根因报告 → 结构化建议包 + 风险升级校验。"""
import json

from industryagent_agent.agents.schemas import AdvicePackage
from industryagent_agent.config import get_settings
from industryagent_agent.core.chat_model import TokenUsageCallback, get_llm
from industryagent_agent.logging_conf import get_logger
from industryagent_agent.prompts.advice import ADVICE_SYSTEM_PROMPT, ADVICE_USER_TEMPLATE

logger = get_logger(__name__)
settings = get_settings()


def advice_node(state: dict) -> dict:
    """建议节点：LLM 生成建议 + 程序化风险校验（升级规则不走 LLM，硬编码兜底）。"""
    usage = TokenUsageCallback()
    llm = get_llm(task_type="generation", usage_callback=usage)

    evidence_block = "\n".join(
        f"- {e['evidence_id']} [{e['source_tool']}]: {e['content'][:200]}"
        for e in (state.get("evidences") or [])
    )
    structured_llm = llm.with_structured_output(AdvicePackage)
    package: AdvicePackage = structured_llm.invoke([
        ("system", ADVICE_SYSTEM_PROMPT),
        ("human", ADVICE_USER_TEMPLATE.format(
            root_cause_json=json.dumps(state.get("root_cause"), ensure_ascii=False, indent=2),
            event_json=json.dumps(state.get("event"), ensure_ascii=False),
            evidence_block=evidence_block or "（无）",
        )),
    ])

    # ---- 程序化风险校验（红线规则不信任 LLM，硬编码强制执行）----
    escalation = package.escalation_needed
    for a in package.advices:
        a.requires_approval = True  # 红线：全部必须审批，无视 LLM 输出
        if (a.affected_wafers > settings.risk_escalation_threshold
                or a.risk_level.value == "critical"):
            escalation = True

    token_usage = {"prompt_tokens": usage.prompt_tokens,
                   "completion_tokens": usage.completion_tokens,
                   "total_tokens": usage.total_tokens}
    logger.info("建议生成: %d 条, escalation=%s",
                len(package.advices), escalation)
    return {
        "advice": package.model_dump(),
        "token_usage": token_usage,
        "history": [f"[advice] {len(package.advices)} 条建议, "
                    f"升级审批={escalation}, "
                    + "; ".join(f"{a.action_type}:{a.target}" for a in package.advices)],
    }
```

要点：`escalation` 的判定做了**双层防护**——LLM 按提示词给一次，代码按 `risk_escalation_threshold` 再强制一次。凡"影响晶圆数 > 阈值"一律升级，这类红线规则必须硬编码，因为 LLM 的输出永远存在不确定性，而工厂的安全规则不允许概率性失效。

> **验证**：在 `scripts/smoke_root_cause.py` 末尾追加：
> ```python
> from industryagent_agent.agents.advice_agent import advice_node
> state.update(advice_node(state))
> print(json.dumps(state["advice"], ensure_ascii=False, indent=2))
> ```
> 预期：对"温度漂移"根因给出 `tune` 建议（suggested_value 为 80.0 左右的目标值），且 `escalation_needed` 与影响晶圆数估算逻辑一致。若出现 `stop_line`，检查种子数据里良率下降是否超过 3pct。

## 9. 审批 Agent：人工确认（HITL 核心）

### 9.1 LangGraph interrupt 机制讲解

LangGraph 的 HITL 原语只有两个，理解它们是本章全部：

1. **`interrupt(payload)`**：在节点函数内部调用。图执行到此处立即**抛出 GraphInterrupt**，整个图的状态被冻结并写入 checkpointer（持久化），`payload`（审批请求内容）作为中断现场返回给调用方。服务进程可以重启，状态不丢。
2. **`Command(resume=value)`**：恢复执行。用**同一个 thread_id** 再次 invoke 图并携带 `resume` 值，图从中断点原样恢复，`interrupt()` 调用返回 `value`，节点继续执行。

与"轮询等待"的根本区别：interrupt 是**彻底挂起**——不占线程、不占连接、不占内存中的等待队列，等待 24 小时和等待 1 分钟的成本完全一样。这正是审批场景需要的语义。

### 9.2 审批节点实现

# industryagent_agent/agents/approval_agent.py
"""审批 Agent：HITL 中断等待 + 超时升级巡检。"""
import asyncio
import json
from datetime import datetime, timedelta, timezone

from langgraph.types import interrupt

from industryagent_agent.agents.schemas import ApprovalDecision, ApprovalRecord

def approval_node(state: dict) -> dict:
    """审批节点：发起 interrupt 等待人工决策，恢复后落审计记录。

    interrupt 的入参是"审批请求载荷"——FastAPI 层会把它推给审批看板/IM。
    恢复时 interrupt() 返回 ApprovalDecision（由 /agent/approve 接口传入）。
    """
    approval_request = {
        "event_id": state["event_id"],
        "advice": state.get("advice"),
        "root_cause_top1": (state.get("root_cause") or {}).get("top3", [None])[0],
        "escalation_needed": (state.get("advice") or {}).get("escalation_needed", False),
        "message": "请值班工程师审批以下处置建议（超时 24h 自动升级主管）",
    }
    # ---- 图在此冻结，状态持久化到 checkpointer ----
    decision_payload = interrupt(approval_request)

    decision = ApprovalDecision.model_validate(decision_payload)
    record = ApprovalRecord(
        decision=decision.decision,
        approver=decision.approver,
        reason=decision.reason,
        approved_at=datetime.now(timezone.utc),
        escalated=False,
    )
    logger.info("审批完成: event=%s decision=%s approver=%s",
                state["event_id"], decision.decision, decision.approver)
    return {
        "approval": record.model_dump(),
        "history": [f"[approval] {decision.decision} by {decision.approver}: {decision.reason}"],
    }
```

### 9.3 审批等待状态的持久化：checkpointer 演进

checkpointer 是 LangGraph 的"状态存档器"，每个超级步（superstep）后自动保存全量 State。演进路线：

| 阶段 | 实现 | 适用 | 说明 |
|---|---|---|---|
| 开发 | `MemorySaver` | 单机调试 | 进程内存，重启即丢 |
| 生产 | `PostgresSaver` | 正式部署 | 状态存 Postgres，服务重启/多副本都不丢 |

```python
# industryagent_agent/agents/graph.py 的 checkpointer 部分
from langgraph.checkpoint.memory import MemorySaver
from industryagent_agent.config import get_settings

settings = get_settings()


def get_checkpointer():
    """开发用 MemorySaver；生产切换 PostgresSaver（同一份图代码零改动）。

    生产环境取消以下注释即可（需 pip install langgraph-checkpoint-postgres，
    并保证 PostgreSQL 中已执行 PostgresSaver.setup() 建表）：
    """
    try:
        from langgraph.checkpoint.postgres import PostgresSaver
        saver = PostgresSaver.from_conn_string(settings.timescale_dsn)
        saver.setup()  # 首次运行建表（checkpoint / checkpoint_writes 等表）
        return saver
    except Exception as e:  # noqa: BLE001
        import logging
        logging.getLogger(__name__).warning(
            "PostgresSaver 不可用（%s），降级 MemorySaver（仅限开发环境）", e)
        return MemorySaver()
```

关键理解：**thread_id 是状态的钥匙**。我们把 `event_id` 作为 `thread_id`，审批接口凭同一个 `event_id` 就能在任何时刻、任何进程里恢复这张图——这就是"审批等待状态持久化"的全部秘密。

### 9.4 持久层与 HTTP 路由（FastAPI）

路由之前先补**持久层**——智能体的分析结论必须落到与 Egg.js 后端共享的业务表（`agent_tasks / rootcause_results / suggestions / approvals / reports_8d`，表结构见 2.6 节，与数据库教程 4.5/4.6 一致）。没有这一层，后端与前端看板就读不到智能体的产出，"联调"无从谈起。

def save_root_cause_results(task_no: str, top3: list[dict],
                             model_version: str = "industryagent-agent-0.1"
                             ) -> list[int]:

    task_rows = safe_query(
        "save_root_cause_results", ts_conn,

        return []
    task_id = task_rows[0]["id"]
    result_ids: list[int] = []
    for s in top3:

            "evidence=EXCLUDED.evidence RETURNING id",

             round(float(s["confidence"]), 4),
             json.dumps({"evidence_refs": s.get("evidence_refs", [])},

            "proposer_type, status) VALUES (%s,%s,%s::jsonb,%s,'agent',"

接下来是 HTTP 路由。**出入参契约与《00-后端开发教程》第 8 章严格对齐**——后端 `rootcause.ts` 的 `_callAgent` 发送 `{batch_no, yield_rate, top_k}`，并校验响应必须含 `root_causes` 数组（`suggestions` 数组逐条落库到它自己的 Suggestion 表）；任务状态枚举与 `agent_tasks.ck_agent_status` 一致。逐字段对照表：

| 契约项 | 后端教程约定 | 本服务实现 |
|---|---|---|
| 请求字段 | `batch_no`（必填）、`yield_rate`（可选）、`top_k`（默认 3） | `AnalyzeRequest` 三字段 + 智能体自有字段（`event`/`equipment`/`process_step`/`parameters`，后端不传时走现场检测） |
| 响应字段 | `root_causes: [{rank, factor, confidence, description}]` | 由 `RootCauseReport.top3` 映射：`factor=parameter`、`description=evidence_summary` |
| 响应字段 | `suggestions: [{type, content, risk_level}]` | 由 `AdvicePackage.advices` 映射：`tune→param_adjust`、`monitor→recheck`、`content=rationale` |
| 响应字段 | `summary`、`batch_no` | `overall_analysis` 摘要、原样回传 |
| 状态码 | HTTP 200 + body 内 code 区分（熔断器只认非 200 为失败） | 全部 200；业务错误走 main.py 的 BizError 处理器（也返回 200 + code） |
| 任务状态 | `pending / running / succeeded / failed`（后端枚举） + `cancelled/timeout`（数据库教程枚举） | `/agent/tasks/{task_no}` 原样返回 agent_tasks.status；审批等待以 `output_payload.workflow_status=pending_approval` 表达，不占用任务状态枚举 |

```python
# industryagent_agent/api/routes.py
"""Agent HTTP 路由：触发分析 / 审批恢复 / 任务与状态查询。

与 Egg.js 后端的契约见上方对照表；与后端教程 8.6 节 _callAgent 逐字段兼容。
"""
from datetime import datetime, timezone
from typing import Optional

from fastapi import APIRouter, Request
from pydantic import BaseModel, Field

from industryagent_agent.agents.persistence import (
    create_task, finish_task, get_task, save_approval,
    save_report_8d, save_root_cause_results, save_suggestions,
    update_workflow_status,
)
from industryagent_agent.agents.schemas import AnomalyEvent, ApprovalDecision
from industryagent_agent.config import get_settings
from industryagent_agent.logging_conf import get_logger

logger = get_logger(__name__)
router = APIRouter()


class AnalyzeRequest(BaseModel):
    """触发一次根因分析。

    后端契约字段（Egg.js rootcause.ts 调用）：batch_no / yield_rate / top_k；
    智能体自有字段：event（完整事件）或 equipment+process_step+parameters
    （现场检测模式）。两类字段可组合：后端传 batch_no 时，智能体自动
    现场检测并把 batch_no 写入分析上下文。
    """
    batch_no: Optional[str] = Field(None, description="批次号（后端契约字段）")
    yield_rate: Optional[float] = Field(None, description="批次良率 0-1（后端契约字段）")
    top_k: int = Field(3, ge=1, le=5, description="返回根因嫌疑数，后端固定传 3")
    event: Optional[dict] = Field(None, description="完整 AnomalyEvent；为空则现场跑监控Agent")
    equipment: Optional[str] = Field(None, description="现场检测模式：目标设备")
    process_step: Optional[str] = Field(None, description="现场检测模式：工序")
    parameters: Optional[list[str]] = Field(None, description="现场检测模式：参数清单")


def _to_backend_payload(batch_no: str | None, result: dict) -> dict:
    """把图的 State 映射为后端契约响应体（root_causes / suggestions 必有）。"""
    top3 = (result.get("root_cause") or {}).get("top3") or []
    advices = (result.get("advice") or {}).get("advices") or []
    type_map = {"tune": "param_adjust", "stop_line": "stop_line",
                "monitor": "recheck"}
    return {
        "batch_no": batch_no or "",
        "summary": (result.get("root_cause") or {}).get(
            "overall_analysis", "根因分析完成")[:200],
        "root_causes": [
            {"rank": s["rank"], "factor": s["parameter"],
             "confidence": s["confidence"],
             "description": s.get("evidence_summary", "")}
            for s in top3
        ],
        "suggestions": [
            {"type": type_map.get(a["action_type"], "recheck"),
             "content": a.get("rationale", ""),
             "risk_level": a.get("risk_level", "low")}
            for a in advices
        ],
        "generated_at": datetime.now(timezone.utc).isoformat(),
        "event_id": result.get("event_id"),
        "workflow_status": "pending_approval",   # 由调用方按分支覆盖
    }


@router.post("/analyze")
async def analyze(req: AnalyzeRequest, request: Request):
    """触发根因分析流程。图执行到审批节点会因 interrupt 返回 pending 状态。

    响应始终为后端契约结构（root_causes/suggestions 在挂起审批时也已产出），
    Egg.js 的格式校验（data.root_causes 为数组）在任何分支下都能通过。
    """
    graph = request.app.state.graph
    event = req.event
    if event is None:
        from industryagent_agent.agents.monitor_agent import detect_anomaly
        detected = detect_anomaly(
            req.equipment or "ETCH-03", req.process_step or "etch",
            req.parameters or ["chamber_temp", "rf_power", "pressure"])
        if detected is None:
            return {"code": 0, "message": "无异常",
                    "data": {"batch_no": req.batch_no, "anomaly": False,
                             "root_causes": [], "suggestions": []}}
        event = detected.model_dump(mode="json")
    if req.batch_no:
        event.setdefault("detail", {})["batch_no"] = req.batch_no

    # ---- 任务落库（agent_tasks，与后端共享表）----
    task_no = create_task("rootcause", {
        "batch_no": req.batch_no, "yield_rate": req.yield_rate,
        "top_k": req.top_k, "equipment": event.get("equipment")})

    cfg = {"configurable": {"thread_id": event["event_id"]},
           "recursion_limit": get_settings().graph_recursion_limit}
    initial_state = {"event_id": event["event_id"], "event": event}
    try:
        result = await graph.ainvoke(initial_state, config=cfg)
    except Exception as e:  # noqa: BLE001
        finish_task(task_no, "failed", None, error_message=str(e)[:1000])
        logger.exception("分析失败: task=%s", task_no)
        return {"code": 50001, "message": f"分析失败：{e}", "data": None}

    top3 = (result.get("root_cause") or {}).get("top3") or []
    advices = (result.get("advice") or {}).get("advices") or []
    tokens = (result.get("token_usage") or {}).get("total_tokens", 0)
    result_ids = save_root_cause_results(task_no, top3)
    suggestion_ids = save_suggestions(task_no, result_ids, advices)

    # interrupt 发生时，结果里包含 __interrupt__ 信息
    if "__interrupt__" in result:
        payload = _to_backend_payload(req.batch_no, result)
        payload["workflow_status"] = "pending_approval"
        payload["task_no"] = task_no
        payload["suggestion_ids"] = suggestion_ids
        finish_task(task_no, "succeeded", payload, token_usage=tokens)
        # 登记超时巡检注册表（9.5 节）——含建议 id，供 approve 落 approvals 表
        registry = getattr(request.app.state, "pending_approvals", {})
        registry[event["event_id"]] = {
            "created_at": datetime.now(timezone.utc),
            "task_no": task_no,
            "suggestion_ids": suggestion_ids,
            "advice_summary": payload["summary"],
            "escalated": False,
        }
        request.app.state.pending_approvals = registry
        # 通知后端（16.3 节：经 Egg.js WS 推给审批看板）
        from industryagent_agent.api.notify import notify_backend
        await notify_backend(request.app, event["event_id"], task_no,
                             "pending_approval", payload["summary"])
        return {"code": 0, "message": "等待人工审批",
                "data": {"anomaly": True, "event_id": event["event_id"],
                         "task_no": task_no,
                         "status": "pending_approval",
                         "approval_request": str(result["__interrupt__"]),
                         **{k: payload[k] for k in
                            ("batch_no", "summary", "root_causes",
                             "suggestions", "generated_at")}}}

    payload = _to_backend_payload(req.batch_no, result)
    payload["workflow_status"] = "finished"
    payload["task_no"] = task_no
    finish_task(task_no, "succeeded", payload, token_usage=tokens)
    return {"code": 0, "message": "流程完成",
            "data": {"anomaly": True, "event_id": event["event_id"],
                     "task_no": task_no, "status": "succeeded",
                     "report": result.get("report_markdown"),
                     **{k: payload[k] for k in
                        ("batch_no", "summary", "root_causes",
                         "suggestions", "generated_at")}}}


class ApproveRequest(BaseModel):
    """审批决策：恢复被 interrupt 冻结的图。"""
    event_id: str = Field(..., description="对应 /analyze 返回的 event_id（即 thread_id）")
    decision: str = Field(..., description="approve / reject")

@router.post("/approve")
async def approve(req: ApproveRequest, request: Request):
    """审批回调：approve → 流程继续走报告节点；reject → 流程终止。"""
    graph = request.app.state.graph
    if req.decision not in ("approve", "reject"):
        return {"code": 40001, "message": "decision 只能是 approve 或 reject", "data": None}

    # 从注册表取该事件的任务号与建议 id（approvals 表外键需要）
    registry = getattr(request.app.state, "pending_approvals", {})
    info = registry.get(req.event_id, {})
    task_no: str | None = info.get("task_no")
    suggestion_ids: list[int] = info.get("suggestion_ids", [])

    from langgraph.types import Command
    resume_value = ApprovalDecision(decision=req.decision,
                                    approver=req.approver,
                                    reason=req.reason).model_dump()
    cfg = {"configurable": {"thread_id": req.event_id},
           "recursion_limit": get_settings().graph_recursion_limit}
    try:
        result = await graph.ainvoke(
            Command(resume=resume_value), config=cfg)
    except Exception as e:  # noqa: BLE001
        if task_no:
            finish_task(task_no, "failed", None, error_message=str(e)[:1000])
        return {"code": 40402, "message": f"恢复失败：{e}", "data": None}

    # ---- 审批与报告落库 ----
    if suggestion_ids:
        save_approval(suggestion_ids, req.decision, req.approver,
                      req.reason or "")
    if req.decision == "approve" and task_no:
        save_report_8d(task_no, result.get("report_markdown", ""),
                       lot_no=None)
    if task_no:
        update_workflow_status(
            task_no, "finished" if req.decision == "approve" else "rejected")
    registry.pop(req.event_id, None)
    request.app.state.pending_approvals = registry

    # 通知后端（16.3 节）
    from industryagent_agent.api.notify import notify_backend
    await notify_backend(request.app, req.event_id, task_no,
                         "finished" if req.decision == "approve" else "rejected",
                         f"审批人 {req.approver}：{req.reason or '无意见'}")

    return {"code": 0, "message": "审批已处理",
            "data": {"event_id": req.event_id, "task_no": task_no,
                     "status": "finished" if req.decision == "approve"
                     else "rejected",
                     "report": result.get("report_markdown")}}

## 10. 报告 Agent：8D 报告自动生成

### 10.1 8D 报告结构

8D（Eight Disciplines）是汽车/半导体行业标准的问题解决报告格式，质量工程师写一份通常要 2-4 小时——报告 Agent 把它压缩到分钟级，但**必须保留人工抽检（见 10.4）**。

| 维度 | 内容 | 对应智能体数据 |
|---|---|---|
| D1 | 组建团队 | 固定模板：值班工程师/工艺工程师/设备工程师/质量工程师（从审批人与配置读取） |
| D2 | 问题描述 | `event`（监控Agent输出：5W2H 化） |
| D3 | 临时围堵措施 | `advice`（建议Agent：停线/隔离批次等） |
| D4 | 根本原因分析 | `root_cause`（Top-3 + 证据链） |
| D5 | 纠正措施选定 | `advice`（审批通过的调参建议） |
| D6 | 纠正措施实施 | 审批记录 + 建议执行状态 |
| D7 | 预防再发生 | 预防建议（由 LLM 基于证据生成：如增加 SPC 采样频率、修订规格书） |
| D8 | 团队表彰与结案 | 审批人/参与者致谢 + 结案时间 |

## 11. LangGraph 总编排

前面九章造好了所有"零件"，本章用 LangGraph 把它们装配成一台机器：**谁先执行、谁后执行、哪里循环、哪里中断、哪里分叉**——全部显式声明，一行不多一行不少。

### 11.1 图结构设计

```text
START → monitor(监控) ──无异常──▶ END
              │有异常
              ▼
      collect_evidence(证据收集,第1轮) → analyze_root_cause(根因分析LLM)
              ▲                              │
              │证据不足且轮次<2               │证据充分
              └──────────────────────────────┤
                                             ▼
                                       advice(建议生成LLM)
                                             ▼
                                     approval(审批, interrupt)
                              ┌──────────────┴──────────────┐
                          approve                       reject
                              ▼                            ▼
                         report(8D报告LLM)               END
                              ▼
                             END
```

三条关键边：

1. **条件边 monitor → (root_cause | END)**：无异常直接结束，不浪费一次 LLM 调用；
2. **条件边 analyze_root_cause → (collect_evidence | advice)**：证据不足回炉（限 2 轮，防死循环）；
3. **条件边 approval → (report | END)**：驳回即终止流程（报告失去意义，审计记录已在 State 中）。

def monitor_node(state: dict) -> dict:
    """监控节点：跑 SPC+EWMA 检测。无异常时写入 no_anomaly 标记，条件边据此终止。"""
    event = state.get("event")
    if event is None:
        detected = detect_anomaly(
            state.get("equipment", "ETCH-03"),
            state.get("process_step", "etch"),
            state.get("parameters") or MONITOR_PARAMS,
        )
        event = detected.model_dump(mode="json") if detected else None
    if event is None:
        logger.info("监控Agent未检出异常, 流程终止")
        return {"history": ["[monitor] 未检出异常，流程终止"],
                "no_anomaly": True, "event_id": state.get("event_id", "N/A")}
    return {"event": event, "event_id": event["event_id"],
            "started_at": datetime.now(timezone.utc).isoformat(),
            "history": [f"[monitor] 检出异常 {event['event_id']} "
                        f"severity={event['severity']} params={event['parameters']}"]}


def _route_after_monitor(state: dict) -> str:
    """条件边谓词：有异常进根因，无异常终止。"""
    return "collect_evidence" if not state.get("no_anomaly") else END


def _route_after_analysis(state: dict) -> str:
    """条件边谓词：证据不足回炉收集，否则进建议。"""
    return "collect_evidence" if _needs_more_evidence(state) else "advice"


def _route_after_approval(state: dict) -> str:
    """条件边谓词：审批通过进报告，驳回终止（审计数据已随 checkpointer 留存）。"""
    decision = (state.get("approval") or {}).get("decision")
    return "report" if decision == "approve" else END


def build_graph() -> StateGraph:
    """构建并返回未编译的 StateGraph。"""
    from industryagent_agent.agents.root_cause_agent import RCAState

    builder = StateGraph(RCAState)
    builder.add_node("monitor", monitor_node)
    builder.add_node("collect_evidence", collect_evidence_node)
    builder.add_node("analyze_root_cause", analyze_root_cause_node)
    builder.add_node("advice", advice_node)
    builder.add_node("approval", approval_node)
    builder.add_node("report", report_node)

    builder.add_edge(START, "monitor")
    builder.add_conditional_edges("monitor", _route_after_monitor,
                                  ["collect_evidence", END])
    builder.add_edge("collect_evidence", "analyze_root_cause")
    builder.add_conditional_edges("analyze_root_cause", _route_after_analysis,
                                  ["collect_evidence", "advice"])
    builder.add_edge("advice", "approval")
    builder.add_conditional_edges("approval", _route_after_approval,
                                  ["report", END])
    builder.add_edge("report", END)
    return builder


def get_checkpointer():
    """checkpointer 工厂：优先 PostgresSaver（生产），失败降级 MemorySaver（开发）。

    PostgresSaver 把每个超级步的状态快照写入 Postgres：
    服务重启 / 多副本部署时，凭 thread_id 即可恢复审批中断现场（见第 9 章）。
    """
    try:
        from langgraph.checkpoint.postgres import PostgresSaver
        saver = PostgresSaver.from_conn_string(settings.timescale_dsn)
        saver.setup()   # 幂等建表
        logger.info("checkpointer = PostgresSaver (生产模式)")
        return saver
    except Exception as e:  # noqa: BLE001
        logger.warning("PostgresSaver 不可用(%s)，降级 MemorySaver（仅限开发）", e)
        return MemorySaver()


def compile_app():
    """编译完整图：main.py 的 lifespan 调用一次，全局复用。"""
    app = build_graph().compile(checkpointer=get_checkpointer())
    logger.info("LangGraph 编译完成, 递归上限=%s", settings.graph_recursion_limit)
    return app


def export_mermaid(path: str = "graph.mmd") -> str:
    """图结构可视化：导出 mermaid（贴到 GitHub/Markdown 直接渲染）。"""
    mermaid = compile_app().get_graph().draw_mermaid()
    with open(path, "w", encoding="utf-8") as f:
        f.write(mermaid)
    logger.info("mermaid 已导出: %s", path)
    return mermaid


if __name__ == "__main__":
    print(export_mermaid())
```

## 12. MCP 工具层

### 12.1 为什么要把工具暴露为 MCP

目前工具是"进程内函数"——只有本服务的 LLM 能用。把它暴露为 MCP（Model Context Protocol）Server 后：

1. **跨系统复用**：Egg.js 业务后端、其他智能体（排产 Agent、维护 Agent）、甚至工程师的 IDE AI 助手（Claude/CodeBuddy 类）都能以标准协议调用同一套工具；
2. **解耦演进**：工具的 Python 实现（含数据库迁移、算法升级）独立发布，调用方零感知；
3. **统一治理**：工具的权限、审计、限流在 MCP 层统一收口——呼应手册 10.2 节"智能体通过 MCP 调用工具，降低耦合"。

### 12.3 Egg.js 与 MCP 的两种形态辨析（呼应手册 8.4）

手册 8.4 节给出混合架构"前端 → Egg.js 业务后端 → Python AI 微服务 → 模型/向量库；Egg.js 同时承担 MCP Server → 智能体工具链"。落地时"MCP Server 放在哪"有两种形态，各有适用场景：

**形态一：Egg.js 做统一 MCP Server（业务工具的中心化聚合）**

```text
各类智能体(LangGraph/IDE/运营助手) ──MCP──▶ Egg.js MCP Server ──REST──▶ MES/ERP/审计/权限系统
                                              │
                                              └──MCP转发──▶ Python mcp_server（算法工具）
```

- Egg.js 把**业务域工具**（查工单、查排产计划、写审计日志、查权限）封装成 MCP 工具统一暴露；
- 对算法工具（传感器统计、图谱、因果）则作为 **MCP client** 转发到 Python 的 `mcp_server.py`。
- 优点：权限/审计单点收口；公司所有智能体只需要对接一个 MCP 端点；Node 生态对业务系统 API 的胶水代码更好写。
- 代价：多一跳转发延迟（约 1-5ms，可忽略）；两套技术栈都要维护。

**形态二：Python 直供 MCP（算法工具就近暴露）**

```text
LangGraph 根因Agent ──进程内调用──▶ tools/（零开销）
外部智能体 ──MCP(stdio/SSE)──▶ Python mcp_server.py ──直连──▶ Neo4j/TimescaleDB/pgvector
```

- 算法工具由 Python 直供，业务系统只在需要算法能力时才接入；
- 优点：链路最短、部署简单，适合团队小、智能体少的阶段。
- 代价：每接入一个新智能体都要单独配 MCP 端点与凭证；权限策略分散。

**选型建议**：本教程主线采用形态二起步（LangGraph 进程内调用 + Python MCP Server 直供）；当智能体数量 ≥3 或公司统一治理要求出现时，演进为形态一——Egg.js 4.0 作为统一 MCP Server，Python 算法工具成为其后端之一。这与手册的演进路线（Docker Compose 起步 → 治理收口）一致。

**Egg.js 作为 MCP client 调用 Python 工具（形态一的桥接示例）**：

```javascript
// app/service/mcpClient.js —— Egg.js 侧用 @modelcontextprotocol/sdk 连接 Python MCP Server
'use strict';
const { Client } = require('@modelcontextprotocol/sdk/client/index.js');
const { StdioClientTransport } =
  require('@modelcontextprotocol/sdk/client/stdio.js');

const SERVICE = require('egg').Core;

class MCPClientService extends SERVICE {
  async sensorStats(equipment, parameter, hours = 24) {
    // 生产中应长连接复用；此处每次新建以演示协议
    const transport = new StdioClientTransport({
      command: 'python',
      args: ['-m', 'industryagent_agent.mcp_server'],
    });
    const client = new Client({ name: 'egg-business-backend', version: '1.0.0' });
    await client.connect(transport);
    try {
      const result = await client.callTool({
        name: 'sensor_stats',
        arguments: { equipment, parameter, hours },
      });
      return JSON.parse(result.content[0].text);
    } finally {
      await client.close();
    }
  }
}
module.exports = MCPClientService;
```

同时，Egg.js 业务后端与智能体服务的**主调用链**（触发分析/审批）走 REST——`app/controller/agent.js` 收到前端请求后 POST `http://industryagent-agent:8300/agent/analyze`，把返回的 `pending_approval` 状态推送到审批看板；审批看板提交时再由 Egg.js 转发 `/agent/approve`。这样 **HTTP 走人类交互、MCP 走工具调用**，职责清晰。

## 13. 评估 Agent 与量化体系

手册第 12 章的核心论断：**没有量化，智能体就无法迭代**。本章构建评估 Agent——它在闭环之外异步运行，回答"这套智能体到底行不行、值不值"。

### 13.1 指标定义（与手册案例 A 对齐）

| 指标 | 定义 | 计算口径 | 目标 |
|---|---|---|---|
| Top-3 命中率 | 真实根因出现在模型 Top-3 中的样本占比 | hit / n_samples | > 80% |
| 误报率 | 监控 Agent 报出但无真实异常的事件占比 | false_events / total_events | < 10% |
| 人工接管率 | 审批被驳回或人工大幅修正根因的占比 | (reject + major_fix) / total_events | < 30% |
| 端到端延迟 | 事件产生 → 报告生成（扣除人工等待） | report_ts - event_ts - approval_wait | < 5 分钟 |
| Token 成本 | 单事件平均消耗（prompt+completion） | total_tokens / n_events | 观测项 |

### 13.2 50 样本标注集：合成数据 + 已知注入根因

评估的最大难题是 ground truth 从哪来。本项目的答案：**合成数据注入法**——我们自己"制造"异常，所以知道正确答案。

`eval/dataset.py` 负责生成 50 个评估事件：

- 40 个"注入根因"样本：随机选设备/参数/工序，按物理机理注入异常（均值阶跃 +1~3σ、慢漂移 0.05σ/h、方差膨胀 3 倍），ground truth 就是注入的参数与设备；
- 5 个"多参数耦合"困难样本：两个参数同时注入，检验多根因场景；
- 5 个"正常"样本：不注入异常，检验误报率（监控 Agent 应全部不报）。

```python
# industryagent_agent/eval/dataset.py
"""评估数据集构建：注入已知根因的合成事件，ground truth 即注入参数。"""
import json
import uuid
from dataclasses import dataclass, asdict
from datetime import datetime, timezone

import numpy as np


@dataclass
class EvalSample:
    sample_id: str
    equipment: str
    process_step: str
    parameters: list          # 注入异常的参数 = ground truth
    injected_type: str        # step_shift / slow_drift / variance / none / coupled
    magnitude_sigma: float    # 注入幅度（σ 倍数）
    ground_truth_root_cause: str   # 真实根因参数名
    is_false_alarm_probe: bool = False  # 是否为"应无告警"的阴性样本


EQUIPMENTS = ["ETCH-03", "ETCH-07", "DEP-01", "DEP-02", "LITH-05"]
STEPS = {"ETCH": "etch", "DEP": "deposition", "LITH": "lithography"}
PARAM_POOL = {
    "etch": ["chamber_temp", "rf_power", "pressure", "etch_rate"],
    "deposition": ["chamber_temp", "gas_flow", "pressure", "film_thickness"],
    "lithography": ["exposure_dose", "focus_offset", "temp"],
}


def generate_eval_samples(n_injected: int = 40, n_coupled: int = 5,
                          n_negative: int = 5, seed: int = 2026) -> list[dict]:
    """生成 50 个评估样本（确定性：同 seed 同结果，保证回归可比）。"""
    rng = np.random.default_rng(seed)
    samples: list[EvalSample] = []

    for i in range(n_injected):
        equip = EQUIPMENTS[rng.integers(len(EQUIPMENTS))]
        step = STEPS[equip.split("-")[0]]
        param = PARAM_POOL[step][rng.integers(len(PARAM_POOL[step]))]
        itype = ["step_shift", "slow_drift", "variance"][rng.integers(3)]
        samples.append(EvalSample(
            sample_id=f"S-{i:03d}", equipment=equip, process_step=step,
            parameters=[param], injected_type=itype,
            magnitude_sigma=float(round(rng.uniform(1.0, 3.0), 2)),
            ground_truth_root_cause=param))

    for i in range(n_coupled):
        equip = EQUIPMENTS[rng.integers(len(EQUIPMENTS))]
        step = STEPS[equip.split("-")[0]]
        pool = PARAM_POOL[step]
        idx = rng.choice(len(pool), size=2, replace=False)
        params = [pool[j] for j in idx]
        samples.append(EvalSample(
            sample_id=f"S-C{i:02d}", equipment=equip, process_step=step,
            parameters=params, injected_type="coupled",
            magnitude_sigma=float(round(rng.uniform(1.5, 3.0), 2)),
            ground_truth_root_cause=params[0]))  # 主根因记第一参数

    for i in range(n_negative):
        samples.append(EvalSample(
            sample_id=f"S-N{i:02d}", equipment="ETCH-03", process_step="etch",
            parameters=[], injected_type="none", magnitude_sigma=0.0,
            ground_truth_root_cause="", is_false_alarm_probe=True))

    return [asdict(s) for s in samples]


def save_dataset(path: str = "eval_dataset.json") -> list[dict]:
    ds = generate_eval_samples()
    with open(path, "w", encoding="utf-8") as f:
        json.dump({"version": "v1", "seed": 2026, "samples": ds},
                  f, ensure_ascii=False, indent=2)
    return ds


if __name__ == "__main__":
    ds = save_dataset()
    print(f"评估集已生成: {len(ds)} 个样本 -> eval_dataset.json")
```

配套的注入器 `inject_anomaly(sample)` 已在 2.6 节 `scripts/init_databases.py` 中给出完整实现：按 `injected_type` 生成近 48h 的传感器序列——`step_shift` 在中点加 `magnitude_sigma * baseline_std` 阶跃、`slow_drift` 按时间线性抬升、`variance` 放大方差、`coupled` 双参数同漂、`none` 原样。良率按"chamber_temp 每偏 1σ 良率降 2pct"机理同步生成——因果工具才能测出负效应。

### 13.3 指标计算完整代码

```python
# industryagent_agent/eval/metrics.py
"""评估指标计算：Top-3命中率 / 误报率 / 人工接管率 / 端到端延迟 / Token成本。"""
from dataclasses import dataclass
from datetime import datetime

from industryagent_agent.logging_conf import get_logger

logger = get_logger(__name__)


@dataclass
class RunResult:
    """单样本的一次运行结果（跑完图后抽取）。"""
    sample_id: str
    triggered: bool                    # 监控是否报事件（阴性样本应为 False）
    top3_parameters: list[str]         # 根因 Agent 输出的参数名列表
    approval_decision: str             # approve / reject / no_event
    human_fixed: bool                  # 人工是否大幅修正根因（来自第14章回流标签）
    event_ts: float | None             # 事件产生时刻（unix 秒）
    report_ts: float | None            # 报告生成时刻
    approval_wait_seconds: float       # 审批等待时长（从等待开始到决策）
    total_tokens: int


def top3_hit_rate(results: list[RunResult], samples: list[dict]) -> float:
    """Top-3 命中率：真实根因出现在模型 Top-3 中 / 全部阳性样本。"""
    gt = {s["sample_id"]: s["ground_truth_root_cause"] for s in samples}
    positive = [r for r in results if gt.get(r.sample_id)]
    if not positive:
        return 0.0
    hits = sum(1 for r in positive if gt[r.sample_id] in r.top3_parameters)
    return hits / len(positive)


def false_alarm_rate(results: list[RunResult]) -> float:
    """误报率：阴性样本（is_false_alarm_probe，sample_id 以 S-N 开头）被报警的比例。"""
    probe = [r for r in results if r.sample_id.startswith("S-N")]
    if not probe:
        return 0.0
    return sum(1 for r in probe if r.triggered) / len(probe)


def manual_takeover_rate(results: list[RunResult]) -> float:
    """人工接管率：驳回 + 大幅修正 / 全部触发事件的样本。"""
    events = [r for r in results if r.triggered]
    if not events:
        return 0.0
    takeover = sum(1 for r in events
                   if r.approval_decision == "reject" or r.human_fixed)
    return takeover / len(events)


def end_to_end_latency_seconds(results: list[RunResult]) -> float:
    """端到端延迟（均值，秒）：事件→报告，扣除人工审批等待。"""
    latencies = [r.report_ts - r.event_ts - r.approval_wait_seconds
                 for r in results
                 if r.event_ts and r.report_ts and r.triggered]
    return sum(latencies) / len(latencies) if latencies else 0.0


def avg_tokens(results: list[RunResult]) -> float:
    """单事件平均 Token 消耗。"""
    used = [r.total_tokens for r in results if r.triggered]
    return sum(used) / len(used) if used else 0.0


def full_report(results: list[RunResult], samples: list[dict]) -> dict:
    """汇总全部指标，并对照目标值输出达标判定。"""
    metrics = {
        "top3_hit_rate": top3_hit_rate(results, samples),
        "false_alarm_rate": false_alarm_rate(results),
        "manual_takeover_rate": manual_takeover_rate(results),
        "end_to_end_latency_seconds": end_to_end_latency_seconds(results),
        "avg_tokens_per_event": avg_tokens(results),
        "n_samples": len(samples),
        "evaluated_at": datetime.utcnow().isoformat() + "Z",
    }
    metrics["pass"] = {
        "top3_hit_rate>0.80": metrics["top3_hit_rate"] > 0.80,
        "false_alarm_rate<0.10": metrics["false_alarm_rate"] < 0.10,
        "manual_takeover_rate<0.30": metrics["manual_takeover_rate"] < 0.30,
        "latency<300s": metrics["end_to_end_latency_seconds"] < 300,
    }
    logger.info("评估完成: %s", metrics)
    return metrics
```

### 13.4 评估入口脚本与回归评估

```python
# industryagent_agent/eval/run_eval.py
"""评估入口：遍历样本集 → 注入数据 → 跑图（审批自动模拟 approve）→ 计算指标。

用法： python -m industryagent_agent.eval.run_eval --dataset eval_dataset.json
回归评估规则（团队红线）：提示词文件、模型版本、温度参数任何变更后必须重跑，
对比 metrics 与上一版基线，任何指标退化超过 2 个百分点即阻塞合并。
"""
import argparse
import json
import time
from datetime import datetime, timezone

from industryagent_agent.agents.graph import compile_app
from industryagent_agent.eval.dataset import generate_eval_samples
from industryagent_agent.eval.metrics import RunResult, full_report
from industryagent_agent.logging_conf import setup_logging


def _equip_ids() -> dict[str, int]:
    """加载 code→id 映射（注入器需要）。"""
    from industryagent_agent.tools.db import safe_query, ts_conn
    rows = safe_query("_equip_ids", ts_conn, "SELECT code, id FROM equipments")
    return {r["code"]: int(r["id"]) for r in rows}


def run_one(graph, sample: dict, equip_ids: dict[str, int]) -> RunResult:
    """跑单个样本：注入→检测→分析→（自动审批）→记录结果。

    注入环节复用 2.6 节 scripts/init_databases.py 的 inject_anomaly——
    先清掉该设备相关参数近 48h 数据，再按 injected_type 写入"已知根因"。
    """
    import sys
    sys.path.insert(0, "scripts")            # 让 scripts 包内的模块可导入
    from init_databases import inject_anomaly
    inject_anomaly(sample, equip_ids)

    from langgraph.types import Command
    cfg = {"configurable": {"thread_id": f"eval-{sample['sample_id']}"},
           "recursion_limit": 40}
    t0 = time.time()
    result = graph.invoke(
        {"event_id": f"EVAL-{sample['sample_id']}",
         "event": {"event_id": f"EVAL-{sample['sample_id']}",
                   "equipment": sample["equipment"],
                   "process_step": sample["process_step"],
                   "parameters": sample["parameters"],
                   "detail": {"defect_type": "微桥接"},
                   "detected_at": datetime.now(timezone.utc).isoformat()}},
        config=cfg)
    triggered = bool(sample["parameters"]) or not result.get("no_anomaly", False)
    if not triggered:
        return RunResult(sample["sample_id"], False, [], "no_event", False,
                         t0, None, 0.0, 0)
    # 自动审批（评估中不等待人工）
    wait_start = time.time()
    result = graph.invoke(Command(resume={"decision": "approve",
                                          "approver": "eval-bot",
                                          "reason": "自动审批"}), config=cfg)
    approval_wait = 0.0  # 自动审批无真实等待
    top3 = [s["parameter"] for s in (result.get("root_cause") or {}).get("top3", [])]
    tokens = (result.get("token_usage") or {}).get("total_tokens", 0)
    return RunResult(sample["sample_id"], True, top3, "approve", False,
                     t0, time.time(), approval_wait, tokens)


def main() -> None:
    setup_logging()
    parser = argparse.ArgumentParser()
    parser.add_argument("--dataset", default="eval_dataset.json")
    parser.add_argument("--out", default="eval_report.json")
    args = parser.parse_args()

    try:
        with open(args.dataset, encoding="utf-8") as f:
            samples = json.load(f)["samples"]
    except FileNotFoundError:
        samples = generate_eval_samples()  # 首次运行自动生成

    graph = compile_app()
    equip_ids = _equip_ids()
    results = [run_one(graph, s, equip_ids) for s in samples]
    report = full_report(results, samples)

    # LLM 摘要（评估 Agent 的"解读"节点，见下方 eval/summarize.py）
    try:
        from industryagent_agent.eval.summarize import summarize_report
        report["llm_summary"] = summarize_report(report)
    except Exception as e:  # noqa: BLE001
        report["llm_summary"] = f"（摘要生成失败：{e}）"

    with open(args.out, "w", encoding="utf-8") as f:
        json.dump(report, f, ensure_ascii=False, indent=2)
    print(json.dumps(report, ensure_ascii=False, indent=2))
    all_pass = all(report["pass"].values())
    print("回归评估结论:", "PASS（相对基线可合并）" if all_pass
          else "FAIL（存在指标未达标或退化，阻塞合并）")
    raise SystemExit(0 if all_pass else 1)


if __name__ == "__main__":
    main()
```

评估 Agent 的最后一环是 **LLM 摘要节点**：把 `eval_report.json` 的指标交给 `get_llm("generation")`，生成一份"指标解读 + 短板定位 + 迭代建议"的中文评估报告（如"误报率 12% 超标，主要来自 S-N 阴性样本中 pressure 参数的方差膨胀误判，建议 EWMA 的 λ 从 0.2 调至 0.15"）。完整代码（结构化输出 + 提示词全文，与根因节点同构）：

```python
# industryagent_agent/eval/summarize.py
"""评估报告 LLM 摘要节点：指标数字 → 可读的解读与迭代建议。"""
import json

from pydantic import BaseModel, Field

from industryagent_agent.core.chat_model import get_llm
from industryagent_agent.logging_conf import get_logger

logger = get_logger(__name__)

SUMMARIZE_SYSTEM_PROMPT = """你是半导体制造智能体的评估分析师。你的任务是解读自动评估报告的指标，输出中文摘要，供团队决定下一步迭代方向。

# 解读规则
1. 逐项对照目标值（Top-3命中率>0.80、误报率<0.10、人工接管率<0.30、端到端延迟<300秒），
   明确说"达标/未达标"，禁止含糊。
2. 未达标项必须给出"最可能的短板定位"——结合指标数值推理（如误报率高→监控Agent
   检测器阈值过松；人工接管率高→提示词证据引用规则不足）与一条可执行的迭代建议。
3. 数字引用必须与输入 JSON 完全一致，禁止编造未给出的数据。

# 输出格式（JSON）
- overall: 一句话总体结论（20-50字）
- passed: 达标指标名列表
- failed: 未达标指标名列表
- findings: 数组，每项 {"metric", "value", "target", "diagnosis", "suggestion"}
  （diagnosis=短板定位，suggestion=可执行建议，各 60 字以内）
- next_action: 下一步最优先的一件事（30 字以内）"""


class Finding(BaseModel):
    metric: str = Field(..., description="指标名")
    value: float = Field(..., description="实际值")
    target: str = Field(..., description="目标值描述")
    diagnosis: str = Field(..., description="短板定位")
    suggestion: str = Field(..., description="可执行迭代建议")


class EvalSummary(BaseModel):
    overall: str
    passed: list[str]
    failed: list[str]
    findings: list[Finding]
    next_action: str


def summarize_report(report: dict) -> str:
    """把 full_report 的指标 dict 交给 LLM 解读，返回摘要文本（JSON 字符串）。"""
    llm = get_llm(task_type="analysis")
    structured = llm.with_structured_output(EvalSummary)
    summary: EvalSummary = structured.invoke([
        ("system", SUMMARIZE_SYSTEM_PROMPT),
        ("human", "# 评估报告指标\n```json\n"
                  + json.dumps(report, ensure_ascii=False, indent=2)
                  + "\n```\n请输出评估摘要 JSON。"),
    ])
    logger.info("评估摘要: %s | 未达标=%s", summary.overall, summary.failed)
    return summary.model_dump_json()
```

> **验证**：`python -m industryagent_agent.eval.run_eval`。首次运行会生成 50 样本并逐个跑图（约 20-40 分钟，取决于 LLM 吞吐），结束后检查 `eval_report.json` 四项 pass 与 `llm_summary` 字段的解读是否与指标一致。把 `eval_report.json` 提交进 Git——这就是你的**评估基线**，后续一切变更都和它比。

## 14. 人机协同与反馈回流

HITL 不止"审批放行"这一个动作。审批结果、人工修正、根因复核都是**智能体的训练燃料**。本章把反馈闭环落地成三张表和一条回流管线。

### 14.1 反馈数据模型（PostgreSQL）

```sql
-- 审批结果回流
CREATE TABLE IF NOT EXISTS approval_feedback (
    event_id      TEXT PRIMARY KEY,
    decision      TEXT NOT NULL,           -- approve / reject
    approver      TEXT NOT NULL,
    reason        TEXT,
    advice_snapshot JSONB,                 -- 审批时的建议快照
    created_at    TIMESTAMPTZ DEFAULT now()
);

-- 人工修正根因标签（比自动输出更权威的 ground truth）
CREATE TABLE IF NOT EXISTS root_cause_correction (
    event_id      TEXT,
    original_top3 JSONB,                   -- 智能体原始输出
    corrected_root_cause TEXT NOT NULL,    -- 工程师确认的真实根因
    corrected_by  TEXT,
    correction_note TEXT,                  -- 为什么改（最有提示词价值的部分）
    created_at    TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (event_id, created_at)
);

-- 提示词迭代数据积累（每次重要变更的 A/B 素材库）
CREATE TABLE IF NOT EXISTS prompt_iteration_log (
    version     TEXT NOT NULL,             -- 如 root_cause@2026-10-15-3
    event_id    TEXT,
    outcome     TEXT,                      -- hit / miss / corrected / rejected
    diff_summary TEXT,                     -- 本次提示词改动摘要
    eval_delta  JSONB,                     -- 评估指标相对上一版的变化
    created_at  TIMESTAMPTZ DEFAULT now()
);
```

### 14.2 回流管线（scripts/feedback_pipeline.py）

```python
# scripts/feedback_pipeline.py
"""反馈回流管线：从审批/修正记录中提炼提示词迭代素材。

运行时机：每天定时（或每次评估前）。产出：
1. miss_cases.md —— 命中失败样本的"事件+证据+人工修正"三元组，直接用于改提示词；
2. prompt_iteration_log 补登记。
"""
import json
import psycopg

from industryagent_agent.config import get_settings
from industryagent_agent.logging_conf import setup_logging, get_logger

logger = get_logger(__name__)


def extract_miss_cases(out_path: str = "miss_cases.md") -> int:
    """把"被驳回/被修正"的事件整理成可读的复盘材料。"""
    s = get_settings()
    sql = """
    SELECT c.event_id, c.original_top3, c.corrected_root_cause,
           c.correction_note, a.decision, a.reason
    FROM root_cause_correction c
    LEFT JOIN approval_feedback a USING (event_id)
    ORDER BY c.created_at DESC LIMIT 100;
    """
    with psycopg.connect(s.timescale_dsn) as conn, conn.cursor() as cur:
        cur.execute(sql)
        rows = cur.fetchall()

    lines = ["# 根因失误复盘素材（自动生成）", ""]
    for event_id, top3, truth, note, decision, reason in rows:
        lines += [
            f"## 事件 {event_id}",
            f"- 智能体 Top-3: {json.dumps(top3, ensure_ascii=False)}",
            f"- 人工确认根因: **{truth}**",
            f"- 修正理由: {note or '（未填写）'}",
            f"- 审批结论: {decision or 'N/A'}（{reason or ''}）",
            "",
        ]
    with open(out_path, "w", encoding="utf-8") as f:
        f.write("\n".join(lines))
    logger.info("复盘素材已导出: %s（%d 条）", out_path, len(rows))
    return len(rows)


def record_prompt_version(version: str, diff_summary: str,
                          eval_delta: dict) -> None:
    """提示词每次重要变更登记在案，关联评估增量。"""
    s = get_settings()
    with psycopg.connect(s.timescale_dsn) as conn, conn.cursor() as cur:
        cur.execute(
            "INSERT INTO prompt_iteration_log (version, diff_summary, eval_delta) "
            "VALUES (%s, %s, %s)",
            (version, diff_summary, json.dumps(eval_delta, ensure_ascii=False)))
        conn.commit()
    logger.info("提示词版本已登记: %s", version)


if __name__ == "__main__":
    setup_logging()
    n = extract_miss_cases()
    print(f"导出 {n} 条复盘素材 -> miss_cases.md")
```

### 14.3 用反馈迭代提示词的标准动作

1. 读 `miss_cases.md`，把重复出现的失误模式**升格为提示词规则**。典型例子：工程师多次在"温度与压力同时漂移"时修正根因为 pressure——把"当两个参数同时漂移时，优先检查压力对温度的耦合影响（见工艺文档 xxx）"写入 `ROOT_CAUSE_SYSTEM_PROMPT` 的解读规则；
2. 登记版本：`record_prompt_version("root_cause@2026-10-18-1", "增加压力-温度耦合判定规则", {})`；
3. 跑第 13 章回归评估，`eval_delta` 回填登记；
4. 达标才合并——**提示词变更与代码变更走同等严格的回归门禁**。

## 15. 测试体系

智能体的测试分层与普通服务不同：除了"代码对不对"，还要测"LLM 输出稳不稳"。三层递进：

| 层 | 对象 | 策略 | 速度 |
|---|---|---|---|
| 单元测试 | 算法/工具函数 | 输入输出断言，外部依赖全 mock | 毫秒级 |
| 提示词回归 | LLM 结构化输出 | 固定输入 + 断言输出字段（不比对全文） | 秒级，需真实 LLM |
| 集成测试 | 全图流程 | FakeListChatModel 假 LLM + mock 工具 | 秒级，CI 可跑 |

### 15.1 工具函数 mock 测试

```python
# tests/test_tools_mock.py
"""工具层单测：所有外部依赖（DB/LLM）全部 mock，只测纯逻辑。

mock 策略：5.2 节把数据库访问统一收口到 safe_query / equipment_name_to_id，
因此只需 patch 这两个函数——不必再伪造 psycopg 连接对象（V1.0 教程的写法），
测试代码量减半且不随 SQL 细节耦合。
"""
import json
from unittest.mock import patch

### 15.1.1 conftest.py：公共 fixture（FakeListChatModel 的结构化封装）

15.3 节集成测试的稳健做法——**同时 mock 掉 `with_structured_output`，让 FakeListChatModel 直接返回 JSON 文本**——封装成 fixture 放进 `conftest.py`（V1.0 教程在 15.3 节末尾省略了这层封装，此处补全为完整代码）：

```python
# tests/conftest.py
"""pytest 公共 fixture：假 LLM（结构化输出兼容）、测试图装配。

FakeListChatModel 返回纯文本，而真实节点走 llm.with_structured_output(schema)
——两者不兼容。fake_structured_llm fixture 把 with_structured_output mock 成
"忽略 schema、直接把预置 JSON 文本交给节点解析"，使全图可以在无真实 LLM
环境下完整跑通（CI 每次提交都跑的关键）。
"""
import json

import pytest
from langchain_core.language_models.fake_chat_models import (
    FakeListChatModel,
)


def make_fake_llm(responses: list[str]) -> FakeListChatModel:
    """构造"结构化输出兼容"的假 LLM。

    用法：responses 按 LLM 节点的调用顺序给 JSON 文本列表，例如
    [json_top3(), json_advice(), "8D 报告正文（fake）"]。
    """
    fake = FakeListChatModel(responses=responses)

    # 关键封装：绕过 with_structured_output 的 JSON Schema 注入与解析，
    # 直接返回 fake 本体——节点拿到的 invoke 结果就是原始 JSON 文本。
    fake.with_structured_output = lambda schema=None, **kw: _ParsingLLM(fake, schema)
    return fake


class _ParsingLLM:
    """带 schema 的解析层：把 fake 的文本响应按 Pydantic 模型解析。

    节点代码 `structured_llm.invoke(messages)` 期望得到 Pydantic 对象
    （with_structured_output 的行为）；本类把 JSON 文本转成 schema 实例。
    """

    def __init__(self, inner: FakeListChatModel, schema=None):
        self._inner = inner
        self._schema = schema

    def invoke(self, messages, config=None, **kwargs):
        text = self._inner.invoke(messages, config=config, **kwargs).content
        if self._schema is None:
            return text
        return self._schema.model_validate_json(text)


@pytest.fixture
def patch_all_llms(mocker):
    """把三个 LLM 节点的 get_llm 一并替换为同一个假 LLM 工厂。

    用法：
        def test_xxx(patch_all_llms):
            patch_all_llms([json_top3(), json_advice(), "8D 正文"])
            ...  # 之后 build_graph().compile() 跑全图
    """
    def _install(responses: list[str]):
        fake = make_fake_llm(responses)
        for module in (
            "industryagent_agent.agents.root_cause_agent",
            "industryagent_agent.agents.advice_agent",
            "industryagent_agent.agents.report_agent",
        ):
            mocker.patch(f"{module}.get_llm", return_value=fake)
        return fake
    return _install
```

说明三个工程决策：

1. **`--workers 1`**：LangGraph 图实例与连接池是非进程安全的设计（checkpointer 多进程需要 PostgresSaver 配合），多副本横向扩展交给 K8s `replicas`，不要用 uvicorn 多 worker；
2. **多阶段构建**：builder 装编译链，运行镜像只带运行库，体积从 ~2.5GB 降到 ~800MB；
3. **HEALTHCHECK 用 `/health` 的语义判定**：数据库连不上时容器自动被判不健康（`degraded`），K8s 摘流——半死不活的服务比彻底挂掉更危险。

      contentType: 'json',
      dataType: 'json',
      timeout: 600000,                       // 全流程最长 10 分钟
      data: {
        batch_no: batchNo,                   // 后端契约字段
        yield_rate: undefined,               // 由 service 层从批次记录填充
        top_k: 3,
        equipment,                           // 智能体自有字段：现场检测模式
        process_step: processStep,
      },
    });
    const body = res.data;
    // 3) 挂起审批 → 生成审批工单；完成 → 存报告
    //    （响应体必有 root_causes/suggestions 数组——9.4 节契约保证任何分支都通过格式校验）
    if (body.data && body.data.status === 'pending_approval') {
      await ctx.model.ApprovalTicket.create({
        event_id: body.data.event_id,
        task_no: body.data.task_no,          // 智能体侧 agent_tasks.task_no
        status: 'PENDING',
        created_by: ctx.user.id,
      });
      await ctx.service.notify.pushApproval(body.data.event_id);
    }
    ctx.body = body;
  }

  // 审批回调：POST /api/v1/agent/approve
  async approve() {
    const { ctx } = this;
    const { eventId, decision, reason } = ctx.request.body;
    ctx.permission.check('agent:approve');
    // 双保险：本系统也无权跳过审批红线
    if (!['approve', 'reject'].includes(decision)) {
      ctx.throw(400, '非法审批动作');
    }
    const res = await ctx.curl('http://industryagent-agent:8300/agent/approve', {
      method: 'POST', contentType: 'json', dataType: 'json',
      data: { event_id: eventId, decision, approver: ctx.user.name, reason },
    });
    // 审计日志（Egg.js 侧独立留痕，与 Python 侧审计互相印证）
    await ctx.model.AuditLog.create({
      action: 'AGENT_APPROVAL', target: eventId, result: decision,
      operator: ctx.user.id, at: new Date(),
    });
    ctx.body = res.data;
  }
}
module.exports = AgentController;
```

联调检查清单：

- [ ] Egg.js 与 ia-agent 在同一 docker network（服务名互通）；
- [ ] `/health` 通过（否则 Egg.js 转发层应熔断报"智能体服务不可用"而非 500 传染）；
- [ ] 审批工单状态机：PENDING → APPROVED/REJECTED 与图状态一致（用 `/agent/status/{event_id}` 或 `/agent/tasks/{task_no}` 对账）；
- [ ] 优雅停机：`docker stop` 时 uvicorn 收到 SIGTERM 完成 in-flight 请求（中断中的流程不受影响——状态在 Postgres）；
- [ ] 任务状态回调链路通（16.3 节）：智能体 `notify_backend` → Egg.js 回调接口 → WS 推送，前端实时收到 `agent.task.status` 帧。

### 16.3 任务状态实时通知：打通 Egg.js 的 WebSocket 通道

后端教程 18.2 节已经建好了 WebSocket 服务端（agent 进程独占端口 7002，帧格式 `{event, eventId, data, ts}`，支持 `anomaly.push` 广播与 `notification.push` 定向推送）。本节回答联调的最后一问：**智能体侧如何把任务状态变化（挂起审批/审批完成/驳回）实时送到前端看板？**

先明确架构决策——**智能体不直连 7002 端口**。后端的 WS 服务端面向"浏览器用户"：连接需要用户 JWT 鉴权、进入用户房间、上行消息只处理心跳——它是用户会话通道，不是服务间通道。服务间通知走 **HTTP 回调**，由 Egg.js 落库并转发到 WS：

```text
┌────────────────────────┐  ①HTTP 回调（X-Internal-Token）  ┌─────────────────────────────┐
│ industryagent-agent    │ ───────────────────────────────▶ │ Egg.js 业务后端              │
│ (FastAPI :8300)        │  POST /api/v1/agent/callback/    │  controller/agentCallback    │
│                        │       task-status                │  → notification.createNotification
│ api/notify.py          │                                  │  → messenger.sendToAgent      │
│ (9.4 节 notify_backend)│ ◀─────────────────────────────── │                              │
└────────────────────────┘  ②HTTP 200（通知是尽力而为）      │ agent 进程 (agent.ts, 18.2.5)
                                                          │  ws:broadcast / ws:send-to-user
                                                          └──────────────┬───────────────┘
                                                                         │ ③WebSocket :7002
                                                                         ▼
                                                          ┌─────────────────────────────┐
                                                          │ 前端看板（审批看板/大屏）      │
                                                          │ onmessage: agent.task.status │
                                                          └─────────────────────────────┘
```

**为什么这样分**：HTTP 走服务间（有重试语义、有 token 鉴权、无连接状态），WS 走人机间（在线才推、断线由前端补偿拉取）。智能体不需要知道"谁在线"，Egg.js 不需要理解分析流程——各自职责单一。

**智能体侧**已在 9.4 节完成：`api/notify.py` 的 `notify_backend` 在 `/agent/analyze`（挂起审批时）与 `/agent/approve`（审批完成/驳回时）被调用，payload 为 `{event_id, task_no, workflow_status, summary, ts}`。通知失败只打 warning——通知是"尽力而为"的副作用，绝不拖垮主流程。

**Egg.js 侧**需要补一个回调接口（以下代码加到后端项目，是对后端教程 18.2 节的标准扩展）：

```javascript
// app/controller/agentCallback.js —— Egg.js 侧：接收智能体任务状态回调
'use strict';

const Controller = require('egg').Controller;

module.exports = class AgentCallbackController extends Controller {
  /** POST /api/v1/agent/callback/task-status（内部接口，X-Internal-Token 鉴权） */
  async taskStatus() {
    const { ctx } = this;
    // 1) 内部令牌校验（不走用户 JWT——这是服务间接口）
    if (ctx.get('x-internal-token') !== this.app.config.biz.agentCallbackToken) {
      ctx.throw(401, 'invalid internal token');
    }
    const { event_id: eventId, task_no: taskNo,
            workflow_status: workflowStatus, summary } = ctx.request.body;

    ctx.logger.info('[agent-callback] %s -> %s (task=%s)',
      eventId, workflowStatus, taskNo);

    // 2) 广播给所有在线看板（复用 18.2.5 的 ws:broadcast 通道，帧格式一致）
    this.app.messenger.sendToAgent('ws:broadcast', {
      event: 'agent.task.status',
      data: { eventId, taskNo, workflowStatus, summary,
              ts: Date.now() },
    });

    // 3) 落通知表 + 定向推送给值班工程师（复用 18.2.3 的 createNotification，
    //    演示固定通知 engineer；生产应从排班表解析当前值班人）
    await this.service.notification.createNotification({
      userId: 2,   // engineer
      type: 'anomaly',
      title: workflowStatus === 'pending_approval'
        ? `事件 ${eventId} 等待审批` : `事件 ${eventId} 已${workflowStatus === 'finished' ? '完成' : '被驳回'}`,
      content: summary || '',
    }).catch(e => ctx.logger.warn('[agent-callback] notify: %s', e.message));

    ctx.status = 200;
    ctx.body = { code: 0 };
  }
};
```

路由注册（`app/router.ts`，放在鉴权路由区之外——内部接口用独立令牌）：

```javascript
  // ---------------- 智能体回调（内部，X-Internal-Token 鉴权） ----------------
  router.post('/api/v1/agent/callback/task-status',
    controller.agentCallback.taskStatus);
```

配置（`config.default.ts` 的 `biz` 段，与智能体侧 `.env` 的 `BACKEND_CALLBACK_TOKEN` 保持一致）：

```javascript
  biz: {
    // ...既有配置...
    agentCallbackToken: 'ia-agent-internal',   // 生产环境必换并走内网/防火墙
  },
```

**前端对接**（呼应后端教程 18.2.8）：前端在既有 WS 客户端的 `onmessage` 分发中增加一个 case：

```javascript
ws.onmessage = e => {
  const { event, eventId, data } = JSON.parse(e.data);
  switch (event) {
    case 'anomaly.push':       store.appendAnomaly(data); break;
    case 'notification.push':  store.increaseUnread(data); break;
    case 'agent.task.status':  // 智能体任务状态：审批看板刷新工单状态
      store.updateAgentTask(data.eventId, data.workflowStatus, data.taskNo); break;
    case 'pong': break;
  }
};
```

**验证**（三步闭环）：

1. 启动 Egg.js（`npm run dev`，WS 端口 7002 就绪）与智能体服务（`.env` 配置 `BACKEND_BASE_URL=http://127.0.0.1:7001`）；
2. 挂一个 WS 客户端（后端教程 18.2.9 的 Node 一行脚本，带 engineer 的 token）；
3. 触发 `curl -X POST http://localhost:8300/agent/analyze -H "Content-Type: application/json" -d '{"batch_no":"B20261015001","equipment":"ETCH-03","process_step":"etch"}'`——WS 客户端应**立即**打印 `{"event":"agent.task.status","eventId":"evt-N","data":{"eventId":"EVT-...","workflowStatus":"pending_approval",...}}`；随后调 `/agent/approve`，应再收到一帧 `workflowStatus: "finished"`。若收不到帧但 Egg 日志有 `[agent-callback]`，检查智能体侧 `.env` 的 `BACKEND_BASE_URL` 是否指向正确的 Egg 地址。

## 17. 常见坑 FAQ

**Q1：LLM 输出不稳定，同样的输入两次结果不一样，怎么办？**
温度不是唯一因素。① 分析类任务温度压到 0.1 以下（0.0 也可，但部分模型 0.0 仍非完全确定）；② vLLM 启动参数加 `--seed 42`；③ 最重要的：**不要把稳定性寄托在采样上**——结构化输出（`with_structured_output`）+ 断言字段特征的回归测试（15.2 节）才是工程正解。断言"Top-1 是谁、置信度区间"，不断言全文。

**Q2：`with_structured_output` 解析 JSON 失败怎么重试？**
两层防护：① LangChain 的 `with_structured_output(..., include_raw=True)` 返回 `(raw, parsed, error)`，error 非空时把 raw 里最后一个 `{...}` 用正则抠出来手动 `model_validate`；② 仍失败则把"解析失败 + 原始输出 + schema"作为 human 消息再喂一次（自我修复提示），最多 1 次；③ 两次都失败 → 节点抛 BizError，流程终止留审计。参考实现：在 `analyze_root_cause_node` 里把 `structured_llm.invoke` 包成 `_invoke_structured_with_retry(llm, messages, schema, retries=2)` 工具函数。

**Q3：Token 超限（ContextWindowExceededError）怎么办？**
三处源头逐一排查：① `query_sensor_stats` 的 `hourly_avg` 截断到 12 条、`content` 截 500-800 字（本教程代码已做）；② 多轮证据回炉时，`evidence_block` 会越滚越大——把已引用过的弱证据从 prompt 中折叠成一行"（已引用，略）"；③ 8D 报告的 `pipeline_json` 里 `tool_calls_made` 只带 result_summary 不带全量。监控手段：TokenUsageCallback 在每节点后检查 `total_tokens`，超过模型上限 60% 时告警。

**Q4：Neo4j 连接抖动（SessionExpired / ServiceUnavailable）。**
本教程图工具里每次查询都新建 driver 太重，生产应该全局单例 driver + 复用 session。driver 内置连接池（默认 max 100），报错时先检查：① `verify_connectivity()` 是否在 lifespan 成功过；② Cypher 是否缺索引——`Defect.name`、`Parameter.name` 上要建索引（`CREATE INDEX FOR (d:Defect) ON (d.name)`），全表扫描会让会话超时；③ 容器内存限制 ≥ 1GB。

**Q5：工具死循环——LLM 反复调用同一个工具。**
三重防护（缺一不可）：① 图层：`root_cause_attempts < MAX_EVIDENCE_ROUNDS` 条件边兜底（第 7 章）；② 调用层：`recursion_limit=40` 超限 LangGraph 直接抛 GraphRecursionError；③ 审计层：`_record_tool_call` 检测"同一工具+同一入参"连续出现 2 次即拒绝并写入 history。注意：`recursion_limit` 数的是**超级步**不是工具调用，40 对 6 节点图绰绰有余。

**Q6：interrupt 之后恢复失败："No pending interrupt found"。**
九成原因是 **thread_id 不一致**：`/analyze` 用了 `event_id` 做 thread_id，`/approve` 却传了工单号。排查顺序：① 两个接口的 thread_id 是否同源（都应是 event_id）；② 图是否换了 checkpointer（开发时 MemorySaver 的状态在另一个进程/重启后就没了——切 PostgresSaver）；③ 是否图被重新 compile 且 checkpoint 结构变了（LangGraph 升级大版本会改 checkpoint 表结构，需要迁移）。

**Q7：服务重启后审批中的流程全部丢失。**
你在用 MemorySaver。看第 9.3 节：生产必须 PostgresSaver，且 `saver.setup()` 建表只用跑一次。验证方法：重启容器后调 `GET /agent/status/{event_id}`，若 `is_pending_approval=true` 依然可查，说明持久化生效。

**Q8：DoWhy 报 "Cannot identify effect" 或 effect 值为 NaN。**
混杂变量与处理变量共线了。检查：① `common_causes` 里不要放由 treatment 派生的列；② `_load_analysis_dataframe` 的 JOIN 是否造出重复批次行（一条 lot 匹配多参数窗口）；③ 样本量 < 30 直接返回 insufficient_data（本教程已做），不要硬算。

**Q9：pgvector 检索相似度全是 0.9+，没有区分度。**
向量维度与 embedding 模型不一致（表是 1536 维，模型输出 768/1024 维时报错；一致但文档太短/太相似时区分度低）。检查：① `SELECT dim(embedding) FROM doc_chunks LIMIT 1` 与模型维度比对；② 文档切块策略：工艺 SOP 按"参数条目"切块而不是整篇灌入；③ 换中文模型（bge-large-zh > m3e > 通用多语模型），换模型必须整表重嵌入（doc_chunks.embedding 与 embedding_model 强绑定）。

**Q10：LLM 编造了不存在的参数名（如 "temperature" 而库里是 "chamber_temp"）。**
防线在两处：① 提示词"必须与工具返回原词一致"（第 7.3 节）；② 程序化白名单校验——`analyze_root_cause_node` 落库前把 top3 的 parameter 与"所有证据 content 中出现过的参数名"求交集，不在交集内的嫌疑整体剔除。还可以在 `_record_tool_call` 里维护 `known_params` 集合。

**Q11：审批接口被绕过——报告直接生成了。**
检查三处：① 图的条件边 `_route_after_approval` 是否只认 `decision == "approve"`；② `ApprovalDecision` 的 Pydantic 校验是否放过了 `decision="Approve "`（大小写/空格）——本教程用 `not in ("approve", "reject")` 硬拒绝，保持严格；③ Egg.js 网关的 `agent:approve` 权限点是否真的启用（联调时最容易注释掉忘了开）。

**Q12：端到端延迟超过 5 分钟指标。**
先分层计时再优化：`history` 里每节点打时间戳，定位慢在哪。常见排序：LLM 综合节点（占 60-80%，对策：vLLM 开连续批处理、换小一档模型做初筛）＞ 工具查询（加 TimescaleDB 时间桶聚合索引）＞ 证据回炉轮次（第一轮就把时序+图谱并行查完，减少回炉概率）。**最大坑：把"等待审批"计入端到端延迟**——评估口径必须扣掉人工等待（13.3 节的 `approval_wait_seconds`）。

**Q13：评估集跑一次太慢/太贵。**
① 把 50 样本按 `sample_id` 哈希分片，CI 只跑 10 样本的"冒烟分片"，全量 50 跑周度回归；② 监控 Agent 的误报指标不需要 LLM——阴性样本只跑到 monitor 节点（无异常即结束，成本近零）；③ Token 成本本身是评估产出的一部分，`avg_tokens_per_event` 的下降就是优化成果。

**Q14：Windows 开发机上 weasyprint/psycopg 装不上。**
psycopg 用 `psycopg[binary]`（本教程 requirements 已带）。weasyprint 在 Windows 依赖 GTK 运行库，嫌麻烦就改用方案 B（Pandoc）或干脆只在 Docker（Linux）里导 PDF——报告生成与导出解耦后，导出失败不影响主流程。

## 18. 小结与延伸

### 18.1 本教程小结

我们完成了一个完整的多智能体闭环，按六层复杂度模型复盘：

| 层 | 本项目落地 |
|---|---|
| 业务领域 | 8D 方法论、SPC/EWMA/FDC、Top-3 根因、调参/停线决策规则 |
| 系统集成 | Egg.js 网关联调、MCP 工具协议、REST/Webhook 审批链 |
| 数据 | TimescaleDB 时序、Neo4j 图谱、pgvector 文档、SECOM 式统计、脏数据注入 |
| 算法/智能体 | 三路证据设计、防幻觉约束、结构化输出、HITL 中断 |
| 工程/运维 | 健康检查、Token 统计、审计日志、Docker 多阶段构建 |
| 组织/合规 | 审批红线（代码级强制）、超时升级、人工抽检、数据不出域（vLLM 私有部署） |

三条最重要的经验（比代码更值得带走）：

1. **确定性规则优先于 LLM**：监控用统计、审批红线用代码、因果用量化——LLM 只做它不可替代的部分（证据综合与文本生成），并且永远被"程序化校验"兜底。
2. **证据链是工业智能体的命根**：从 docstring 到提示词到硬校验，我们围绕"每条结论可回溯"建了四层防线——这是审计、评估、迭代共同的地基。
3. **评估驱动迭代**：50 样本回归基线 + 反馈回流管线让提示词变更有了"红绿灯"，智能体项目从"玄学调优"变成工程。

### 18.2 延伸方向

- **多目标权衡**（手册案例 B 的核心课题）：建议 Agent 目前只看"恢复良率"，可扩展为在良率/产能/能耗/成本间权衡——把 Pareto 前沿的选择交给审批人，Agent 负责呈现各方案的量化权衡表。
- **在线学习**：EWMA 基线目前用固定 7 天窗口，可换成滑动再训练 + 概念漂移自适应（ADWIN 检测漂移后自动重建基线），让监控 Agent 跟上设备老化。
- **漂移检测**：数据漂移（PSI/KL 散度监控输入分布）与模型漂移（LLM 输出分布的稳定性监控）双管齐下——把 `eval/metrics.py` 的指标搬到 Prometheus，Grafana 出趋势看板，形成"指标即监控"。
- **检索增强的图谱联合推理**（GraphRAG）：当前图谱查询与 RAG 检索独立取证，可让图谱结构引导文档检索（按关联路径扩展查询词），提升困难样本命中率。
- **多智能体协作升级**：当排产 Agent、维护 Agent（手册案例 B）接入后，当前单图架构演进为 Supervisor 模式——Egg.js MCP Server 做跨 Agent 工具治理，LangGraph 做各域内编排。

### 18.3 交付物清单（对照手册第 14 章）

完成本教程后，你的仓库应包含：源码（本教程全部模块）、`eval_report.json`（量化基线）、`graph.mmd`（架构图）、`demo` 运行日志、Dockerfile 与 compose 文件、测试报告（pytest 输出）。按手册 14.1 的 README 模板包装："根因 Top-3 准确率 XX%、误报率 XX%、端到端延迟 X 分钟"——每个数字都来自你的 `eval_report.json`，可复现、可讲述。
