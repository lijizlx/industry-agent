## 状态

已接受（2026-10-15，架构评审会通过）

## 背景

IndustryAgent 的数据负载具有鲜明的**多模态混合**特征：

1. **业务事务数据**：用户/角色/设备/配方/批次/晶圆/缺陷/审批/审计——强事务、强一致、外键关系多；
2. **传感器时序数据**：3 条产线 × 40 台设备 × 500 测点 × 1Hz，约 3~6 万数据点/秒，需要按时间分区、列压缩、保留策略与连续聚合（看板加速）；
3. **向量数据**：工艺文档（SOP/FMEA/CAPA/历史 8D）分块 embedding（1536 维），支撑根因 Agent 的 RAG 检索，规模约 4 万向量（v1.0）；
4. **图数据**：设备-工序-参数-缺陷关联知识图谱，多跳查询（根因召回核心路径），节点量级 ~800、边 ~2 万；
5. **对象数据**：缺陷图、工艺文档原件、8D 报告 PDF，约 1GB/月。

同时约束条件为：数据不出域（全私有化）、v1.0 Docker Compose 单机部署、团队 DBA 资源有限（1 名兼职 DBA）。

## 备选方案对比

| 维度 | 方案A：PostgreSQL+TimescaleDB+pgvector（一栈多能） | 方案B：MySQL+InfluxDB+Milvus（分库方案） | 方案C：MongoDB（文档库为主） |
|---|---|---|---|
| 业务事务 | ★★★★★ ACID 完善，JSONB 灵活 | ★★★★ 成熟 | ★★★ 事务仅文档级，跨文档弱 |
| 时序能力 | ★★★★ TimescaleDB 超表：自动分区/列压缩(10:1)/保留策略/连续聚合，SQL 原生 | ★★★★ InfluxDB 专业时序，但需独立运维另一套 | ★★ 无原生时序能力 |
| 向量能力 | ★★★★ pgvector HNSW，4 万向量规模检索 <50ms | ★★★ Milvus 专业向量库，但多引入一个重组件 | ★★ 需外挂向量方案 |
| 混合查询（JOIN 时序/向量/业务） | ★★★★★ 同库同 SQL，一次查询跨业务+时序+向量 | ★★ 三库各自查询，应用层聚合 | ★★★ 仅文档内 |
| 图能力 | ★★★★（可用 Apache AGE/递归 CTE 兜底，但本项目另配 Neo4j） | ★★ 无 | ★★★（$graph 弱） |
| 运维复杂度 | ★★★★★ 一套 PG：备份/HA/监控/升级统一 | ★★ 三套系统：MySQL+Influx+Milvus 各自备份、监控、版本 | ★★★★ 单系统 |
| 数据不出域/私有化 | ★★★★★ 容器化成熟 | ★★★ Milvus 集群化部署较重 | ★★★★★ |
| 团队技能 | ★★★★ SQL 通用 | ★★★ 三套各需学习 | ★★★ |

## 决策

**采用 PostgreSQL 16 + TimescaleDB + pgvector 一栈式作为核心持久层，配合 Neo4j 5 承载知识图谱、MinIO 承载对象存储。**

具体分工：

| 数据 | 存储 |
|---|---|
| 业务事务 + 时序（sensor_readings 超表） + 向量（doc_chunks） | PostgreSQL 16（库 ia_business，schema：biz/ts/vec） |
| 知识图谱（Equipment/ProcessStep/Parameter/DefectType/Recipe 多跳关联） | Neo4j 5 |
| 缺陷图 / 工艺文档 / 8D PDF | MinIO |
| 缓存/会话/限流 | Redis（非持久层） |

## 理由

1. **运维复杂度是本项目第一约束**：单机 Compose 下，方案 B 需要同时运维 MySQL、InfluxDB、Milvus 三套有状态服务（三份备份策略、三份监控、三个升级周期），对 1 名兼职 DBA 不现实；PG 一栈式只有一份备份/HA/监控；
2. **事务一致性**：审批链（suggestions→approvals→audit_logs）必须强事务；PG 单库内完成，分库方案需引入分布式事务或最终一致补偿，复杂度得不偿失；
3. **混合查询是根因链路的刚需**：根因证据组装常需要"业务表 JOIN 时序聚合 + 向量相似度"组合查询（如"该设备近 30 天缺陷记录 + 参数统计 + 相似 CAPA 文档"），同库 SQL 一次完成；
4. **规模匹配**：本项目向量 4 万条、时序 2.6 亿行/月——均在 TimescaleDB + pgvector 的舒适区（pgvector 千万级以下表现良好；TimescaleDB 压缩后容量可控股），无需为想象中的超大规模引入 Milvus；
5. **Neo4j 不可替代**：多跳图推理（设备→工序→参数→缺陷三跳）是根因召回的核心路径，Cypher 表达力与 GDS 图算法远超 SQL 递归，值得独立部署。

## 后果

### 正面

- 一套 PG 覆盖三种负载，备份（每日 pg_dump + WAL）、监控（postgres_exporter）、迁移（Flyway）全部统一；
- SQL 全栈可查，根因证据链组装查询简洁；
- TimescaleDB 压缩（7 天后段压缩 10:1）显著控制 3 年时序容量（40GB/月 → ~4GB/月等效）。

### 负面

- 超表 + pgvector 扩展要求 PG 特定版本组合，升级需回归验证扩展兼容性；
- 时序、向量、业务同实例存在资源争抢风险（大范围时序扫描可能拖慢业务查询）；
- Neo4j 单机版存在单点风险（本项目量级下未配集群）。

### 缓解

- 扩展版本锁定在镜像中（postgres:16 + timescaledb 2.x + pgvector 0.7 组合镜像），升级走灰度环境全量回归；
- 资源隔离：连接池分组（业务池/时序池/向量池配额分离），看板重查询走连续聚合物化视图，v1.5 迁 K8s 时引入只读副本分离审计与看板负载；
- Neo4j 每日全量 GraphML 导出备份；运行时降级策略：图谱不可用时根因 Agent 跳过 GRAPH 证据、置信度 ×0.7 并明确标注（见 IA-SD-006 第 4 章）。
