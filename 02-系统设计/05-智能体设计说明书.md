## 1. 引言

### 1.1 编制目的

定义 IndustryAgent 智能体服务层（Python FastAPI + LangGraph）的多智能体编排、每个 Agent 的详细设计（职责、输入输出、提示词、工具、失败重试）、工具层、人机协同、记忆与成本控制。链路口径：**监控Agent(FDC异常检测)→根因Agent(知识图谱Neo4j+因果推断DoWhy+RAG检索→Top-3嫌疑)→建议Agent(调参/停线建议+风险评估)→审批Agent(人工确认+审计记录)→报告Agent(自动生成8D报告)**，另设**评估Agent**做离线闭环。

### 1.2 设计原则

1. **确定性优先**：证据采集（图谱/因果/检索/时序）全部走确定性工具，LLM 只做综合表述与文档生成，降低幻觉风险；
2. **工具即 MCP**：所有数据访问经 Egg.js MCP Server（工具注册表见第 9 章），智能体不直连数据库；
3. **HITL 硬约束**：任何影响产线的建议未经人工审批不得下发生效；
4. **全程可追溯**：每次工具调用、每条证据、每次 Token 消耗都携带 trace_id 落库。

## 2. 多智能体总体编排（LangGraph）

### 2.1 状态机图

```text
                          ┌──────────────┐
                          │    START     │ (Kafka fdc.alarm / 手动触发)
                          └──────┬───────┘
                                 ▼
                        ┌─────────────────┐  复核不通过(误报)
                        │   monitor_node  │──────────────┐
                        │ (监控Agent复核)  │              │ 标记FP并结束
                        └────────┬────────┘              ▼
                          通过   │                 ┌────────────┐
                                 ▼                 │    END     │
                        ┌─────────────────┐        └────────────┘
                        │ rootcause_node  │ 重试≤3(指数退避)
                        │ (Top-3+证据链)  │────失败────► FAILED + 告警
                        └────────┬────────┘
                                 ▼
                        ┌─────────────────┐
                        │  suggest_node   │
                        │ (建议+风险评估)  │
                        └────────┬────────┘
                                 ▼
                     ┌───────────────────────┐
              ┌─────►│   approve_node        │ (HITL interrupt 中断点)
              │      │ (等待人工审批)         │───────┐
              │ 超时  └───────────────────────┘       │ 批准
              │ 升级                                   ▼
              │(30min通知主管                  ┌─────────────────┐
              └─2h转工单)                      │  report_node    │
                                              │ (8D报告生成)    │
                                              └────────┬────────┘
                                                       ▼
                                                  ┌────────────┐
                                                  │    END     │
                                                  └────────────┘
  驳回 ──► agent.feedback (Kafka) ──► 评估Agent 离线评估（旁路，不阻塞主链路）
  人工接管 ──► TAKEOVER 终态 ──► 评估Agent
```

### 2.2 State 定义（TypedDict）

```python
from typing import TypedDict, Annotated, Literal
from operator import add

class AgentState(TypedDict):
    # ---- 输入区（一次写入） ----
    task_id: str
    anomaly: Annotated[dict, add]      # {anomaly_id, equipment_code, param_name, score, occurred_at}
    trace_id: str
    # ---- 中间结果区（节点覆写） ----
    monitor_verdict: dict              # {pass: bool, fp_reason: str|None, votes: {fdc,spc,iforest}}
    rootcause: dict                    # {suspects_top3: [...], confidence: float}
    suggestions: list[dict]            # 建议数组（同 IA-SD-005 14.5 契约）
    approval: dict                     # {decision, reason, approver, decided_at, sla_minutes}
    report: dict                       # {report_no, content_d1_d8, pdf_key}
    # ---- 控制区 ----
    retry_count: int                   # 当前节点重试计数（上限3）
    error: str | None
    token_usage: Annotated[dict, add]  # {node: {in, out}} 成本累加
```

### 2.3 条件边与中断点

```python
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver

builder = StateGraph(AgentState)
builder.add_node("monitor",  monitor_node)
builder.add_node("rootcause", rootcause_node)
builder.add_node("suggest",  suggest_node)
builder.add_node("approve",  approve_node)   # 内部调用 interrupt() 挂起
builder.add_node("report",   report_node)

builder.set_entry_point("monitor")
builder.add_conditional_edges("monitor", route_monitor,
    {"pass": "rootcause", "false_alarm": END})
builder.add_conditional_edges("rootcause", route_retry,
    {"ok": "suggest", "retry": "rootcause", "fail": END})
builder.add_edge("suggest", "approve")
builder.add_conditional_edges("approve", route_approval,
    {"approved": "report", "rejected": END, "escalated": "approve"})
builder.add_edge("report", END)

graph = builder.compile(checkpointer=PostgresSaver.from_conn_string(PG_DSN))
# approve_node 内: decision = interrupt({"suggestions": state["suggestions"]})
# Egg.js 收到人工审批后: graph.invoke(Command(resume=decision), config={"thread_id": task_id})
```

持久化：`PostgresSaver` 按 `thread_id=task_id` 保存检查点，服务重启后从中断点恢复（HITL 等待可达数小时，必须持久化）。

## 3. 监控 Agent

| 项 | 设计 |
|---|---|
| 职责 | 常驻消费 Kafka `sensor.raw`，FDC 规则 + SPC 控制图 + 孤立森林三模型投票检测异常，发布 `fdc.alarm`；graph 内 `monitor_node` 对告警复核防误报 |
| 输入 | 时序窗口（10min/1h/24h）+ FDC 规则库 + Recipe 规格限 |
| 输出 | 异常事件 `{anomaly_id, equipment_code, param_name, score(0-1), votes, occurred_at}` |
| 工具依赖 | query_sensors（复核时回看时序） |
| 模型 | FDC 规则引擎（阈值/斜率/驻留）+ EWMA 控制图 + IsolationForest（sklearn，SECOM 预训练） |
| 投票策略 | 三模型至少 2/3 触发才产生告警（误报率<10% 硬指标） |
| 失败重试 | 规则/模型异常跳过该窗口并记录；Kafka 消费失败 offset 不提交，重启重放；单测点连续 5 次异常自动标 `BAD` 隔离（防传感器故障误报风暴） |

FDC 规则示例：`R12: RF_POWER 10min 滑动均值偏离 nominal > 3% 且持续 ≥ 5 个采样点`。

## 4. 根因 Agent

| 项 | 设计 |
|---|---|
| 职责 | 综合知识图谱、因果推断、RAG 检索、SECOM 特征相关性，产出 Top-3 嫌疑 + 置信度 + 证据链 |
| 输入 | AgentState.anomaly + query_sensors 回看 24h |
| 输出 | `rootcause.suspects_top3`（契约同 IA-SD-004 3.10 / IA-SD-005 9.3） |
| 工具依赖 | query_graph、search_docs、run_causality、query_sensors |
| 算法流程 | ①图谱召回：query_graph(rootcause_trace) 得候选设备/参数集；②因果排序：对 Top-5 候选逐一 run_causality；③文献佐证：search_docs 检索历史 CAPA/8D；④特征相关性：SECOM 训练的参数-缺陷相关系数合并打分；⑤LLM 综合表述（提示词见下） |
| 失败重试 | 单工具失败重试 3 次（指数退避 2s/4s/8s）；图谱不可用→降级（跳过 GRAPH 证据、置信度×0.7 并标注）；全部失败→FAILED + Grafana 告警 |

置信度合成：`confidence = 0.35*graph_weight + 0.30*|causal_effect_norm| + 0.20*rag_score + 0.15*secom_corr`（权重可配置，评估Agent 回归调优）。

**根因 Agent 系统提示词（全文）：**

```text
你是芯联半导体12英寸晶圆厂的资深工艺根因分析专家。

【职责】基于系统提供的确定性证据（知识图谱、DoWhy因果效应、RAG文献检索、
传感器统计），对异常事件给出Top-3根因嫌疑排序，并撰写可解释的分析结论。

【硬性规则】
1. 你只能引用工具返回的证据，禁止编造任何设备编号、参数名、数值或文献。
2. 每个嫌疑必须至少包含2类证据（GRAPH/CAUSAL/RAG/SENSOR中至少2种），
   证据不足的候选不得进入Top-3，宁缺毋滥。
3. 排序依据置信度降序；置信度必须由系统计算的公式给出，你只解释成因逻辑。
4. 输出使用简体中文，术语使用行业惯用语（如"腔体漂移""颗粒污染""匹配器校准"）。
5. 若所有候选证据均不足，输出空列表并说明"证据不足，建议人工排查"，
   不得强行给出嫌疑。

【输出格式】严格输出JSON：
{"suspects_top3": [
  {"rank": 1, "equipmentCode": "...", "processStep": "...", "paramName": "...",
   "confidence": 0.00,
   "summary": "80字以内成因推理",
   "evidences": [{"type": "GRAPH|CAUSAL|RAG|SENSOR", "desc": "...", "detail": {}}]
 }],
 "overallConclusion": "150字以内整体判断，包括对良率影响的初步估计"}

【当前输入】
异常事件：{anomaly}
图谱候选：{graph_candidates}
因果效应：{causal_results}
文献检索：{rag_hits}
传感器统计：{sensor_stats}
```

## 5. 建议 Agent

| 项 | 设计 |
|---|---|
| 职责 | 针对 Top-3 嫌疑（主要 rank=1）生成调参/PM/停线/复检建议，附风险等级与影响晶圆数估算 |
| 输入 | `state.rootcause` + query_graph(sibling_check)（同型设备对照）+ Recipe spec_limits |
| 输出 | `state.suggestions[]`（契约同 IA-SD-005 14.5） |
| 建议模板 | PARAM_ADJUST：`建议将 {equipment} {param} 由 {current} 回调至 {nominal}（配方基准 {recipe_code}），并执行 {n} 片验证批`；STOP_LINE（仅风险 HIGH 且缺陷率超基线 3 倍时允许提出）；PM_PLAN：联动设备工程师派工；RECHECK_WAFER：HOLD 影响批次全检 |
| 风险等级 | LOW（规格带内调参）/ MID（WIP 重排队）/ HIGH（停线/整批隔离） |
| 影响晶圆数 | `当前设备WIP批数×25 + 24h内流经该工序的批次估算` |
| 失败重试 | 生成失败重试 2 次；输出契约校验失败（params_delta 缺失等）→ 修正提示重试 1 次 → FAILED |

**建议 Agent 系统提示词（全文）：**

```text
你是芯联半导体晶圆厂的工艺优化顾问，负责把根因结论转化为可执行建议。

【职责】针对给定的Top-3根因嫌疑，生成结构化行动建议（调参/PM/停线/复检），
并完成风险评估。

【硬性规则】
1. 调参建议的目标值必须来自工具返回的Recipe基准值（nominal），禁止自行编造数值。
2. 建议类型优先级：PARAM_ADJUST > RECHECK_WAFER > PM_PLAN > STOP_LINE。
   STOP_LINE仅当缺陷率超过基线3倍且风险为HIGH时才允许提出。
3. 每条建议必须包含：建议正文、参数变更明细params_delta、风险等级、
   风险评估说明（对良率/产能/交付的影响）、影响晶圆数估算。
4. 语气客观审慎，不得使用"肯定""绝对"等绝对化表述。
5. 你生成的建议将由人工审批后才执行——在正文中明确提示验证批安排。

【输出格式】严格输出JSON数组：
[{"suggestionType": "PARAM_ADJUST|PM_PLAN|STOP_LINE|RECHECK_WAFER",
  "suspectRank": 1,
  "content": "建议正文（含验证批安排）",
  "paramsDelta": {"PARAM": {"from": 0, "to": 0, "unit": "..."}},
  "riskLevel": "LOW|MID|HIGH",
  "riskAssessment": "50字以内",
  "affectedWaferCount": 0,
  "estimatedBenefit": "50字以内"}]

【当前输入】
根因结果：{rootcause}
配方规格：{recipe_limits}
同型设备对照：{siblings}
当前WIP：{wip_status}
```

## 6. 审批 Agent（HITL）

| 项 | 设计 |
|---|---|
| 职责 | 在 approve_node 调用 `interrupt()` 挂起图执行，通知人工审批；审批结果恢复执行；管理超时升级 |
| 输入 | `state.suggestions` |
| 输出 | `state.approval`（decision/reason/approver/decided_at/sla_minutes）→ 落库 approvals + audit_logs |
| 流程 | ①interrupt 挂起（checkpointer 持久化）②WebSocket 推送审批工作台 ③Egg.js `POST /approvals` → 回调 `graph.invoke(Command(resume))` ④超时升级：30min 未决通知生产主管（approval.escalated），2h 未决状态→ESCALATED 转人工工单，图终态结束 |
| 失败重试 | 升级通知失败重试 3 次；回调恢复失败由 schedule 补偿扫描（每 5 分钟） |

      │                            │                  ┌────┴────┐
      │                       通知生产主管            批准      驳回

## 7. 报告 Agent

| 项 | 设计 |
|---|---|
| 职责 | 汇总全流程数据，生成 8D 报告（D1-D8），引用证据链，归档 MinIO |
| 输入 | 完整 State（anomaly + rootcause + suggestions + approval）+ 后续验证数据（D7 需求） |
| 输出 | `reports_8d` 记录 + PDF（MinIO `reports-8d/…`） |
| D1-D8 生成规则 | D1 团队：按审批人角色自动组队（工艺+设备+质量）；D2 问题描述：异常事件 + 缺陷率对比基线；D3 临时措施：HOLD 批次与隔离（取建议 EXECUTED 记录）；D4 根因：rank=1 嫌疑 + 证据链内联引用；D5 永久措施：参数回调 + SOP 修订建议；D6 预防：FMEA 更新与 FDC 规则灵敏度调整；D7 效果确认：验证批 7 天良率曲线（未满 7 天标注"跟踪中"，定时任务回填）；D8 表彰：人工补充 |
| 失败重试 | 生成失败重试 2 次；PDF 渲染失败保留 JSON 草稿（status=DRAFT），人工可触发重新渲染 |

**报告 Agent 系统提示词（全文）：**

```text
你是芯联半导体的质量工程师助理，负责撰写8D报告。

【职责】将一次完整的异常处理闭环（异常→根因→建议→审批→执行）整理为
标准8D报告（D1-D8），供质量工程师审阅签发。

【硬性规则】
1. D4根因与D5措施只能引用本次任务的真实数据（rootcause/suggestions/approval），
   每个关键论断后附证据引用标记，如 [证据:CAUSAL]、[证据:RAG:doc-a12f#42]。
2. D7效果确认：若验证数据不足7天，如实标注"跟踪中"，禁止虚构验证结论。
3. 报告语言正式、简洁，符合半导体行业8D报告惯例。
4. 不做任何责任归咎表述，聚焦事实与改进。

【输出格式】输出JSON：
{"reportNo": "由系统提供", "title": "...",
 "d1_team": {...}, "d2_problem": "...", "d3_containment": "...",
 "d4_rootcause": "...", "d4_evidence_refs": [...],
 "d5_corrective": "...", "d6_preventive": "...",
 "d7_verify": "...", "d8_recognition": "待人工补充"}

【当前输入】
异常事件：{anomaly}
根因结果：{rootcause}
建议与执行：{suggestions}
审批记录：{approval}
验证数据：{verification}
```

## 8. 评估 Agent

| 项 | 设计 |
|---|---|
| 职责 | 离线评估：消费 `agent.feedback`（驳回/接管）+ 人工确认的 final_rootcause，计算核心指标，输出调优建议 |
| 输入 | 历史任务终态数据（终审根因为 ground truth） |
| 输出 | 指标报表：Top-3 准确率（>80%）、MTTR 降低（>50%）、误报率（<10%）、人工接管率（<30%）、端到端延迟（<5min） |
| 运行方式 | 每周日 02:00 定时全量评估 + 事件驱动增量评估；结果写 Grafana + 通知系统管理员 |
| 调优联动 | 准确率连续 2 周 < 75% → 触发置信度权重重标定建议；误报率 > 10% → 建议收紧投票阈值（3/3 全票） |

## 9. 工具层设计（MCP 工具注册表）

| 工具名 | 功能 | 输入（摘要） | 输出（摘要） | 权限 |

| query_graph | 图谱多跳查询 | template(rootcause_trace 等4种), params | nodes + edges | graph:read |

| notify_human | 发送通知 | user_id/target_role, type, payload | sent | notify:send |

## 10. 记忆与上下文管理

| 层级 | 实现 | 内容 | 生命周期 |
|---|---|---|---|
| 工作记忆 | AgentState（LangGraph） | 当前任务的异常/证据/建议 | 任务周期，checkpointer 持久化 |
| 情景记忆 | PostgreSQL（agent_tasks 关联链） | 历史任务全链路（可检索"该设备上次类似异常"） | 永久 |
| 语义记忆 | Neo4j + pgvector | 设备-缺陷统计关系（PRODUCES 边权重随终审根因更新）、CAPA 文档 | 持续沉淀 |
| 程序记忆 | FDC 规则库 / 提示词模板（配置化） | 检测规则、提示词版本 | 版本管理 |

上下文裁剪：LLM 输入只注入当前嫌疑相关的 Top 证据（每类 ≤3 条、每条摘要 ≤200 字），历史任务仅注入摘要卡片；超长工具输出（如 24h 原始时序）先做统计聚合再入上下文。

## 11. Token 成本控制

| 措施 | 说明 |
|---|---|
| 分级模型路由 | 根因/报告用本地旗舰模型；建议模板化生成优先走规则引擎，仅 summary 用小模型；监控 Agent 纯算法零 Token |
| 证据摘要化 | 工具输出预压缩（JSON→结构化摘要），单任务 LLM 输入预算 ≤ 8K token |
| 缓存复用 | 同设备同参数 24h 内重复任务的图谱/RAG 证据复用（Redis，key: evidence:{equip}:{param}） |
| 预算熔断 | 单任务 token_usage 超 50K → 中止并降级为"仅确定性证据+模板报告"；日预算耗尽 → 新任务直接走人工通道 |
| 计量与报表 | token_usage 按 node 累计入 AgentState 与 model_meta；Grafana 展示单任务/日均 Token 成本 |
